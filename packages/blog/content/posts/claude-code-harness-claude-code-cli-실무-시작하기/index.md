## GUI형 Claude (Artifacts)와 CLI의 근본 차이 (파일 직접 편집,명령 실행, 영속적 메모리) 이해

새로운 섹션이 시작됩니다. 앞 섹션에서 **6가지 하네스**로 Claude Code라는 작업 시스템의 설계도를 그렸다면, 이번 섹션은 그 시스템을 **실제로 손에 쥐는** 이야기입니다. 그리고 그 출발점은 도구
선택입니다.

강사 **미국달팽이**님은 이 강의의 방향을 첫 문장부터 못 박습니다.

> "이 강의는 Claude Code **GUI 앱으로 작업을 할 수 있도록 하는 것이 아니라 터미널 CLI 버전으로** Claude Code를 어떻게 유용하게 사용할 수 있는지, 실무에서 어떻게 협업하고
> 어떻게 **AI 네이티브 엔지니어**로서 어떻게 사용을 해야 되는지 등에 대한 실무적 강의를 진행하도록 합니다."

왜 굳이 CLI일까요. 이 챕터는 그 이유를 **실무의 구조**에서 찾습니다.

### 대부분의 강의가 GUI에서 시작하는 이유

Claude Code를 다루는 강의들은 보통 GUI에서 출발합니다. 이유는 단순합니다. **보여 주기 쉽기 때문**입니다.

| 접근               | 형태                                       |
|--------------------|--------------------------------------------|
| **GUI 중심 강의**  | 채팅창에 질문하고 **코드를 추천받는** 방식 |
| **이론 중심 강의** | 개념 설명 위주                             |

두 방식 모두 "Claude가 코드를 잘 짜 준다"는 사실은 잘 보여 줍니다. 그런데 실무에서 우리가 겪는 어려움은 **코드를 못 짜서**가 아닙니다.

### 실무의 본질은 다섯 단계다

여기서 강사는 시선을 도구에서 **일 자체**로 옮깁니다.

> "그런데 여기서 한번 생각을 해보면 실제 백엔드 실무나 프론트 실무 같은 경우에는 **제일 작은 단위로 쪼개서 진행을 했을 때 결국 우리가 하는 일은 몇 가지 밖에 없어요.**"

그리고 그 "몇 가지"를 다섯으로 정리합니다.

> "그렇기 때문에 **실무의 본질은 5단계로 구성이 되어 있다**고 할 수 있습니다."

| # | 단계            | 하는 일                  |
|---|-----------------|--------------------------|
| 1 | **관찰**        | 문제를 관찰한다          |
| 2 | **원인 좁히기** | 원인을 좁힌다            |
| 3 | **수정**        | 코드를 고친다            |
| 4 | **검증**        | 제대로 됐는지 확인한다   |
| 5 | **반영**        | 안전하게 코드를 반영한다 |

```
  관찰  →  원인 좁히기  →  수정  →  검증  →  반영
```

이 다섯 단계를 놓고 보면 뭔가 눈에 띕니다. **"코드 작성"은 다섯 중 하나 (3번)일 뿐**입니다. 나머지 넷은 전부 **코드 바깥의 일**입니다. 로그를 보고, 파일을 뒤지고, 테스트를 돌리고, diff를
확인하고, 브랜치를 정리하는 일이죠.

GUI 채팅이 잘하는 것은 3번 하나입니다. 그런데 실무의 병목은 대개 나머지 넷에 있습니다.

### GUI 방식의 진짜 문제: 흐름이 끊긴다

GUI로 이 다섯 단계를 처리하면 어떤 모습이 될까요.

```
 [GUI 방식의 하루]

  터미널에서 로그를 본다
      ↓  (복사)
  채팅창에 붙여넣고 물어본다
      ↓  (답변 복사)
  에디터로 가서 반영한다
      ↓
  터미널로 돌아가 테스트를 돌린다
      ↓  (실패 로그 복사)
  다시 채팅창으로 간다
      ↓
  git status를 확인한다
      ↓
  Docker를 확인한다
      ↓
  배포 전 검토를 한다
```

문제는 **각 단계가 나쁜 게 아니라, 단계 사이를 사람이 손으로 이어 붙이고 있다**는 점입니다. 복사하고, 붙여넣고, 창을 바꾸고, 다시 복사합니다.

| 구분               | GUI                | CLI                    |
|--------------------|--------------------|------------------------|
| **강한 영역**      | **대화**           | **작업 흐름 연결**     |
| **위치**           | 작업 환경 **바깥** | 작업 환경 **안**       |
| **단계 사이 이동** | 사람이 손으로 옮김 | **그 자리에서 이어짐** |

### CLI의 강점은 "작업 흐름 연결"이다

CLI로 옮기면 다섯 단계가 **하나의 흐름 안에서** 처리됩니다.

| 실무 작업          | CLI에서 가능한가 |
|--------------------|------------------|
| **로그 읽기**      | ⭕               |
| **파일 찾기**      | ⭕               |
| **설정 확인**      | ⭕               |
| **수정안 만들기**  | ⭕               |
| **테스트 실행**    | ⭕               |
| **Diff 검토**      | ⭕               |
| **브랜치 정리**    | ⭕               |
| **배포 직전 단계** | ⭕               |

관찰부터 반영 직전까지, **터미널을 벗어나지 않고** 이어집니다. 강사가 강조하는 표현이 이것입니다.

> **GUI는 대화에 강하지만, CLI는 작업 흐름 연결을 이어 주어 처리량을 늘릴 수 있습니다.**

여기서 **"처리량 (throughput)"** 이라는 단어가 중요합니다. "더 똑똑한 답"이 아니라 **"단위 시간에 끝내는 일의 양"** 입니다. 답의 품질이 아니라 **흐름의 연속성**이 만들어 내는
이득입니다.

```
  GUI  :  대화 품질은 좋지만 단계마다 사람이 이어 붙임 → 처리량 제한
  CLI  :  단계가 그대로 이어짐                         → 처리량 증가
```

### 그래서 근본 차이는 무엇인가

챕터 제목이 짚는 세 가지가 바로 이 "흐름 연결"을 가능하게 하는 조건들입니다.

| 근본 차이          | GUI형 Claude (Artifacts)            | CLI (Claude Code)                   |
|--------------------|-------------------------------------|-------------------------------------|
| **파일 직접 편집** | 코드를 **보여 준다** → 사람이 옮김  | **프로젝트 파일을 직접 수정**한다   |
| **명령 실행**      | 실행 결과를 **사람이 알려 줘야** 함 | **테스트·빌드·git을 직접 실행**한다 |
| **영속적 메모리**  | 세션이 끝나면 사라짐                | **`CLAUDE.md`로 규칙이 남는다**     |

세 가지가 각각 다섯 단계의 어디를 담당하는지 보면 그림이 맞아떨어집니다.

```
  관찰 ──── 명령 실행 (로그·상태를 직접 본다)
  원인 ──── 파일 직접 편집 권한 (코드를 직접 뒤진다)
  수정 ──── 파일 직접 편집
  검증 ──── 명령 실행 (테스트를 직접 돌린다)
  반영 ──── 명령 실행 (git·diff를 직접 다룬다)

  그리고 이 전부를 관통하며 규칙을 유지하는 것 = 영속적 메모리
```

**영속적 메모리**가 특히 중요합니다. 앞 섹션의 Context Harness 챕터에서 본 것처럼, 각 세션은 `FreshContext` 윈도우로 시작합니다. 그 위에 `CLAUDE.md`가 프로젝트 규칙을 매번
다시 실어 나릅니다. GUI 채팅은 매번 "우리 프로젝트는 이런 규칙이 있어요"를 다시 설명해야 하지만, **CLI는 그 설명을 파일로 고정**합니다.

그리고 파일로 고정된다는 것은 **저장소에 커밋되고, 팀이 공유한다**는 뜻이기도 합니다. 개인의 노하우가 팀의 규칙이 되는 지점이죠.

### "AI가 다 해준다"는 환상이다

이 챕터에서 가장 균형 잡힌 대목입니다. 강사는 CLI를 권하면서도, 기대치를 분명히 조정합니다.

> "**중요한 건 AI가 다 해준다는 게 아닙니다. 이건 환상인데**, 아직까지는 그렇기 때문에 진짜 중요한 건 **사람이 하던 반복적인 탐색이나 정리, 초안 작성, 검토 보조, 협업 이런 단계에서 어디까지
> 할 수 있는지, 사람은 그만큼 더 중요한 판단에 집중할 수 있는지**가 더 중요하기 때문에..."

즉 목표는 **대체**가 아니라 **재배치**입니다.

| 넘길 수 있는 일      | 사람이 붙들어야 할 일     |
|----------------------|---------------------------|
| **반복적인 탐색**    | **중요한 판단**           |
| **정리**             | 무엇이 옳은 방향인지 결정 |
| **초안 작성**        | 최종 책임                 |
| **검토 보조**        | 최종 검토                 |
| **협업 단계의 잡무** | 팀 차원의 의사결정        |

이 구도는 앞 섹션의 하네스 이야기와 정확히 이어집니다. 하네스 엔지니어링의 목표가 **"무한 자율성이 아니라 검증 가능한 경계"** 였던 것처럼, 여기서도 AI에게 넘길 영역과 사람이 쥘 영역을 **의도적으로
나누는** 것이 핵심입니다.

### 병목을 줄이려면 워크플로우 안으로 들어가야 한다

결론입니다.

> **실무에서 병목을 줄이려면 결국 워크플로우 안에 들어가서 작업을 해야 합니다.**

GUI를 쓰면 터미널과 채팅창을 계속 왔다 갔다 해야 합니다. 그 왕복 자체가 병목입니다. CLI는 **작업이 실제로 일어나는 곳에 AI를 데려다 놓는** 방식입니다.

```
  ❌ AI를 옆에 두고 결과를 받아 오기   →  왕복 비용이 매번 발생
  ⭕ AI를 워크플로우 안에 두기         →  왕복 자체가 사라짐
```

이 차이가 "한번 써 보니 신기하다"와 **"실제 프로젝트에서 계속 쓰는 수준"** 을 가릅니다. 강사가 CLI로 시작하는 이유가 여기 있습니다.

### 정리

1. **실무의 본질은 다섯 단계다.** `관찰 → 원인 좁히기 → 수정 → 검증 → 반영`. 이 중 "코드 작성"은 하나뿐이다.
2. **GUI가 잘하는 건 그 하나다.** 나머지 넷은 터미널에서 일어나고, GUI를 쓰면 사람이 단계 사이를 손으로 이어 붙이게 된다.
3. **CLI의 강점은 답의 품질이 아니라 작업 흐름 연결이다.** 그 결과로 늘어나는 것은 **처리량**이다.
4. **근본 차이는 세 가지다.** 파일 직접 편집 · 명령 실행 · 영속적 메모리. 각각 다섯 단계의 서로 다른 지점을 담당한다.
5. **"AI가 다 해준다"는 환상이다.** 반복적인 탐색·정리·초안·검토 보조를 넘기고, 사람은 **중요한 판단**에 집중하는 것이 목표다.
6. **병목을 줄이려면 워크플로우 안으로 들어가야 한다.** AI를 옆에 두는 게 아니라 작업이 일어나는 자리에 두는 것이다.

## [실습] Claude Code CLI 설치 → 프로젝트 초기화 → 첫 세션 실행까지 5분 완성

앞 챕터에서 "왜 CLI인가"에 답했으니, 이제 손을 움직일 차례입니다. 이 챕터는 **설치 → 프로젝트 초기화 → 첫 세션 실행**까지 한 번에 통과하는 실습입니다.

그런데 강사 **미국달팽이**님이 짚는 진짜 문제는 설치가 아닙니다.

> "Claude Code를 **설치는 했는데, 막상 쓰려면 뭐부터 해야 될지 모르겠고, 프로젝트에 들어가서 첫 프롬프트를 어떻게 던져야 할지도 애매한** 경우가 되게 많습니다."

설치는 명령어 한 줄이라 어렵지 않습니다. 정작 막히는 곳은 **"설치 다음"** 입니다. 그래서 이 챕터는 설치보다 **어디서 실행할 것인가**와 **첫 프롬프트를 무엇으로 던질 것인가**에 무게가 실립니다.

### 전체 흐름

먼저 5분 안에 지나갈 길을 한눈에 보겠습니다.

```
 1. 설치        anthropic.com에서 설치 명령어 복사 → 터미널 실행
        ↓
 2. 프로젝트     mkdir <프로젝트명>  →  cd <프로젝트명>
        ↓
 3. 실행        claude
        ↓
 4. 로그인      브라우저 인증
        ↓
 5. 첫 프롬프트  ← 여기가 진짜 시작점
```

### 1단계. Claude Code CLI 설치하기

설치 명령어는 **공식 사이트에서 그대로 가져오는 것**이 가장 안전합니다. 설치 방식은 계속 바뀌기 때문에, 외워 둔 명령어보다 **공식 페이지의 최신 안내**가 항상 옳습니다.

`anthropic.com`에 접속하면 여러 제품이 보입니다.

> "누르는 게 아니죠. **갖다 대면** Claude Code, Co-Work, Platform 여러 가지를 보실 수 있는데,"

여기서 우리가 고를 것은 명확합니다.

> "하지만 **저희는 터미널을 쓸 것이기 때문에 이 Claude Code CLI를 써 줄 겁니다.**"

Claude Code 페이지에서 제공하는 **설치 명령어를 복사해 터미널에 붙여넣으면** 설치가 진행됩니다. 참고로 널리 쓰이는 방식은 npm 전역 설치입니다.

```bash
npm install -g @anthropic-ai/claude-code
```

설치가 끝났으면 확인부터 합니다.

```bash
claude --version
```

버전이 찍히면 1단계는 끝입니다.

> **주의.** 설치 방법 (네이티브 설치 스크립트 / npm 등)은 시점에 따라 달라질 수 있습니다. 강의에서도 **공식 페이지의 명령어를 복사해 쓰는 방식**을 택하는데, 그게 가장 확실합니다.

### 2단계. 프로젝트 루트로 이동하기

설치보다 중요한 단계입니다.

> "그래서 여기서 이제 **프로젝트 루트에서 시작을 해야 됩니다.**"

강의에서는 데모용 폴더를 하나 만들어 진행합니다.

```bash
mkdir america_snail_demo
cd america_snail_demo
```

명령어 자체는 평범합니다. 그런데 **"프로젝트 루트에서 시작한다"** 는 조건은 그냥 관례가 아닙니다. 앞 섹션의 하네스 관점에서 보면 의미가 분명해집니다.

| `claude`를 실행한 위치  | 결과                                                   |
|-------------------------|--------------------------------------------------------|
| **프로젝트 루트**       | 그 프로젝트가 **작업 경계**가 된다                     |
| **홈 디렉터리 등 상위** | 경계가 넓어져 **관련 없는 파일까지 사정권**에 들어온다 |

즉 `cd`로 어디에 서느냐가 곧 **Claude가 보게 될 세계의 크기**를 정합니다. Context Harness 챕터에서 "작업면을 잘라서 준다"고 했던 것의 가장 원초적인 형태가 **디렉터리 선택**인
셈입니다.

```
  ❌ 홈에서 claude 실행     →  작업면이 통째로 열림
  ⭕ 프로젝트 루트에서 실행 →  경계가 프로젝트로 한정됨
```

기존 프로젝트에서 시작한다면 새 폴더를 만들 필요 없이 그 저장소 루트로 이동하면 됩니다.

```bash
cd ~/workspace/my-project
```

### 3단계. `claude` 실행

이제 명령어 하나면 됩니다.

```bash
claude
```

> "**claude를 입력을 해줍니다. 그러면 이 `america_snail_demo`라는 프로젝트 루트에서 Claude Code가 열린 거예요.**"

여기서 "**프로젝트 루트에서 열렸다**"는 표현이 핵심입니다. Claude Code는 **어디서 실행됐는지를 기억한 채로** 켜집니다. 앞 챕터에서 말한 **파일 직접 편집**과 **명령 실행**이 바로 이 위치를
기준으로 작동합니다.

### 4단계. 로그인

첫 실행이면 로그인 절차를 거칩니다. 인증이 끝나면 **Claude Code 인터페이스**가 나타납니다. 참고로 강의에서는 이 시점에 **보이스 모드** 같은 신규 기능도 함께 언급합니다. CLI라고 해서 텍스트
입력만 있는 것은 아니라는 이야기죠.

여기까지가 대략 5분입니다. 설치 1~2분, 폴더 만들고 이동하는 데 몇 초, 로그인 1~2분.

### 5단계. 그래서 첫 프롬프트는 무엇을 던지나

빈 화면 앞에서 대부분 여기서 멈춥니다. 강사가 지적한 **"첫 프롬프트를 어떻게 던져야 할지 애매한"** 순간이죠.

앞 섹션의 **Context Harness** 기준을 적용하면 답이 나옵니다. 거기서 얻은 결론이 **"Context Harness의 목적은 Claude가 올바른 첫 번째 행동을 하게 만드는 것"** 이었으니까요.

그렇다면 첫 프롬프트로 **하지 말아야 할 것**부터 분명해집니다.

| ❌ 나쁜 첫 프롬프트           | 왜 문제인가                                   |
|-------------------------------|-----------------------------------------------|
| "이 프로젝트 개선해 줘"       | 목표도 범위도 없어 **아무 파일이나 건드린다** |
| "로그인 기능 만들어 줘"       | 기존 구조를 모른 채 **새로 짜기 시작한다**    |
| (기존 프로젝트에서) "고쳐 줘" | 탐색 없이 **바로 Edit으로 직행**한다          |

반대로 좋은 첫 행동은 **탐색**입니다. `Explore → Plan → Edit → Verify` 순서에서 첫 칸이 `Explore`인 이유가 그것이죠.

```
[빈 폴더에서 시작할 때]
  · 무엇을 만들 것인지 목표를 먼저 말한다
  · 기술 스택과 제약을 함께 준다
  · 구조를 제안받고 → 확인한 뒤 → 구현으로 넘어간다

[기존 프로젝트에서 시작할 때]
  · "먼저 프로젝트 구조를 파악하고 요약해 줘"
  · "인증이 어디서 처리되는지 관련 파일을 찾아 줘"
  · 수정은 그 다음이다
```

첫 프롬프트를 **"고쳐 줘"가 아니라 "살펴봐 줘"로 시작하는 것.** 이것만으로도 첫 세션의 결과가 달라집니다.

### 설치 다음에 바로 해야 할 것

세션이 열렸다고 준비가 끝난 건 아닙니다. 앞 챕터에서 CLI의 근본 차이로 꼽았던 세 가지 중 **영속적 메모리**가 아직 비어 있기 때문입니다.

| 근본 차이          | 지금 상태                      |
|--------------------|--------------------------------|
| **파일 직접 편집** | ✅ 프로젝트 루트에서 열림      |
| **명령 실행**      | ✅ 바로 사용 가능              |
| **영속적 메모리**  | ❌ **아직 `CLAUDE.md`가 없음** |

지금 상태의 Claude Code는 **매 세션마다 이 프로젝트를 처음 보는 상태로 시작**합니다. 규칙도, 컨벤션도, 금지 사항도 모릅니다. 그래서 강의도 다음 순서로 **`CLAUDE.md` 설정과 메모리
기능**을 예고합니다.

```
  설치 완료  →  세션 열림  →  [다음] CLAUDE.md로 규칙 고정
                              [다음] settings.json으로 권한 설계
```

앞 섹션의 표현을 빌리면, 지금은 **하네스가 비어 있는 상태**입니다. 도구는 손에 쥐었지만 경계는 아직 그리지 않았습니다.

### 정리

1. **설치는 공식 페이지의 명령어를 복사해 쓰는 것이 가장 안전하다.** `claude --version`으로 확인한다.
2. **반드시 프로젝트 루트에서 실행한다.** `cd`로 어디에 서느냐가 곧 **Claude가 보게 될 작업 경계**다.
3. **`claude` 한 줄로 세션이 열린다.** 첫 실행이면 로그인 절차를 거친다.
4. **첫 프롬프트는 "고쳐 줘"가 아니라 "살펴봐 줘"다.** 올바른 첫 번째 행동은 언제나 **탐색**이다.
5. **여기까지는 도구를 쥔 것일 뿐이다.** `CLAUDE.md`와 권한 설정이 붙어야 비로소 작업 시스템이 된다.

## Claude Code architecture - Claude Code의 병목 지점 파악하기

세션은 열었습니다. 이제 **"잘 안 될 때 어디를 봐야 하는가"** 를 알아야 할 차례입니다. 이 챕터는 Claude Code의 아키텍처를 **네 개의 레이어**로 쪼개고, 각 레이어가 어떤 증상의 원인이 되는지를
짚습니다.

### Claude Code는 답하는 도구가 아니라 이어서 하는 도구다

먼저 정의부터 다시 잡습니다. Anthropic 공식 문서는 Claude Code를 **에이전틱 코딩 툴 (agentic coding tool)** 로 설명합니다. 하는 일은 넷입니다.

- 코드베이스를 **읽고**
- 파일을 **수정하고**
- 명령을 **실행하고**
- 개발 도구와 **통합한다**

강사 **미국달팽이**님은 이 정의에서 핵심을 하나 뽑아냅니다.

> "**클로드 코드의 핵심은 질문에 답하는 게 아니라 작업을 이어서 수행하는 거다** 라고 보시면 될 것 같아요."

이 차이가 왜 중요할까요. 실무의 작업 흐름은 **한 번의 답변으로 끝나지 않기 때문**입니다.

```
  문제 관찰  →  원인 좁히기  →  파일 수정  →  설정 확인  →  테스트  →  검토
       ↑                                                              │
       └──────────  중간 상태를 읽고 다시 판단하고 다시 실행  ─────────┘
```

앞 챕터의 5단계가 여기서 **반복 루프**로 다시 등장합니다. 새 코드베이스를 이해하고, 버그를 디버깅하고, 리팩터링하고, 테스트를 쓰는 일 전부가 이 루프 위에서 벌어집니다.

그래서 Claude Code는 코딩 전용 도구도 아닙니다.

> "클로드 코드는 **터미널 안에서 동작하는 에이전트형 어시스턴트**라고 할 수 있고요, **코딩 뿐만 아니라 명령줄에서 할 수 있는 작업**, 커맨드에서 할 수 있는 작업이죠."

문서 작성, 빌드 실행, 파일 검색, 조사까지 **명령줄에서 가능한 일이면 사정권**입니다. 그래서 이렇게 이해하는 편이 정확합니다.

> "클로드 코드는 **대화 인터페이스라기보다는 명령줄 작업과 연결된 실행 시스템**으로 이해하는 게 맞습니다."

### 아키텍처를 이루는 구성 요소들

Claude Code를 작업 시스템으로 만드는 부품들을 먼저 훑겠습니다.

| 구성 요소                     | 역할                                               |
|-------------------------------|----------------------------------------------------|
| **`CLAUDE.md`**               | 프로젝트 수준의 지시·규칙을 유지하는 **기억 장치** |
| **`/init`**                   | 그 시작 파일을 만들어 주는 명령                    |
| **Skills**                    | 반복 가능한 워크플로우를 Claude의 **툴킷에 추가**  |
| **Hooks**                     | 특정 시점마다 **반드시 실행되는** 규칙·자동화      |
| **GitHub Actions**            | PR·이슈 흐름 안에서 **실제 협업 시스템과 연결**    |
| **Agent / Teams / Sub-Agent** | **컨텍스트를 분리**하고 작업을 병렬화              |

Hooks의 설명에 특히 주목할 만합니다. Hooks는 **LLM이 선택적으로 하지 않도록 통제하는 장치**입니다. 즉 "하면 좋은 것"이 아니라 **"안 할 수 없게 만드는 것"** 이죠. 앞 섹션 Tool
Harness 챕터의 "결정론적 개입"과 같은 이야기입니다.

이 요소들이 모여 만드는 것은 결국 하나입니다.

> **기억 · 컨텍스트 · 실행 · 검증 · 자동화 · 협업을 아우르는 작업 시스템.**

### 네 개의 레이어

이 챕터의 핵심입니다. Claude Code 아키텍처를 **네 층**으로 나눠서 봅니다.

```
 ┌──────────────────────────────────────────────┐
 │ 1. 규칙 레이어      세션이 바뀌어도 유지되는 기준 │  CLAUDE.md
 ├──────────────────────────────────────────────┤
 │ 2. 컨텍스트 레이어   이번 작업에 필요한 문맥      │  문제·파일·로그·범위
 ├──────────────────────────────────────────────┤
 │ 3. 전략 레이어      어떻게 진행할 것인가 판단     │  계획 vs 실행, 서브에이전트
 ├──────────────────────────────────────────────┤
 │ 4. 실행·검증 레이어  실제 반영과 확인            │  수정·테스트·diff·git·PR
 └──────────────────────────────────────────────┘
```

#### 1. 규칙 레이어 (Rule Layer)

`CLAUDE.md`에 담기는 층입니다. **세션이 바뀌어도 유지되어야 하는 기준**이 여기 들어갑니다.

- 프로젝트 규칙
- 금지 사항
- 코딩 스타일 컨벤션

이 층이 약하면 어떻게 될까요.

> "**이 레이어가 약하면 같은 프로젝트인데도 세션마다 계속 결과가 흔들릴 수가 있어요.**"

같은 요청을 했는데 어제와 오늘의 결과물이 다르다면, 모델이 변덕스러운 게 아니라 **기준이 파일로 고정돼 있지 않은 것**입니다.

#### 2. 컨텍스트 레이어 (Context Layer)

**이번 작업**에 필요한 문맥입니다.

- 해결하려는 문제
- 관련 파일
- 실패 로그
- 수정 범위

이 층이 잘못되면 **Claude가 엉뚱한 방향으로 나아갑니다.** 앞 섹션 Context Harness 챕터에서 다룬 내용이 그대로 이 층에 대응합니다.

#### 3. 전략 레이어 (Strategy Layer)

가장 자주 빠뜨리는 층입니다. **어떻게 진행할 것인가**를 판단합니다.

| 판단해야 할 것           | 선택지                             |
|--------------------------|------------------------------------|
| 바로 수정할 것인가       | vs **먼저 계획할 것인가**          |
| 메인 세션에서 할 것인가  | vs **서브 에이전트를 쓸 것인가**   |
| 어디까지 자동화할 것인가 | vs **어디서 사람이 검토할 것인가** |

핵심은 **작업 종류에 따라 계획과 실행을 구분**하는 것입니다. 한 줄 오타 수정에 계획 단계를 붙일 필요는 없지만, 여러 파일에 걸친 변경은 계획 없이 들어가면 반드시 흔들립니다.

#### 4. 실행·검증 레이어 (Execution & Verification Layer)

실제로 **반영과 확인이 일어나는** 층입니다.

- 파일 수정
- 테스트 실행
- diff 검토
- Git 정리
- 자동 검증
- PR 생성

그리고 이 층을 강화하는 장치가 **Hooks**와 **GitHub Actions**입니다. 사람이 매번 챙기는 대신 **구조가 챙기게 만드는** 것이죠.

### 증상으로 병목 레이어를 찾는 법

이 챕터가 실무적으로 가장 쓸모 있는 대목입니다. 증상을 레이어로 번역하는 표입니다.

| 증상                                 | 병목 레이어          | 보강 방법                          |
|--------------------------------------|----------------------|------------------------------------|
| **세션마다 결과가 다르다**           | **규칙 레이어**      | `CLAUDE.md`에 기준을 고정          |
| **자꾸 엉뚱한 파일을 건드린다**      | **컨텍스트 레이어**  | 작업면·수정 범위를 잘라서 제공     |
| **수정 품질이 들쭉날쭉하다**         | **전략 레이어**      | 계획/실행 구분, 서브 에이전트 활용 |
| **코드는 맞는데 충돌·버그가 생긴다** | **실행·검증 레이어** | 테스트·diff·Hooks·CI 보강          |

네 번째 항목이 특히 인상적입니다. **"코드가 맞아도"** 충돌이나 버그가 난다면 그건 코드 문제가 아니라 **반영 절차의 문제**라는 뜻입니다. 로직은 옳은데 브랜치가 꼬였거나, 검증 없이 머지됐거나 하는
경우죠.

### 프롬프트만 잘 쓴다고 되는 도구가 아니다

이 챕터의 결론입니다.

> "**이렇게 구조를 나눠서 보면 Claude Code는 프롬프트만 잘 쓴다고 해서 되는 도구가 아니라는 것을 알 수가 있죠.**"

네 레이어 중 프롬프트가 관여하는 건 주로 **컨텍스트 레이어** 하나입니다. 나머지 셋은 **파일과 설정과 절차**의 영역입니다.

| 레이어        | 손대는 수단                     |
|---------------|---------------------------------|
| **규칙**      | `CLAUDE.md` (파일)              |
| **컨텍스트**  | 프롬프트·작업면 설계            |
| **전략**      | 진행 방식의 선택 (사람의 판단)  |
| **실행·검증** | Hooks · GitHub Actions · 테스트 |

그래서 각 구성 요소를 **"무엇을 할 수 있는 기능"** 이 아니라 **"어떤 병목을 줄이는 도구"** 로 이해해야 합니다.

| 구성 요소          | 줄여 주는 병목                                           |
|--------------------|----------------------------------------------------------|
| **`CLAUDE.md`**    | 단순한 메모가 아니라 **프로젝트 규칙을 안정시키는 장치** |
| **Skills**         | 반복 워크플로우를 **매번 다시 설명하지 않게** 만듦       |
| **Hooks**          | 중요한 검증·규칙을 **잊지 않게** 만듦                    |
| **GitHub Actions** | 개인 사용을 **팀 협업으로 확장**                         |

### 결국 하나의 루프로 연결된다

마지막으로 전체를 다시 붙여 보면 이렇습니다.

```
  코드베이스 이해  →  문맥 유지  →  전략 선택  →  파일 수정
        ↑                                            ↓
     협업·자동화  ←  검증  ←──────────────────  명령 실행
```

이해부터 협업까지가 **끊기지 않는 하나의 루프**이고, 앞서 본 구성 요소들은 각자 이 루프의 **다른 지점을 받치고** 있습니다. 어느 한 곳이 약하면 루프 전체가 그 지점에서 막힙니다. 그게 병목입니다.

### 정리

1. **Claude Code는 답하는 도구가 아니라 이어서 하는 도구다.** 대화 인터페이스가 아니라 **명령줄 작업과 연결된 실행 시스템**으로 이해해야 한다.
2. **아키텍처는 네 층이다.** `규칙` · `컨텍스트` · `전략` · `실행·검증`.
3. **증상마다 병목 레이어가 다르다.** 세션마다 결과가 다르면 규칙, 엉뚱한 파일이면 컨텍스트, 품질이 들쭉날쭉하면 전략, 충돌·버그면 실행·검증이다.
4. **가장 자주 빠지는 건 전략 레이어다.** 작업 종류에 따라 **계획과 실행을 구분**하는 판단이 필요하다.
5. **프롬프트가 닿는 건 네 층 중 하나뿐이다.** 나머지는 `CLAUDE.md`·Hooks·CI 같은 **파일과 절차**로 보강한다.
6. **구성 요소는 기능이 아니라 병목 해소 도구로 보라.** "무엇을 할 수 있나"가 아니라 **"어떤 병목을 줄이나"** 가 선택 기준이다.

## 세션 간 memory와 CLAUDE.md 역할 구분 + context control 기본 명령어 마스터

앞 챕터에서 네 개의 레이어를 봤고, 그중 **규칙 레이어**와 **컨텍스트 레이어**가 흔들리면 어떤 증상이 나오는지도 확인했습니다. 이번 챕터는 그 두 층을 실제로 다루는 방법입니다.

시작은 익숙한 문제 제기입니다. 큰 코드베이스에서 Claude가 헛돌거나 엉뚱한 파일을 건드릴 때, 그건 **모델 성능이 떨어져서가 아닙니다.** 잘못된 컨텍스트를 줬기 때문입니다. Anthropic 공식 문서가
코드베이스 탐색, 세션 관리, 병렬 작업, 컨텍스트 운영을 반복해서 강조하는 이유이기도 합니다.

### 핵심은 프롬프트가 아니라 컨텍스트 컨트롤이다

강사 **미국달팽이**님은 이 챕터의 결론을 초반에 꺼내 놓습니다.

> "**클로드 코드를 잘 쓰는 핵심은 프롬프트를 잘 쓰는 게 아니라 작업 범위와 맥락을 어떻게 제어하느냐에 있습니다.**"

그리고 큰 코드베이스에서의 실패 원인을 이렇게 정리합니다.

```
  컨텍스트가 부족해서 실패    <   컨텍스트가 넓고 흐려서 실패
```

Anthropic 문서 역시 **컨텍스트 매니지먼트가 비용과 품질 모두에 영향을 준다**고 설명합니다. 넓은 컨텍스트는 돈도 더 들고 결과도 나쁘다는 뜻이죠.

### 큰 코드베이스가 어려운 진짜 이유

우리는 보통 "파일이 많아서 어렵다"고 생각합니다. 그런데 진짜 이유는 조금 다릅니다.

> 큰 코드베이스가 어려운 이유는 **파일이 많아서가 아니라 관련 없는 파일이 너무 많기 때문**입니다.

Claude에게 지나치게 넓은 컨텍스트를 주면 **모델이 아무리 좋아도 문제 정의 자체가 흐려집니다.** 반대로 뒤집어 보면 기회이기도 합니다. 규모가 큰 코드 환경일수록 **어디가 관련 코드인지 더 강하게 식별할
수 있다**는 점이 여러 엔지니어링 자료에서 반복해서 나옵니다.

그래서 사람의 역할이 달라집니다.

> "즉, **AI가 계속 빨라질수록 사람은 더 정확하게 경계를 만들어 줘야** 되는 겁니다."

> "**컨텍스트 컨트롤의 목표는 많이 보여주기가 아니라 정확하게 보여주는 겁니다.**"

```
  ❌ 많이 보여주기   →  문제 정의가 흐려짐
  ⭕ 정확히 보여주기 →  판단이 선명해짐
```

### 세션 간 memory와 `CLAUDE.md`는 층이 다르다

챕터 제목이 짚는 첫 번째 주제입니다. Claude Code에서 "기억"은 하나가 아니라 **여러 층**으로 되어 있고, 각각 **수명과 성격이 다릅니다.**

| 층                | 수명            | 누가 쓰는가       | 성격                        |
|-------------------|-----------------|-------------------|-----------------------------|
| **세션 컨텍스트** | **이번 세션만** | 대화하며 쌓임     | 휘발성. `/clear`하면 사라짐 |
| **Auto Memory**   | 세션을 넘어감   | **Claude가 작성** | 자동으로 남는 기억          |
| **`CLAUDE.md`**   | 세션을 넘어감   | **사용자가 작성** | **의도적으로 고정한 규칙**  |

앞 섹션 Context Harness 챕터에서 확인했듯, 각 세션은 **`FreshContext` 윈도우로 시작**합니다. 즉 기본값은 "아무것도 모르는 상태"이고, `CLAUDE.md`와 Auto Memory가 그
위에 지식을 실어 나릅니다.

역할을 나누면 이렇게 정리됩니다.

| 넣을 곳           | 넣어야 할 것                                            |
|-------------------|---------------------------------------------------------|
| **`CLAUDE.md`**   | 프로젝트 규칙, 금지 사항, 코딩 컨벤션, 빌드·테스트 명령 |
| **세션 컨텍스트** | 이번 작업의 문제·관련 파일·실패 로그·수정 범위          |

구분 기준은 간단합니다. **다음 세션에도 필요한가?** 필요하면 `CLAUDE.md`, 이번 작업에만 필요하면 세션 컨텍스트입니다.

```
  "우리 프로젝트는 컨트롤러에 비즈니스 로직을 두지 않는다"  →  CLAUDE.md
  "지금 로그인 API에서 500이 난다"                          →  세션 컨텍스트
```

그리고 앞 섹션에서 강조한 함정을 다시 기억해야 합니다. **`CLAUDE.md`는 강제가 아니라 제공되는 컨텍스트**입니다. 반드시 막아야 하는 것은 `permissions`나 `hooks`로 옮겨야 합니다.

### 컨텍스트 컨트롤의 세 단계

이 챕터의 핵심 도구입니다. 컨텍스트를 좁히는 작업은 **세 개의 범위**로 나뉩니다.

| 단계             | 좁히는 것                | 실패했을 때                                 |
|------------------|--------------------------|---------------------------------------------|
| **1. 문제 범위** | **무엇을 고치나**        | Claude도 **왔다 갔다** 한다                 |
| **2. 파일 범위** | **어디를 보나**          | 엉뚱한 파일을 건드린다                      |
| **3. 세션 범위** | **무엇을 하는 세션인가** | 조사·수정·검토가 뒤섞여 **판단이 흐려진다** |

#### 1. 문제 범위 줄이기

기준이 명확합니다. **지금 무엇을 고치는지 한 문장으로 줄이지 못하면**, Claude도 왔다 갔다 할 수밖에 없습니다. 사람이 한 문장으로 못 쓰는 문제를 모델이 정확히 겨냥할 리는 없죠.

#### 2. 파일 범위 줄이기

한 번에 좁히는 게 아니라 **두 단계**입니다.

```
  관련 파일 후보를 먼저 모은다  →  거기서 실제 수정할 파일을 좁힌다
```

이 순서가 중요합니다. 처음부터 "이 파일만 고쳐"라고 못 박으면 원인이 다른 데 있을 때 놓치고, 그렇다고 전체를 열어 두면 흐려집니다. **후보 → 확정**의 두 단계가 그 사이를 메웁니다.

#### 3. 세션 범위 줄이기

가장 자주 어기는 항목입니다. **조사 세션과 수정 세션, 검토 세션을 섞으면 안 됩니다.** 하나의 세션 안에서 다 하려고 하면, 조사 과정의 잡음이 그대로 수정 판단에 섞여 들어갑니다.

앞 섹션 Subagent & Worktree Harness 챕터의 **역할 분리**가 여기서는 **세션 분리**로 나타나는 셈입니다.

### 컨텍스트를 분리하는 공식 패턴들

Anthropic 공식 자료도 같은 방향을 가리킵니다. 컨텍스트를 분리하고 관리하는 패턴들이죠.

| 패턴                  | 하는 일                         |
|-----------------------|---------------------------------|
| **Built-in Explorer** | 탐색을 **별도로** 수행          |
| **Plan**              | 실행 전에 **계획을 분리**       |
| **Sub-agent**         | 작업을 **다른 컨텍스트로 위임** |

공통점은 하나입니다. **무엇을 해야 하는지 충분히 이해하고, 작업 사이의 경계를 나눌 줄 아는 것.**

### 에이전트를 좋은 인턴처럼 다뤄라

이 챕터에서 가장 기억에 남는 비유입니다.

> 에이전트를 **좋은 인턴처럼 업무에 투입한다**고 생각하는 편이 맞습니다.

좋은 인턴에게도 한 번에 모든 것을 맡기지는 않습니다. 대신 세 가지를 알려 줍니다.

| 알려 줘야 할 것           | 내용                       |
|---------------------------|----------------------------|
| **지금 뭘 해야 하나**     | 이번 작업의 목표           |
| **어디까지가 범위인가**   | 건드릴 곳과 건드리지 말 곳 |
| **어떤 기준으로 볼 건가** | 결과를 판정하는 기준       |

그리고 맡긴 뒤에도 할 일이 있습니다.

- 작업하는 동안 **터미널에서 흐름을 지켜본다**
- 필요하면 **맥락을 보완해 준다**
- 다음 단계로 넘어갈 때 **핵심 정보가 유지되도록** 관리한다

여기서 나오는 정의가 인상적입니다.

> **에이전트를 잘 쓰는 사람은 에이전트를 많이 만드는 사람이 아니라, 에이전트마다 충분한 맥락을 유지한 채 작업을 넘겨주는 사람입니다.**

앞 섹션 Tool Harness의 "많이 붙이는 게 아니라 제자리에 두는 것"과 같은 결의 이야기입니다.

### 에이전트 친화적 코드베이스

여기서 이야기가 한 단계 확장됩니다. 아무리 Claude를 잘 써도, **코드베이스 자체가 에이전트 친화적이지 않으면 계속 흔들립니다.**

> "**코드베이스가 약하면 에이전트는 그 약점을 증폭시키죠.**"

증폭의 과정은 이렇습니다.

```
  에이전트가 코드를 잘못 이해한다
        ↓
  잘못된 이해를 바탕으로 수정안을 만든다
        ↓
  수정안이 새로운 오류를 만든다
        ↓
  그 오류를 다시 잘못 해석한다
        ↓
  더 큰 혼란
```

그래서 **에이전트 친화적 코드베이스**의 조건을 다섯 가지로 정리합니다.

| # | 조건                     | 확인 질문                                          |
|---|--------------------------|----------------------------------------------------|
| 1 | **테스트 커버리지**      | 테스트 커버리지가 충분한가?                        |
| 2 | **README와 코드 일관성** | README와 실제 코드베이스가 일관적인가?             |
| 3 | **설계 패턴 일관성**     | 설계 패턴이 프로젝트 전체에서 비슷하게 유지되는가? |
| 4 | **빌드·실행 명확성**     | 빌드와 실행 방식이 명확한가?                       |
| 5 | **스타일·규칙 준수**     | 스타일과 규칙이 흔들리지 않는가?                   |

핵심은 **"에이전트가 구조를 이해할 수 있는가"** 입니다. 사람은 애매한 부분을 경험으로 메우지만, 에이전트는 그 애매함을 **그대로 판단 재료로** 씁니다.

### 컨텍스트 컨트롤은 프롬프트 기술이 아니다

그래서 결론이 이렇게 확장됩니다.

> **컨텍스트 컨트롤은 프롬프트 기술이 아닙니다. 코드베이스의 설계, 그리고 테스트·문서화 수준과 연결되어 있는 엔지니어링 문제입니다.**

큰 코드베이스에서 Claude가 덜 헛돌게 하려면 결국 세 가지가 필요합니다.

1. **설계를 일관되게** 하고 있는가
2. **테스트가 충분**한가
3. **문서와 실제 코드가 어긋나지 않는가**

전부 AI가 등장하기 전부터 좋은 코드베이스의 조건이던 것들입니다. 달라진 건 **이것들이 안 되어 있을 때의 대가가 커졌다**는 점이죠.

### 큰 그림만 잘 잡으면 된다? 반대다

이 챕터에서 가장 반직관적인 대목입니다.

> "**많은 사람이 AI 시대에는 큰 그림만 잘 잡으면 된다고 생각을 할 수 있는데, 실제로는 반대입니다.**"

디테일이 단단해야 그 위에서 새로운 기능도, 문제 해결도, 자동화도 안정적으로 나옵니다. 그래서 **AI 네이티브 엔지니어**의 정의도 달라집니다.

| 흔한 이미지                 | 실제                                                                        |
|-----------------------------|-----------------------------------------------------------------------------|
| **도구를 많이 붙이는 사람** | **설계·테스트·빌드의 핵심을 탄탄하게 만든 뒤 그 위에 에이전트를 얹는 사람** |

그리고 접근 방식도 마찬가지입니다. **한 번에 완벽한 에이전트 시스템을 만들려고 하면 대부분 실패합니다.** 단계적으로 구축하고, 실험하고, 피드백을 보고, 그 결과를 다시 워크플로에 반영하는 것이 맞습니다.

> 앞으로는 **새로운 도구와 워크플로를 얼마나 빨리 흡수하고 구조화할 수 있는가**가 더 중요해집니다. "왜 이렇게 된 거지?"라며 끝까지 파고드는 **구조적 사고**에 가깝습니다.

### 실전: 증상별 컨텍스트 조작

마지막으로 이 챕터를 **명령어 수준의 대처법**으로 옮기겠습니다. 강사가 제시하는 세 가지 상황과 대응입니다.

| 증상                              | ❌ 흔한 대처                | ⭕ 올바른 대처                       |
|-----------------------------------|-----------------------------|--------------------------------------|
| **엉뚱한 파일을 보기 시작한다**   | 설명을 더 덧붙인다          | **관련 파일을 다시 좁힌다**          |
| **수정 범위가 넓어진다**          | 계속 밀어붙인다             | **조사 세션과 수정 세션을 분리한다** |
| **세션이 길어져 판단이 흐려진다** | 이전 대화를 억지로 유지한다 | **핵심만 요약해서 새로 시작한다**    |

이 셋이 Claude Code의 기본 컨텍스트 명령어와 그대로 대응합니다.

| 명령           | 하는 일                              | 언제 쓰나                      |
|----------------|--------------------------------------|--------------------------------|
| **`/init`**    | `CLAUDE.md` 시작 파일 생성           | 프로젝트 규칙을 처음 고정할 때 |
| **`/clear`**   | 세션 컨텍스트를 **비우고 새로 시작** | 판단이 흐려졌을 때             |
| **`/compact`** | 대화를 **요약해서 압축**             | 맥락은 유지하되 길이를 줄일 때 |

특히 `/clear`를 쓰는 걸 **작업 실패로 느낄 필요가 없습니다.** 앞 섹션 Context Harness 챕터에서 확인했듯, 오염된 컨텍스트를 이어 가면 Claude는 **이전의 잘못된 가설을 전제로 삼아 더
정교한 오답**을 만듭니다. 새 세션을 여는 것은 포기가 아니라 **오염된 State를 버리는 설계 행위**입니다.

> **주의.** `/compact`는 압축이므로 **손실을 동반**합니다. 압축돼도 반드시 남아야 하는 규칙이라면 대화가 아니라 `CLAUDE.md`에 있어야 합니다. 이 명령들의 실전 운용은 다음 챕터에서 더
> 자세히 다룹니다.

### 정리

1. **헛도는 이유는 모델이 아니라 컨텍스트다.** 큰 코드베이스에서는 **부족해서보다 넓고 흐려서** 실패한다.
2. **기억은 층이 다르다.** 다음 세션에도 필요하면 `CLAUDE.md`, 이번 작업만이면 세션 컨텍스트. 반드시 막을 것은 `permissions`·`hooks`.
3. **컨텍스트 컨트롤은 세 범위를 좁히는 일이다.** `문제 범위` · `파일 범위` · `세션 범위`. 특히 조사·수정·검토 세션을 섞지 않는다.
4. **에이전트는 좋은 인턴처럼 다룬다.** 목표·범위·판정 기준을 주고, 흐름을 지켜보고, 넘길 때 핵심 맥락을 유지한다.
5. **코드베이스가 약하면 에이전트가 그 약점을 증폭한다.** 테스트·README·설계 패턴·빌드·스타일 다섯 조건이 에이전트 친화성을 만든다.
6. **컨텍스트 컨트롤은 프롬프트 기술이 아니라 엔지니어링 문제다.** 큰 그림만으로는 안 되고, **디테일이 단단해야** 그 위에 에이전트를 얹을 수 있다.

## Plan/Thinking Mode, Subagents 개념 도입

앞 챕터에서 컨텍스트를 좁히는 법을 봤습니다. 이번에는 **어떻게 진행할 것인가** — 앞서 아키텍처 4층 중 **전략 레이어**에 해당하는 이야기입니다.

출발점은 우리가 습관적으로 하는 행동입니다.

> "Claude에게 먼저 문제를 주자마자 **바로 코드를 고치게 하는 겁니다. 겉으로는 빨라 보일 수 있어요. 그런데 복잡한 작업일수록 이 방식은 자주 실패를 할 수 있습니다.**"

빠른 것처럼 보이지만 실제로는 아닙니다. 이 챕터는 그 대안으로 **Plan-First · Thinking Mode · Sub-Agent** 세 가지를 소개합니다.

### Plan 모드: 읽기만 하면서 계획을 세운다

Anthropic 공식 문서는 Plan 모드를 이렇게 설명합니다.

> **Read-Only 기반으로 코드베이스를 분석하여 계획을 세우는 모드.**

**Read-Only**라는 조건이 핵심입니다. 계획을 세우는 동안에는 **아무것도 고치지 않습니다.** 그래서 다음 상황에 적합합니다.

| 적합한 상황         | 이유                         |
|---------------------|------------------------------|
| **복잡한 변경**     | 영향 범위를 먼저 파악해야 함 |
| **코드베이스 탐색** | 구조를 이해하는 단계         |
| **안전한 리뷰**     | 변경 없이 살펴보기만 함      |

그리고 공식 권장 흐름이 무엇인지 강사가 짚습니다.

> "즉 **처음부터 실행으로 들어가는 것보다 먼저 범위를 좁히고 계획을 세우는 것이 공식 권장 흐름**입니다."

### 한 단계를 더 넣는 게 더 빠르다

직관과 어긋나는 대목입니다. 단계를 하나 추가하는데 어떻게 더 빠를까요.

> "그래서 복잡한 작업일수록 **바로 수정하는 것보다 먼저 생각하고 분리하는 게 더 빠르다**는 겁니다. 겉보기에는 한 단계를 더 넣는 것 같지만 실제로는 **잘못된 수정, 그리고 넓어진 diff, 그리고
> 실패한 테스트, 되돌리기 비용을 줄여줄** 수 있습니다."

계산해 보면 이렇습니다.

```
 [바로 수정]
  수정(빠름) → 잘못된 방향 → diff 넓어짐 → 테스트 실패 → 되돌리기 → 다시 수정
  ────────────────────────────────────────────────────────────────── 총 시간 ↑

 [Plan-First]
  계획(느림) → 정확한 수정 → 좁은 diff → 테스트 통과
  ─────────────────────────────────────────────────── 총 시간 ↓
```

절약되는 비용이 구체적입니다.

| Plan-First가 줄이는 것 |
|------------------------|
| **잘못된 수정**        |
| **넓어진 diff**        |
| **실패한 테스트**      |
| **되돌리기 비용**      |

강의에서 든 예시가 현실적입니다. 레거시 서비스가 깨졌고, 실패 로그가 많고, 관련 파일도 많은 상황. 여기서 Claude에게 바로 "고쳐 줘"라고 하면 **수정 범위가 넓어지고 불필요한 파일까지 건드리게
됩니다.** 그래서 작은 작업 단위로 쪼개는 편이 안정적입니다.

### Plan-First는 "생각을 많이 하라"가 아니다

여기서 개념이 재정의됩니다.

> "이건 단순히 **생각을 많이 하라는 말이 아니라 수정 전에 작업 경계를 먼저 고정하는 단계**라고 볼 수 있어요."

**작업 경계를 고정한다.** 이게 Plan-First의 정체입니다. 앞 섹션 Permission Harness에서 "행동 반경을 설계한다"고 했던 것의 작업 단위 버전이죠.

#### 언제 Plan-First를 쓰나

| 상황                                               | 왜                            |
|----------------------------------------------------|-------------------------------|
| **영향 범위를 확신할 수 없을 때**                  | 어디까지 번질지 모름          |
| **여러 디렉터리·서비스가 얽혀 있을 때**            | 한 곳 수정이 다른 곳을 건드림 |
| **테스트가 약하거나 레거시라 연쇄 영향이 있을 때** | 수정 한 번이 사슬을 당김      |

#### 좋은 Plan-First가 담아야 할 다섯 가지

계획 모드를 켰다고 계획이 되는 건 아닙니다. **최소한 이 다섯 개**는 들어가야 합니다.

```
  1. 해결할 문제 정의
  2. 가능한 원인 후보
  3. 수정 범위
  4. 테스트 검증 순서
  5. 반영 전 확인할 지점
```

> 그렇지 않으면 **계획 모드를 사용했더라도 실제로는 즉흥적으로 움직이게 됩니다.**

앞 섹션 Context Harness의 **Context Pack**(목표·증거·파일 후보·수정 금지 범위·검증 방법)과 거의 같은 구성입니다. 이름만 다를 뿐, **작업 경계를 문서화한다**는 목적은 동일합니다.

### Sub-Agent: 작업을 섞지 않게 만드는 장치

Sub-Agent는 Claude Code에 **내장**되어 있습니다. 기본 제공되는 종류가 있고, 필요하면 커스텀도 만들 수 있습니다.

| 종류                | 성격      |
|---------------------|-----------|
| **explore**         | 탐색 전용 |
| **plan**            | 계획 수립 |
| **general-purpose** | 범용      |
| **커스텀**          | 직접 정의 |

여기서 중요한 설계 포인트가 나옵니다.

> "커스텀 서브에이전트 중요한 건 **각 서브에이전트의 설명이 곧 역할 경계**라는 점입니다. Claude는 그 설명을 보고 **언제 위임할지 판단**을 합니다. 즉 **서브에이전트는 작업을 섞지 않게 만드는
> 구조와 장치**라고 볼 수 있습니다."

즉 서브에이전트의 **설명 (description)은 그냥 메모가 아닙니다.** 그 문장이 **위임 여부를 결정하는 기준**이 됩니다. 설명이 모호하면 Claude는 언제 넘겨야 할지 판단하지 못합니다.

#### 사용 원칙: 역할이 분명할 때만 만든다

> **역할이 겹치면 만들지 않고, 역할이 분명할 때만 만든다.**

| 만들 가치가 큰 것 | 만들면 안 되는 것                       |
|-------------------|-----------------------------------------|
| **조사용**        | 역할이 서로 겹치는 것                   |
| **수정용**        | **작업 경계가 모호한 상태**에서 여러 개 |
| **검토용**        | 일단 만들고 보는 것                     |

경계가 흐린 상태로 서브에이전트를 여럿 만들면 **혼란만 커집니다.** 앞 섹션 Subagent & Worktree Harness의 "격리 없는 병렬은 오염을 부른다"와 정확히 같은 이야기입니다.

그래서 에이전틱 워크플로우의 원칙은 이렇게 정리됩니다.

> **많이 돌리는 것이 아니라, 작게 시작하고 측정하며 반복적으로 키우는 것.**

### Thinking Mode: 판단 품질에 계산을 더 쓰는 전략

Thinking Mode도 흔한 오해가 있습니다. "더 똑똑한 답을 받는 스위치"로 생각하는 것이죠.

> "Thinking Mode 같은 경우에는 이 경우도 같은 맥락에서 봐야 합니다. 이건 **더 똑똑한 답을 받아보자 수준이 아니라 즉시 실행보다 판단 품질이 중요한 작업에 계산 자원을 더 쓰는 전략**이에요."

즉 **자원 배분의 문제**입니다. 그래서 켜야 할 때와 끄는 게 나은 때가 나뉩니다.

| 쓰면 좋은 경우                   | 과한 경우           |
|----------------------------------|---------------------|
| **영향 범위가 넓은 수정**        | **로그 한 줄 파싱** |
| **설계 대안 비교**               | **파일 경로 찾기**  |
| **원인 후보가 여러 개인 디버깅** | 단순 반복 작업      |

> **Thinking Mode는 항상 켜고 있는 옵션이 아니라, 불확실성이 큰 문제에서만 쓰는 모드입니다.**

### 그래서 언제 무엇을 쓰나

세 가지를 한 표로 정리하면 선택 기준이 명확해집니다.

| 상황                                          | 선택              |
|-----------------------------------------------|-------------------|
| 문제가 **단순하고 수정 범위가 명확**하다      | **바로 실행**     |
| 문제가 **복잡하고 범위가 넓다**               | **Plan-First**    |
| **작업 유형이 서로 다르다**                   | **Sub-Agent**     |
| **결과 품질은 중요한데 범위가 아직 애매**하다 | **Thinking Mode** |

결정 흐름으로 보면 이렇습니다.

```
  범위가 명확한가?
    ├─ 예 ──→ 바로 실행
    └─ 아니오
         ├─ 작업 유형이 여러 개인가? ──→ Sub-Agent로 분리
         ├─ 범위가 넓은가?           ──→ Plan-First
         └─ 판단 자체가 어려운가?     ──→ Thinking Mode
```

주의할 것은 **"바로 실행"도 정당한 선택**이라는 점입니다. 오타 하나 고치는 데 계획 모드를 켜고 Thinking Mode를 돌릴 필요는 없습니다. 전략 레이어의 판단이란 **항상 신중하게 가라**가 아니라
**작업에 맞는 무게를 고르라**는 뜻입니다.

### 세 가지의 정체를 다시 정리하면

강사가 마지막에 세 개를 한 문장씩으로 못 박습니다.

> **Plan-First는 느린 게 아니라 실패 비용을 줄이는 방식, Thinking Mode는 불확실성이 큰 문제에 계산을 더 쓰는 전략, 그리고 Subagent는 자동화를 위한 장식이 아니라 작업 경계를
> 분리해서 결과 품질을 높이는 구조라고 보시면 됩니다.**

| 도구              | 흔한 오해          | 실제 정체                          |
|-------------------|--------------------|------------------------------------|
| **Plan-First**    | 느리다             | **실패 비용을 줄이는 방식**        |
| **Thinking Mode** | 똑똑해지는 스위치  | **불확실성에 계산을 더 쓰는 전략** |
| **Sub-Agent**     | 자동화를 위한 장식 | **작업 경계를 분리하는 구조**      |

셋 다 **"더 잘하게 만드는 마법"이 아니라 "무엇을 언제 쓸지 고르는 판단"** 이라는 공통점이 있습니다. 앞 섹션에서 계속 반복된 **"많이 붙이는 게 아니라 제자리에 두는 것"** 이 여기서도 그대로
적용됩니다.

### 정리

1. **바로 수정하는 건 빨라 보일 뿐이다.** 복잡한 작업일수록 즉시 실행은 자주 실패한다.
2. **Plan 모드는 Read-Only로 분석해 계획을 세우는 모드다.** 실행보다 범위 좁히기가 공식 권장 흐름이다.
3. **Plan-First는 생각을 많이 하는 게 아니라 작업 경계를 고정하는 단계다.** 문제 정의·원인 후보·수정 범위·검증 순서·확인 지점 다섯 개가 들어가야 계획이다.
4. **Sub-Agent의 설명이 곧 역할 경계다.** 역할이 겹치면 만들지 말고, 분명할 때만 만든다. 많이 돌리는 게 아니라 **작게 시작해 키운다.**
5. **Thinking Mode는 항상 켜는 옵션이 아니다.** 불확실성이 클 때만 쓰고, 단순 작업엔 과하다.
6. **선택 기준을 외워 둔다.** 범위 명확 → 바로 실행 / 범위 넓음 → Plan-First / 작업 유형 다름 → Sub-Agent / 판단 어려움 → Thinking Mode.

## 같은 일을 반복하지 않기 위한 Skills와 Tool use의 역할 차이

이 섹션의 마지막 챕터입니다. 주제는 **"같은 설명을 반복하지 않기"** 이고, 그 수단으로 자주 헷갈리는 두 개념 — **Skills**와 **Tool use** — 의 경계를 긋습니다.

결론부터 보면 한 문장입니다.

> "그래서 **Skills는 어떻게 일할지를 재사용하는 것이고, Tool use 같은 경우에는 무엇으로 실행을 할지 확장을 하는 겁니다.**"

`어떻게` vs `무엇으로`. 이 두 단어가 이 챕터의 전부입니다.

### Skills: 요청을 작업 절차로 번역하는 전문가 계층

Anthropic 공식 문서는 Skills를 **반복 가능한 워크플로우와 전문성을 Claude에게 추가하는 구조**로 설명합니다. 강사 **미국달팽이**님은 여기에 정의를 하나 더 붙입니다.

> Skills는 **사용자 요청을 특정한 작업 절차로 번역하는 전문가 계층**입니다.

"로그 좀 봐 줘"라는 한 줄이 들어오면, Skills가 그것을 **"로그를 정리하고 → 원인 후보를 좁히고 → 관련 파일을 탐색하고 → 검증 명령을 제한한다"** 는 절차로 바꿔 주는 것이죠.

#### 언제 Skills가 답인가

강사가 든 상황이 아주 구체적입니다.

> "**매번 같은 종류의 로그를 분석을 하고, 같은 형식의 PR 설명도 쓰고, 같은 체크리스트로 배포 전에 점검을 하고 있으면, 이건 Tool use 문제가 아니라, 도구가 없어서가 아니라 반복 작업이
> 지정되지 않은 문제**라고 보실 수 있어요."

**"도구가 없어서가 아니다"** 라는 부정형이 핵심입니다. 이미 도구는 다 있습니다. 없는 것은 **절차의 고정**입니다.

#### Skills는 템플릿이 아니다

여기서 흔한 오해를 하나 걷어냅니다. Skills를 "프롬프트 스니펫"이나 "템플릿"으로 생각하기 쉬운데, 실제로는 더 많은 것을 담습니다.

| Skills가 담는 것     | 역할                  |
|----------------------|-----------------------|
| **설명**             | 언제 이 스킬을 쓰는지 |
| **절차**             | 어떤 순서로 일할지    |
| **허용된 도구 제한** | **무엇까지만 쓸지**   |

세 번째가 특히 중요합니다. Skills는 **도구 사용 범위까지 제한**할 수 있습니다. 그래서 단순한 템플릿이 아니라 **절차·범위·컨텍스트를 함께 제한하는 구조**이고, 그 결과 **Claude가 추측하지
않게** 만듭니다.

앞 섹션 Subagent 챕터에서 "조사 에이전트에게는 읽기 전용 도구만 준다"고 했던 원칙이, 여기서는 **스킬 단위로** 적용되는 셈입니다.

### Tool use: 실행 능력을 연결한다

Tool use는 성격이 다릅니다. **무엇으로 실행할지를 확장**합니다.

| 필요한 상황                       | 예시                      |
|-----------------------------------|---------------------------|
| **외부 시스템 조회**              | 모니터링, 사내 API        |
| **파일 시스템 외 실행 주체 연결** | 데이터베이스, 외부 서비스 |
| **병렬 도구 호출**                | 여러 소스를 동시에 조회   |

그리고 Claude는 도구를 단순히 하나씩 부르는 게 아니라 **오케스트레이션**합니다.

| 패턴           | 방식                        |
|----------------|-----------------------------|
| **Single**     | 하나만 호출                 |
| **Parallel**   | 여러 개를 **동시에** 호출   |
| **Sequential** | 앞 결과를 받아 **순서대로** |

핵심은 이것입니다. Tool use는 **기능 설명이 아니라 실행 능력을 연결해 줍니다.** 아무리 절차를 잘 써 놔도, 실행할 수단이 없으면 Claude는 그 자리에서 멈춥니다.

### 헷갈리지 않는 비유: 사고 절차 vs 손발

강사가 제시하는 비유가 명쾌합니다.

> "**Skill은 Claude 사고 절차를 강화하면서 Tool use는 Claude의 손발을 늘리는 거죠. 이 비유를 기억하시면 잘 헷갈리지 않습니다.**"

```
 ┌─────────────────────┐        ┌─────────────────────┐
 │       SKILLS        │        │      TOOL USE       │
 │   사고 절차를 강화   │        │   손발을 늘린다      │
 │   "어떻게 일할지"    │        │   "무엇으로 실행할지" │
 └─────────────────────┘        └─────────────────────┘
      머릿속의 순서                  바깥으로 뻗는 손
```

| 구분              | Skills                       | Tool use                     |
|-------------------|------------------------------|------------------------------|
| **확장하는 것**   | **어떻게 일할지** (절차)     | **무엇으로 실행할지** (능력) |
| **비유**          | **사고 절차 강화**           | **손발 늘리기**              |
| **해결하는 문제** | 좋은 절차를 매번 다시 설명함 | 모델 혼자서는 실행할 수 없음 |

### 무조건 MCP부터 붙이지 마라

실무에서 자주 나오는 실수를 짚습니다. 반복 작업이 보이면 **반사적으로 MCP나 Tool use를 붙이는 것**입니다.

그런데 그건 **비쌉니다.** 서버가 하나 늘고, 도구 정의가 컨텍스트를 먹고, 신뢰 검토 대상이 생기고, 유지보수 부담이 붙습니다.

판단 기준은 단순합니다.

```
  작업 절차가 반복된다 + 외부 연결은 필요 없다   →  Skills
  외부 시스템 호출 / 데이터 조회 / 병렬 실행 필요 →  Tools · MCP
```

앞 섹션 Tool Harness 챕터에서 짚은 **"모든 반복 작업에 MCP를 붙이면 시스템이 불필요하게 무거워진다"** 와 같은 이야기입니다. 이 강의가 여러 챕터에 걸쳐 같은 경고를 반복한다는 건, 그만큼 자주
저지르는 실수라는 뜻이겠죠.

### 절차를 먼저 세우고, 도구는 그 다음에

순서에 대한 조언도 분명합니다.

> 작업을 **먼저 표준화된 절차로 바꾼 다음**, 도구 연결을 붙이는 경우가 많습니다.

그리고 그 이유가 뼈아픕니다.

> "**절차가 안정되지 않았는데 도구만 늘리면, 오히려 유지보수 비용만 커지죠.**"

```
 ⭕ 절차 표준화  →  안정화  →  필요한 곳에 도구 연결  →  확대
 ❌ 도구부터 잔뜩 →  절차는 여전히 제각각  →  유지보수 지옥
```

그래서 원칙은 앞 챕터에서 본 것과 같습니다. **처음부터 툴을 많이 붙이는 게 아니라, 작게 시작해서 실제 사용을 보면서 확대하는 것.**

### Skills로 저장할 만한 것들

강의에서 나열하는 후보들입니다. 전부 **"매번 같은 방식으로 하고 있는 일"** 이라는 공통점이 있습니다.

| 후보                              | 성격                       |
|-----------------------------------|----------------------------|
| **버그 리포트 정리**              | 형식이 정해진 작업         |
| **로그 요약**                     | 반복되는 분석 절차         |
| **PR 설명 초안**                  | 팀의 작성 규칙             |
| **배포 전 체크리스트**            | 빠뜨리면 안 되는 점검 항목 |
| **레거시 코드 읽기 절차**         | 탐색 순서                  |
| **특정 프레임워크용 디버깅 루틴** | 도메인 특화 절차           |

### 판단 기준: 3번 규칙과 멈춤 신호

이 챕터에서 가장 실전적인 두 가지 기준입니다.

| 신호                                                    | 결론              |
|---------------------------------------------------------|-------------------|
| **같은 설명을 3번 이상 반복**하고 있다                  | **Skills 후보**   |
| Claude가 **절차는 아는데 외부 실행 능력이 없어 멈춘다** | **Tool use 후보** |

두 번째 신호가 특히 유용합니다. Claude가 "이런 걸 확인해야 하는데 접근할 수가 없습니다"라고 말하는 순간, 그건 **절차의 문제가 아니라 손발의 문제**라는 뜻입니다.

#### 둘 다 필요할 때

물론 둘이 배타적인 관계는 아닙니다.

> 둘 다 필요하면 보통 **Skills가 절차를 잡고, Tool use가 실행을 담당하는 구조**로 갑니다.

```
  Skills      "이런 순서로 확인한다"        ← 절차
     ↓
  Tool use    "그 확인을 실제로 수행한다"   ← 실행
```

### 착각의 두 방향

이 챕터의 마무리이자 가장 압축된 경고입니다.

> "**작업 절차 문제를 실행 문제로 착각하면 과설계가 될 수 있고요. 실행 문제를 절차 문제로 착각하면 Claude는 멈출 수밖에 없습니다.**"

| 착각                             | 결과                                             |
|----------------------------------|--------------------------------------------------|
| 절차 문제 → **실행 문제로 착각** | **과설계** (안 써도 될 MCP·도구가 잔뜩)          |
| 실행 문제 → **절차 문제로 착각** | **Claude가 멈춤** (아무리 잘 설명해도 손이 없음) |

두 방향 모두 손해지만 증상이 다릅니다. 전자는 **무거워지고**, 후자는 **막힙니다.** 그래서 문제를 만났을 때 **"이건 절차 문제인가, 실행 문제인가"** 를 먼저 구분하는 것이 첫 단추입니다.

### 정리

1. **Skills는 "어떻게 일할지", Tool use는 "무엇으로 실행할지"다.** 이 두 단어로 대부분 구분된다.
2. **반복되는 작업은 대개 도구 부족 문제가 아니다.** 도구는 이미 있고, 없는 건 **절차의 고정**이다.
3. **Skills는 템플릿이 아니다.** 설명·절차· **허용 도구 제한**까지 담아 Claude가 추측하지 않게 만든다.
4. **비유로 기억하라.** Skills는 **사고 절차 강화**, Tool use는 **손발 늘리기**.
5. **절차를 먼저 세우고 도구를 붙인다.** 절차가 불안정한 채로 도구만 늘리면 유지보수 비용만 커진다.
6. **판단 기준은 두 개다.** 같은 설명을 **3번 이상** 반복하면 Skills 후보, 절차는 아는데 **실행 능력이 없어 멈추면** Tool use 후보.
7. **착각의 방향을 조심하라.** 절차 문제를 실행 문제로 보면 **과설계**, 실행 문제를 절차 문제로 보면 **정지**다.
