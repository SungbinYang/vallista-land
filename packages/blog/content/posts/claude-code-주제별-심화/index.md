## MCP Tool Search - 도구 10개 연결해도 컨텍스트 여유롭게 쓰기

MCP 서버를 하나둘 붙이다 보면 어느 순간 이런 생각이 듭니다. **"도구를 더 연결하고 싶은데, 컨텍스트가 아깝다."** Notion MCP, Playwright MCP, Supabase MCP, 작업 관리
MCP… 편하긴 한데 대화를 시작하기도 전에 컨텍스트가 상당 부분 차 있는 것이죠.

이번 챕터는 그 문제를 정면으로 해결하는 **Tool Search** 기능을 다룹니다. 그리고 단순한 편의 기능 소개에서 끝나지 않습니다.

> "컨텍스트 엔지니어링 시대에 요즘 개발자들이 Claude Code에 열광하는 진짜 이유까지 말씀드릴 테니, 이번 영상 꼭 끝까지 집중해 주시면 감사드리겠습니다."

### 문제: 연결만 해도 토큰을 먹는다

먼저 문제 상황을 정확히 짚어야 합니다. MCP 도구는 **연결되어 있기만 해도** 컨텍스트 윈도우를 차지합니다. 실제로 그 도구를 쓰지 않아도 말이죠.

`/context` 명령어로 확인해 보면 눈으로 보입니다. 아직 아무 작업도 하지 않았는데 **MCP 도구 정의들이 이미 자리를 차지**하고 있습니다.

왜 이게 문제일까요? **컨텍스트 윈도우**는 AI가 한 번에 이해하고 처리할 수 있는 **최대 토큰 양**입니다. 무한하지 않습니다.

> "결국 몇 번의 대화로 컨텍스트 윈도우가 가득 차버리면, AI는 환각을 일으키면서 바보가 된다라고 말씀드렸죠."

쓰지도 않을 도구 정의로 컨텍스트가 채워지면, 정작 중요한 코드와 맥락이 들어갈 자리가 줄어듭니다. **토큰 비용의 문제이자, 결과 품질의 문제**입니다.

### 해결: 필요할 때만 로드하는 Tool Search

Claude Code에 추가된 **Tool Search** 기능은 이 문제를 정확히 겨냥합니다. 원리는 간단합니다 — **MCP 도구를 필요할 때만 로드**하는 것입니다.

| 구분          | Tool Search 비활성         | Tool Search 활성                    |
|---------------|----------------------------|-------------------------------------|
| **로딩 시점** | 연결만 해도 **미리 전부**  | **필요한 순간에** 검색해서 그때그때 |
| **컨텍스트**  | 도구 수에 비례해 계속 증가 | 거의 차지하지 않음                  |

앞선 챕터에서 배운 **스킬의 점진적 로딩**과 같은 발상입니다. 평소엔 들고 있지 않다가, **필요해지면 그때 꺼내 오는** 방식이죠. 이번엔 그 원리를 MCP 도구에 적용한 것입니다.

### 언제 켜지나: 10% 규칙

Tool Search는 기본값이 **`auto`** 입니다. 즉, **항상 켜져 있는 것도 항상 꺼져 있는 것도 아닙니다.**

> **판단 기준.** MCP 도구가 **컨텍스트 윈도우의 10%를 넘게 차지하면** Tool Search가 자동 활성화됩니다. 10% 미만이면 비활성 상태로, 기존처럼 모든 MCP 도구가 미리 로드됩니다.

꽤 합리적인 설계입니다. 도구가 몇 개 없어서 부담이 크지 않을 땐 **미리 로드해 두는 편이 빠르고**, 도구가 많아져 부담이 커지면 **그때부터 절약 모드**로 전환하는 것이죠.

### 시연: 30%가 18%로

강의에서는 실제 수치로 효과를 보여 줍니다.

| 상황                                     | 결과                                                    |
|------------------------------------------|---------------------------------------------------------|
| MCP 도구가 **약 30%** 차지하던 상태      | Tool Search 활성화 → 사용량 **18%**, MCP 툴 항목 사라짐 |
| MCP를 일부 제거해 **10% 미만**이 된 상태 | Tool Search 비활성화 → MCP 도구가 다시 미리 로드됨      |

`/context`로 확인하면 MCP 도구가 차지하던 영역이 **깔끔하게 비어 있는** 것을 볼 수 있습니다. 도구는 그대로 연결되어 있는데, 컨텍스트만 돌려받은 것이죠.

> "어떤가요? 정말 환상적이지 않나요?"

### 설정 방법

동작 방식을 직접 조절하고 싶다면 **`ENABLE_TOOL_SEARCH`** 환경 변수를 씁니다. 설정 파일의 **`env`** 속성 안에 넣으면 됩니다.

```json
{
  "env": {
    "ENABLE_TOOL_SEARCH": "auto"
  }
}
```

값에 따라 동작이 달라집니다.

| 값           | 동작                                                     |
|--------------|----------------------------------------------------------|
| **`auto`**   | **기본값.** MCP 도구가 컨텍스트의 **10% 초과 시** 활성화 |
| **`auto:5`** | 임계값을 **5%** 로 낮춰 **더 일찍** 활성화               |
| **`true`**   | **항상** 켜기                                            |
| **`false`**  | **끄기** — 모든 도구를 미리 로드 (기존 방식)             |

`auto:5`처럼 **숫자로 임계값을 조정**할 수 있다는 점이 유용합니다. 컨텍스트를 빡빡하게 쓰는 작업이 많다면 임계값을 낮춰 더 공격적으로 절약할 수 있습니다.

> "설정 참 쉽죠?"

### 주의사항: 모델 지원 범위

한 가지 확인할 점이 있습니다. **Tool Search는 모든 모델에서 동작하지 않습니다.**

| 모델       | 지원 여부         |
|------------|-------------------|
| **Sonnet** | 3.5 이상 **지원** |
| **Opus**   | 3 이상 **지원**   |
| **Haiku**  | **미지원**        |

토큰을 아끼려고 Haiku를 쓰고 있다면, 정작 이 기능은 못 쓴다는 뜻입니다. **가벼운 모델 + Tool Search** 조합은 성립하지 않으니 참고해 두면 좋겠습니다.

### 추가 팁: MCP 응답 크기 제한하기

강사는 함께 알아 두면 좋은 환경 변수 하나를 더 소개합니다. **`MAX_MCP_OUTPUT_TOKENS`** 입니다.

이름 그대로 **MCP 도구가 반환하는 응답의 최대 토큰 수를 제한**합니다. Tool Search가 *도구 정의*를 아껴 준다면, 이쪽은 *도구 응답*을 아껴 주는 셈입니다.

> **언제 유용한가.** DB 조회처럼 **대량의 데이터를 가져오는** 작업에서 특히 그렇습니다. 수천 행이 통째로 컨텍스트에 쏟아지는 사고를 막아 줍니다.

Supabase MCP로 테이블을 조회하다 예상보다 많은 데이터가 딸려 온 경험이 있다면, 이 변수를 기억해 두면 좋습니다.

### 이 기능이 말해 주는 것: 컨텍스트 엔지니어링

챕터 서두에서 예고했던 "진짜 이유"가 여기서 나옵니다.

> "이 기능은 Anthropic이 컨텍스트 관리에 진심이라는 증거입니다."

AI를 다루는 기술의 초점이 옮겨 가고 있습니다.

| 시대                    | 핵심 질문                                   |
|-------------------------|---------------------------------------------|
| **프롬프트 엔지니어링** | AI에게 **어떻게 물어볼 것인가**             |
| **컨텍스트 엔지니어링** | AI에게 **어떤 정보와 환경을 제공할 것인가** |

프롬프트를 잘 쓰는 것만으로는 부족합니다. **무엇을 보여 주고 무엇을 감출지**, **언제 로드하고 언제 비울지**를 설계하는 것이 결과를 좌우합니다.

그 관점에서 보면 Claude Code가 제공해 온 기능들이 하나의 방향을 가리키고 있습니다.

- `CLAUDE.md` — 항상 알아야 할 것을 정의
- `/compact`, `/clear` — 쌓인 맥락을 정리
- **서브 에이전트** — 컨텍스트를 격리해 위임
- **스킬의 점진적 로딩** — 필요할 때만 매뉴얼을 펼침
- **Tool Search** — 필요할 때만 도구를 가져옴

전부 **"컨텍스트를 어떻게 관리할 것인가"** 에 대한 답입니다. 도구 하나가 편리해진 것이 아니라, **일관된 설계 철학**이 기능으로 나타나고 있는 것이죠.

### 정리하며

이번 챕터의 내용을 압축하면 이렇습니다.

1. MCP 도구는 **연결만 해도** 컨텍스트를 차지하고, 이는 **AI 성능 저하**로 이어집니다.
2. **Tool Search**는 MCP 도구를 **필요할 때만 로드**해 이 문제를 해결합니다.
3. 기본값은 **`auto`** — MCP 도구가 **10%를 넘으면** 자동 활성화됩니다.
4. **`ENABLE_TOOL_SEARCH`** 환경 변수로 `auto` / `auto:5` / `true` / `false` 조절이 가능합니다.
5. **Haiku는 미지원**이며, **`MAX_MCP_OUTPUT_TOKENS`** 로 응답 크기도 제한할 수 있습니다.

실무적으로 가장 반가운 변화는 **"MCP를 더 붙여도 된다"** 는 점입니다. 그동안 컨텍스트가 아까워 도구 연결을 망설였다면, 이제는 필요한 MCP를 붙여 두고 **쓰는 순간에만 값을 치르면** 됩니다. 그리고
그 편의의 배경에는 **컨텍스트 엔지니어링**이라는 분명한 방향이 있습니다.

## 토큰이 녹는 이유와 실전 절약 팁 총정리

Claude Code를 쓰다 보면 가장 많이 듣게 되는 하소연이 있습니다.

> "토큰이 너무 녹아요."

분명 열심히 쓴 것도 아닌데 사용량 제한에 걸리고, 한창 작업 중인데 "이번 주 한도를 다 썼다"는 메시지를 만납니다. 이번 챕터에서는 **토큰이 왜 그렇게 빨리 사라지는지**를 구조적으로 이해하고, **바로 적용할
수 있는 절약 팁**을 총정리합니다.

핵심은 요령을 외우는 게 아니라 **원리를 아는 것**입니다.

> "모르고 안 쓰는 거랑 알고 안 쓰는 건 완전 다르니까요."

### 원인 ①: 경차에 슈퍼카 엔진

첫 번째 원인은 의외로 단순합니다. **모델 선택**입니다.

**Opus는 Sonnet보다 토큰을 4~5배 더 소모**합니다. 그런데 많은 분들이 이 사실을 모른 채, 기본 설정 그대로 Opus를 쓰고 있습니다.

> "이건 마치 경차에 슈퍼카 엔진을 달아 놓은 것과 비슷해요."

Pro 플랜을 쓰면서 Opus를 기본 모델로 두면, 몇 번의 작업만으로 한도가 소진되는 게 당연합니다. **성능이 부족한 게 아니라, 애초에 엔진을 잘못 고른** 것이죠.

### 원인 ②: AI는 매번 처음부터 다시 읽는다

두 번째 원인이 더 근본적입니다. 강사는 **카카오톡 단톡방** 비유로 설명합니다.

| 주체     | 새 메시지가 왔을 때                         |
|----------|---------------------------------------------|
| **사람** | **새로 온 메시지만** 읽습니다               |
| **AI**   | **이전 대화 전체를 처음부터 다시** 읽습니다 |

그리고 그렇게 다시 읽는 **모든 내용이 토큰으로 과금**됩니다.

이 구조를 이해하면 여러 현상이 한 번에 설명됩니다.

- 대화가 길어질수록 **같은 질문에도 비용이 올라갑니다.**
- 파일을 많이 읽을수록 **이후 모든 대화가 비싸집니다.**
- 로그인 기능을 끝내고 컨텍스트를 비우지 않은 채 다음 작업을 시작하면, **끝난 작업의 대화까지 계속 다시 읽습니다.**

즉, 토큰은 **내가 방금 입력한 프롬프트**가 아니라 **그 대화방에 쌓인 전부**에 대해 나갑니다.

### 그래서 컨텍스트 엔지니어링

여기서 개념 하나가 자연스럽게 도출됩니다.

> **대화방에 담긴 내용이 곧 비용을 결정합니다.** 이 내용을 관리하는 기술이 **컨텍스트 엔지니어링**입니다.

**컨텍스트 윈도우**는 AI가 한 번에 처리할 수 있는 토큰의 총량, 즉 **작업 공간의 크기**입니다. 코드베이스를 탐색하다 보면 생각보다 금방 채워집니다.

컨텍스트 엔지니어링은 이 작업 공간을 **필요한 것만 넣고 불필요한 것은 빼는** 기술입니다. 앞 챕터에서 다룬 Tool Search도, 스킬의 점진적 로딩도 결국 같은 이야기였습니다.

### 방치하면 생기는 일: Context Rot → Hallucination

컨텍스트를 관리하지 않으면 어떻게 될까요? 악순환이 시작됩니다.

| 단계                | 무슨 일이 일어나는가                                      |
|---------------------|-----------------------------------------------------------|
| **① Context Rot**   | 지난 작업의 **잔해가 남아** 토큰을 잡아먹고 AI를 혼란시킴 |
| **② Hallucination** | 혼란이 심해져 AI가 **틀린 답**을 내놓음                   |
| **③ 재소모**        | 틀린 결과를 **고치느라 토큰을 또** 씀                     |

> "바보가 되는 거죠."

무서운 건 ③입니다. 컨텍스트가 지저분해서 AI가 실수하고, 그 실수를 바로잡느라 토큰을 더 쓰고, 그러면서 컨텍스트는 더 지저분해집니다. **토큰이 녹는 속도가 점점 빨라지는** 구조입니다.

### 플랜별 전략: 내 플랜을 알고 쓰기

구독 플랜에 따라 쓸 수 있는 양이 다릅니다. Pro / Max 100 / Max 200 플랜은 **Sonnet과 Opus의 사용 가능 시간이 각각 다르게** 책정되어 있습니다.

| 플랜            | 권장 전략                                                            |
|-----------------|----------------------------------------------------------------------|
| **Pro**         | Opus 사용이 **매우 제한적** → **Sonnet 위주**, Opus는 꼭 필요할 때만 |
| **Max 100/200** | Opus를 **좀 더 활용** 가능하되, 사용량 **모니터링 필요**             |

Pro 플랜에서 Opus를 기본으로 두고 쓰는 것이 앞서 말한 "경차에 슈퍼카 엔진"입니다. 플랜을 바꾸기 전에 **모델 설정부터 점검**하는 것이 순서입니다.

### 모델 고르기: 시니어에게 복사 붙여넣기를 시키지 말자

모델별 성격을 개발자에 비유하면 이해가 쉽습니다.

| 모델       | 비유              | 특징                      | 적합한 작업            |
|------------|-------------------|---------------------------|------------------------|
| **Opus**   | **시니어 개발자** | 가장 똑똑, **토큰 4~5배** | 복잡한 문제 해결·설계  |
| **Sonnet** | **중급 개발자**   | 균형 잡힌 성능            | **대부분의 코딩 작업** |
| **Haiku**  | **주니어 개발자** | 가장 빠르고 저렴          | 간단한 질문, 파일 검색 |

> "시니어 개발자에게 복사 붙여넣기를 시키는 건 정말 낭비겠죠?"

정확한 지적입니다. 파일 하나 찾는 데 Opus를 쓰는 건 낭비이고, **대부분의 코딩 작업은 Sonnet으로 충분**합니다.

### 모델 설정하는 방법

현재 모델은 **`/model`** 명령어로 확인하고 변경합니다.

Pro 플랜인데 Opus로 되어 있다면 **Sonnet으로 바꾸는 것**이 첫 번째 절약입니다. 매번 바꾸기 번거롭다면 **설정 파일에 Sonnet으로 고정**해 두면 Claude Code를 켤 때마다
Sonnet으로 시작합니다.

그리고 알아 두면 좋은 옵션이 하나 있습니다 — **`opusplan`** 입니다.

> **`opusplan` 이란?** **계획 모드에서는 Opus**, **실행 모드에서는 Sonnet**으로 자동 전환해 주는 설정입니다.

머리를 써야 하는 계획 단계에만 비싼 모델을 쓰고, 계획대로 코드를 쓰는 실행 단계는 저렴한 모델에 맡기는 것이죠. 앞선 시리즈에서 배운 **"계획하고 구현하고"** 리듬과 정확히 맞아떨어지는 설정입니다.

### 실전 절약 팁 총정리

이제 바로 적용할 수 있는 팁들입니다.

| 팁                       | 내용                                                                |
|--------------------------|---------------------------------------------------------------------|
| **`/clear`**             | 작업이 끝나면 **대화를 초기화** — 끝난 작업을 다시 읽지 않도록      |
| **`/compact`**           | 컨텍스트가 찼을 때 **대화를 요약**해 토큰 절약                      |
| **Thinking 모드 조절**   | 확장된 사고는 **출력 토큰으로 과금** — `/config`로 끄거나 예산 하향 |
| **구체적인 프롬프트**    | 두루뭉술하면 AI가 **여기저기 탐색** → 범위를 좁혀 주기              |
| **Tool Search 활용**     | MCP를 쓴다면 **툴 서치를 켜기** (앞 챕터 참고)                      |
| **`CLAUDE.md` 다이어트** | **500줄 이하** 권장, 가끔 쓰는 상세 지식은 **스킬로 분리**          |

몇 가지는 부연할 가치가 있습니다.

**`/clear`와 `/compact`의 차이.** `/clear`는 **비우는** 것이고 `/compact`는 **압축하는** 것입니다. 작업이 완전히 끝났으면 `/clear`, 맥락은 이어 가야 하는데 대화가
길어졌으면 `/compact`입니다.

**Thinking 모드.** AI가 답하기 전에 깊이 생각하는 기능인데, 그 **사고 과정도 출력 토큰으로 과금**됩니다. 간단한 작업에도 계속 켜 둘 이유는 없습니다. `/config`로 조절하거나 환경 변수로
사고 예산 자체를 낮출 수 있습니다.

**구체적인 프롬프트.** "로그인이 안 돼요"라고 하면 AI는 관련 파일을 광범위하게 뒤집니다. "`app/login/page.tsx`에서 제출 버튼을 눌렀을 때 이 에러가 납니다"라고 하면 **탐색 범위가 확
줄어듭니다.** 앞선 프로젝트 챕터에서 배운 **재현 시나리오 제공**은 정확도를 높이는 동시에 **토큰도 아끼는** 방법이었던 셈입니다.

**`CLAUDE.md` 다이어트.** 메모리 파일은 **매 대화마다 통째로 로딩**됩니다. 여기에 온갖 지식을 다 넣으면 그게 곧 고정 비용이 됩니다. 공식 문서 권장은 **500줄 이하**이고, 가끔만 필요한
상세 지식은 **스킬로 빼서 필요할 때만 로딩**되게 하는 것이 정석입니다.

### 결국은 플랜에 맞는 관리 전략

마지막으로 강사가 다시 강조하는 것은 **컨텍스트 관리 전략도 플랜에 따라 달라져야 한다**는 점입니다.

- **Pro 플랜** — **엄격한 관리**가 필수. Sonnet 고정, Opus 최소화, `/clear` 습관화
- **Max 플랜** — 여유가 있지만 **모니터링은 계속**

그리고 현실적인 조언 하나. 관리를 잘 하고 있는데도 부족하고 **결과물이 만족스럽다면**, 그때는 **플랜 상향을 고려**해 볼 시점입니다. 무작정 아끼는 것이 목적이 아니라, **쓸 값어치가 있는 곳에 쓰는
것**이 목적이니까요.

### 정리하며

이번 챕터의 내용을 압축하면 이렇습니다.

1. 토큰이 녹는 원인은 **모델 선택**(Opus는 4~5배)과 **대화 누적**(AI는 매번 전체를 다시 읽음)입니다.
2. 관리하지 않으면 **Context Rot → 환각 → 재작업**의 악순환에 빠집니다.
3. **Sonnet을 기본**으로 쓰고, 계획 단계만 Opus가 필요하면 **`opusplan`** 을 씁니다.
4. **`/clear`·`/compact`·Thinking 조절·구체적 프롬프트·Tool Search·`CLAUDE.md` 500줄** 로 절약합니다.
5. 관리 전략은 **플랜에 맞춰** 조정합니다.

가장 기억할 것은 **토큰은 프롬프트 길이가 아니라 대화방에 쌓인 전부에 대해 나간다**는 사실입니다. 이 하나만 이해하면 `/clear`를 왜 습관화해야 하는지, `CLAUDE.md`를 왜 다이어트해야 하는지가
전부 설명됩니다. 절약은 요령이 아니라 **구조를 아는 데서** 나옵니다.
