## Claude Agent Skills 이란?: 강력한 클로드 스킬!!

Claude Code를 쓰다 보면 비슷비슷해 보이는 기능들이 계속 등장합니다. 커스텀 커맨드, 서브 에이전트, MCP, 그리고 여기에 **스킬 (Skills)** 까지. 이름만 들어서는 무엇이 어떻게 다른지 감이 잘
오지 않습니다.

> "클로드 스킬은 많은 분들이 유튜브 콘텐츠를 보고도 많이 헷갈려 하시더라고요."

> "이 스킬이란 놈이 MCP랑 무엇이 다른지, 클로드 코드의 커스텀 커맨드와 서브 에이전트와는 무엇이 다른지, 그래서 제가 이번 영상에서 아주 쉽고 명확하게 정리해 드릴게요."

이번 챕터는 그 혼란을 정리하는 시간입니다. **스킬이 무엇인지**, **어떻게 생겼는지**, 그리고 **기존 기능들과 무엇이 다른지**까지 차근차근 짚어 봅니다.

### 스킬 = 클로드를 위한 업무 매뉴얼

개념부터 잡고 갑시다. 강사의 비유는 아주 명쾌합니다.

> "클로드의 스킬을 쉽게 설명드리면, 클로드를 위한 업무 매뉴얼이에요."

신입 직원이 입사하면 업무 매뉴얼을 받습니다. "우리 회사에서 보고서는 이런 양식으로 쓰고, 이 순서대로 처리한다"는 문서죠. 매뉴얼을 읽은 신입은 처음 하는 일도 회사 방식대로 해냅니다.

스킬이 딱 그 역할입니다. Claude에게 **"이 작업은 이렇게 처리해라"** 라는 매뉴얼을 쥐어 주는 것입니다. 매뉴얼을 받은 Claude는 그 분야의 전문가처럼 일하게 됩니다.

| 스킬 예시           | Claude가 잘하게 되는 일         |
|---------------------|---------------------------------|
| **PPTX 스킬**       | 프레젠테이션 문서 제작          |
| **Excel 스킬**      | 스프레드시트 작업               |
| **React 개발 스킬** | 정해진 컨벤션대로 컴포넌트 작성 |

### 어디서든 쓸 수 있다: 범용성

스킬의 첫 번째 강점은 **범용성**입니다. 특정 도구 전용이 아닙니다.

- **Claude 데스크탑 앱**
- **Claude Code** (터미널 기반)
- **Claude API**

세 환경 모두에서 **동일한 스킬이 그대로 작동**합니다. 한 번 만들어 두면 어디서든 쓸 수 있다는 뜻입니다. (강의에서는 이해를 돕기 위해 Claude 데스크탑 앱으로 시연합니다.)

### 내장 스킬 체험: "PPT로 만들어 줘"

Claude는 기본적으로 **사전 구축된 내장 스킬**을 갖고 있습니다. 여기서 중요한 건 **사용자가 스킬을 지정하지 않는다**는 점입니다.

시연은 간단합니다. "Claude 스킬 도입 제안서를 PPT로 만들어 줘"라고 요청하면 — Claude가 **스스로 판단해 PPTX 스킬을 선택**하고, 그 매뉴얼대로 프레젠테이션을 만들어 냅니다.

> **핵심.** 스킬은 `/명령어`처럼 직접 호출하는 것이 아니라, **자연스러운 대화 중에 Claude가 알아서 꺼내 쓰는** 방식입니다.

### 추가 스킬 켜기

데스크탑 앱 **설정 → 기능** 메뉴에서 **"코드 실행 및 파일 생성"** 옵션을 활성화하면 쓸 수 있는 스킬이 더 늘어납니다.

- **알고리즘 아트** — 코드로 생성하는 시각 작업
- **캔버스 디자인** — 디자인 결과물 제작
- **MCP 빌더** — MCP 서버 제작 보조

### 스킬은 어떻게 만드는가

직접 스킬을 만드는 방법은 두 가지입니다.

1. **`skill-creator` 스킬 활용** — 스킬을 만들어 주는 스킬. Claude에게 맡기는 방식
2. **스킬 업로드** — 직접 만든 스킬 폴더를 올리는 방식

두 번째 방법을 쓰려면 **스킬이 어떤 구조로 생겼는지** 알아야 합니다. 그래서 다음은 구조 이야기입니다.

### 스킬의 구조: 세 가지 구성 요소

스킬은 **하나의 폴더**이고, 그 안에 세 가지가 들어갑니다.

| 구성 요소    | 파일             | 역할                                            |
|--------------|------------------|-------------------------------------------------|
| **지침서**   | `SKILL.md`       | Claude가 **가장 먼저 읽는** 핵심 사용법         |
| **참고자료** | 별도 문서 (선택) | `SKILL.md`가 길어질 때 **상세 설명을 분리**     |
| **스크립트** | 실행 코드        | 복잡한 작업을 **자동화**, 토큰 절약·결과 일관성 |

지침서만 있어도 스킬은 성립합니다. 참고자료와 스크립트는 **필요할 때 덧붙이는** 요소입니다.

### `SKILL.md` 뜯어보기

스킬의 심장인 `SKILL.md`는 두 부분으로 나뉩니다.

#### 프론트메터 — 스킬의 신분증

파일 맨 위에 오는 메타데이터입니다. Claude가 **"이 스킬을 지금 써야 하나?"** 를 판단하는 근거가 됩니다.

| 항목          | 역할                           | 제한        |
|---------------|--------------------------------|-------------|
| `name`        | 스킬의 이름                    | 최대 64자   |
| `description` | 어떤 상황에 쓰는 스킬인지 설명 | 최대 1024자 |

`description`이 특히 중요합니다. 이 한 줄이 부실하면 Claude가 **필요한 순간에 스킬을 꺼내지 못합니다.**

#### 본문 — 실제 업무 매뉴얼

프론트메터 아래는 진짜 매뉴얼입니다. **단계별 가이드와 예시**를 담습니다. 권장 분량은 **500줄 이하**입니다.

그럼 내용이 길어지면 어떻게 할까요? 두 가지 방법이 있습니다.

- **마크다운 링크로 참고 문서 분리** — 상세 설명은 별도 파일로 빼고 링크만 걸어 둡니다
- **스크립트는 배시 명령으로 실행** — 코드를 본문에 넣지 않고 실행만 시킵니다

두 방법 모두 목적은 하나, **토큰 절약**입니다. 그리고 이 설계가 바로 다음에 나올 '점진적 공개'와 이어집니다.

### 실제 예시: 웹 아티팩트 빌더

이론만으로는 감이 안 오니, Anthropic **공식 스킬 저장소**의 실제 스킬을 살펴봅니다. 예시는 **웹 아티팩트 빌더 (Web Artifacts Builder)** 스킬로, React와 TailwindCSS
등을 활용해 복잡한 웹 애플리케이션을 만들도록 돕는 스킬입니다.

구조를 열어 보면 앞서 배운 그대로입니다.

- **프론트메터** — 스킬 이름과 설명
- **본문** — 어떤 순서로 작업할지 단계별 가이드
- **스크립트 폴더** — 자동화 스크립트

강사는 이 스킬로 **강의 홍보 랜딩 페이지**를 직접 제작해 보이며, 스킬이 있을 때와 없을 때의 결과 차이를 체감시켜 줍니다.

### 핵심 특징 ①: 점진적 공개 (Progressive Loading)

여기부터가 이 챕터의 백미입니다. 스킬을 100개 설치하면 느려지고 토큰을 잡아먹을까요? **그렇지 않습니다.** 스킬은 **필요한 순간에 필요한 만큼만** 읽어 들이기 때문입니다.

Claude는 파일 시스템에 접근할 수 있으므로, 스킬 폴더 안에 방대한 자료를 넣어 두어도 **처음부터 전부 읽지 않습니다.**

| 레벨       | 언제                  | 읽는 것                            | 토큰               |
|------------|-----------------------|------------------------------------|--------------------|
| **레벨 1** | 항상 (스킬 목록 파악) | 프론트메터 (`name`, `description`) | 스킬당 **약 100**  |
| **레벨 2** | 그 스킬을 쓰기로 결정 | `SKILL.md` 본문                    | **5,000 미만**     |
| **레벨 3** | 실제 작업 수행        | 참고 문서 열람, 스크립트 실행      | **거의 소비 없음** |

평소에는 스킬당 **100토큰짜리 목차**만 들고 있다가, 쓰기로 결정한 순간에 매뉴얼을 펼치고, 실제 작업은 스크립트에 맡기는 구조입니다. 그래서 **방대한 자료와 복잡한 스크립트를 품고도 토큰 소비는 최소**로
유지됩니다.

> "이게 Claude Skill의 핵심입니다."

### 핵심 특징 ②: 컴포저블 (조합 가능)

두 번째 특징은 **스킬끼리 조합해 쓸 수 있다**는 것입니다. 사용자가 "이 스킬과 저 스킬을 같이 써"라고 지시할 필요가 없습니다. Claude가 **필요한 스킬을 스스로 파악해 조합**하며 복잡한 작업을
완성합니다.

매뉴얼이 여러 권 있으면 필요한 것들을 골라 펼쳐 보는 것과 같습니다.

### 그래서 MCP·커스텀 커맨드·서브 에이전트와 뭐가 다른가

이 챕터를 듣는 진짜 이유일 겁니다. 네 기능을 **네 가지 기준**으로 비교합니다.

| 기준              | 커스텀 커맨드              | 서브 에이전트              | MCP                | **Claude 스킬**        |
|-------------------|----------------------------|----------------------------|--------------------|------------------------|
| **작동 방식**     | 직접 명령 실행             | 대화 중 자동 사용          | 대화 중 자동 사용  | **대화 중 자동 사용**  |
| **이식성**        | Claude Code 전용           | Claude Code 전용           | 지원 플랫폼 한정   | **모든 Claude 제품**   |
| **메모리 효율**   | 전통적 (전체 로딩)         | 전통적 (전체 로딩)         | 전통적 (전체 로딩) | **점진적 로딩**        |
| **스크립트 실행** | 코드 생성 후 컨텍스트 포함 | 코드 생성 후 컨텍스트 포함 | —                  | **스크립트 직접 실행** |

특히 **마지막 줄**을 눈여겨볼 필요가 있습니다.

> **왜 '스크립트 직접 실행'이 중요한가?**
> 커스텀 커맨드나 서브 에이전트는 매번 **코드를 새로 생성**하고, 그 코드가 전부 컨텍스트에 들어갑니다. 토큰이 많이 들 뿐 아니라, **매번 조금씩 다른 코드**가 나와 결과가 달라질 수 있습니다.
> 반면 스킬은 **이미 검증된 스크립트를 그대로 실행**합니다. 코드가 컨텍스트에 포함되지 않아 토큰이 절약되고, **결과의 일관성**이 보장됩니다.

> "이 차이가 정말 막강하죠."

### 언제 무엇을 쓸까

정리하면 각 기능은 **경쟁 관계가 아니라 용도가 다른 도구**입니다.

| 기능              | 한 줄 정의                     | 이럴 때 씁니다                                |
|-------------------|--------------------------------|-----------------------------------------------|
| **커스텀 커맨드** | 자주 쓰는 프롬프트 **단축키**  | Claude Code에서 같은 요청을 반복할 때         |
| **서브 에이전트** | 특정 역할의 **전문가 AI**      | 코드 리뷰어·테스트 담당 등 전문 작업 위임     |
| **MCP**           | 외부 시스템 연결 **다리**      | GitHub·Slack·DB 등 외부 서비스 연동           |
| **Claude 스킬**   | 특정 작업 수행 **업무 매뉴얼** | 대규모 자동화·반복 작업, 여러 환경에서 재사용 |

**"프롬프트를 반복해서 쓴다"** → 커스텀 커맨드, **"외부 시스템에 붙어야 한다"** → MCP, **"작업 방식 자체를 정형화하고 싶다"** → 스킬. 이렇게 **문제의 성격**으로 갈라 보면 헷갈리지
않습니다.

### 정리하며

이번 챕터는 개념 정리에 집중했지만, 남는 것은 분명합니다.

1. 스킬은 **클로드를 위한 업무 매뉴얼**이고,
2. **지침서 (`SKILL.md`) + 참고자료 + 스크립트** 세 요소로 구성되며,
3. **점진적 공개 (3단계 로딩)** 덕분에 아무리 많이 설치해도 가볍고,
4. **컴포저블** 특성으로 여러 스킬이 자동 조합되며,
5. **모든 Claude 제품에서 작동**하고 **스크립트를 직접 실행**해 결과가 일관됩니다.

기존 기능들과 비교했을 때 스킬의 정체성은 **"작업 방식을 문서로 고정하고, 어디서든 재사용한다"** 입니다. 반복 작업이 많고 결과가 흔들리면 곤란한 영역일수록 스킬의 가치는 커집니다. 다음 챕터에서는 이 스킬을
**플러그인과 마켓플레이스로 공유**하는 방법을 살펴봅니다.

## 플러그인으로 기능 공유: 마켓플레이스 실전 데모까지

앞 챕터에서 스킬을 배웠고, 그 전에는 커스텀 커맨드·서브 에이전트·훅·MCP를 배웠습니다. 이제 손에 든 무기가 꽤 많아졌습니다. 그런데 여기서 아주 현실적인 문제가 하나 생깁니다.

> "그런데 이때 한 가지 문제가 있습니다. 이렇게 어렵게 만든 기능들을 우리가 다른 프로젝트에서 사용하려면 어떻게 해야 할까요?"

### 문제: 복사 붙여넣기의 굴레

지금까지의 방식을 떠올려 봅시다.

> "우리가 이제 Claude Code로 개발을 하다 보면 반복되는 프롬프트, 커밋이나 코드 리뷰와 같이 반복되는 프롬프트는 커스텀 커맨드로 이렇게 만들어서 사용을 했었죠."

문제는 이 기능들이 **프로젝트 안에 갇혀 있다**는 점입니다. 새 프로젝트를 시작할 때마다 `.claude` 폴더를 뒤져 커맨드 파일을 복사하고, 서브 에이전트 정의를 옮기고, 훅 설정을 다시 붙여넣어야 합니다.
팀원에게 공유하려면 "이 파일들을 이 경로에 넣으세요"라고 일일이 안내해야 하고요.

기능 하나를 옮기는 것도 번거로운데, 여러 개를 세트로 옮기려면 더 심각합니다. 그리고 원본을 개선했을 때 **복사해 둔 사본들을 전부 갱신**하는 건 사실상 불가능에 가깝습니다.

### 해결책: 플러그인

이 문제를 풀기 위해 등장한 것이 **플러그인 (Plugin)** 입니다. 정의는 간단합니다.

> "쉽게 말하면 관련 기능들을 패키징해서 바로 설치할 수 있도록 도와주는 템플릿이라고 보시면 돼요."

Claude Code의 확장 기능들을 **하나로 묶어 패키징**한 것이 플러그인입니다.

| 플러그인에 담을 수 있는 것 |
|----------------------------|
| **커스텀 커맨드**          |
| **서브 에이전트**          |
| **훅 (Hooks)**             |
| **스킬 (Skills)**          |
| **MCP 서버 설정**          |

이렇게 묶어 두면 얻는 이점은 명확합니다.

- **재사용** — 다른 프로젝트에 **설치 한 번**으로 그대로 가져옵니다
- **공유** — 팀원에게 파일 복사 대신 **주소 하나**만 알려 주면 됩니다
- **수급** — 전 세계 개발자들이 만든 플러그인을 **가져다 쓸 수** 있습니다
- **업데이트** — 개선 사항을 **명령어 하나로** 반영합니다

### 마켓플레이스는 '주소록'이다

그런데 여기서 한 단계가 더 필요합니다. Claude Code가 **그 플러그인을 어디서 가져와야 하는지** 알아야 하니까요. 그 역할을 하는 것이 **플러그인 마켓플레이스**입니다.

> **비유.** 마켓플레이스는 **주소록**입니다. "이런 플러그인들이 있고, 각각 여기에 있다"는 목록과 위치 정보를 담고 있습니다.

구조는 이렇게 겹겹이 쌓여 있습니다.

```
마켓플레이스 (주소록)
 ├─ 플러그인 A ─ 커스텀 커맨드 / 서브 에이전트 / 스킬 ...
 ├─ 플러그인 B ─ 훅 / MCP 설정 ...
 └─ 플러그인 C ─ ...
```

하나의 마켓플레이스에는 **관심사별로 묶인 여러 플러그인**이 들어가고, 각 플러그인 안에 실제 확장 기능들이 담깁니다.

그리고 마켓플레이스는 거창한 서비스가 아닙니다. **로컬 디렉터리**여도 되고, **GitHub 저장소**여도 됩니다. 즉, 내 저장소 하나를 그대로 마켓플레이스로 만들 수 있다는 뜻입니다.

### 마켓플레이스 설치하기

플러그인을 쓰려면 먼저 **그 플러그인이 있는 마켓플레이스를 등록**해야 합니다. 방식은 아주 간단합니다.

```bash
# GitHub 저장소를 마켓플레이스로 등록
/plugin marketplace add <사용자명>/<저장소명>

# 로컬 디렉터리를 마켓플레이스로 등록
/plugin marketplace add ./경로
```

어떤 마켓플레이스가 있는지 궁금하다면 **Claude Code 마켓플레이스 사이트**에서 커뮤니티가 공유한 목록을 둘러볼 수 있습니다.

> "그러면 실제로 이러한 마켓플레이스가 어떻게 생겼고, 마켓플레이스 안에 플러그인이 어떻게 들어가 있는지, 실제로 우리 프로젝트 안에 똑똑한 사람들이 이미 만들어서 공유한 플러그인을 설치해 보면서 더 익숙해져
> 보도록 하겠습니다."

### 실습: 공식 마켓플레이스에서 플러그인 설치

강의에서는 **Anthropic 공식 마켓플레이스**를 등록하고 플러그인을 설치해 봅니다. 흐름은 다음과 같습니다.

1. 마켓플레이스 등록 명령을 프로젝트에 붙여넣고 **실행**합니다.
2. `/plugin` 명령어를 입력해 관리 화면으로 들어갑니다.
3. **`Manage marketplaces`** 항목에서 방금 등록한 마켓플레이스를 확인합니다.
4. 마켓플레이스를 선택하면 그 안의 **플러그인 목록**이 나옵니다.
5. 원하는 플러그인에서 **엔터**를 눌러 상세 정보를 보고 설치합니다.

여러 개를 한 번에 설치하고 싶다면 단축키를 씁니다.

| 조작           | 동작                    |
|----------------|-------------------------|
| **엔터**       | 상세 화면 진입 → 설치   |
| **스페이스바** | 여러 플러그인 다중 선택 |
| **`i`**        | 선택한 항목 일괄 설치   |

> "만약에 이러한 플러그인을 설치하고 싶다면 해당 상세 화면에서 인스톨해서 엔터를 하셔도 되고요."

> **주의.** 플러그인을 설치한 뒤에는 **Claude Code를 재실행**해야 새 기능을 쓸 수 있습니다. 설치하자마자 안 된다고 당황하지 마세요.

### 마켓플레이스는 어떻게 생겼나

GitHub 저장소를 등록할 때 쓴 `<사용자명>/<저장소명>` — 이 주소로 Claude Code는 무엇을 찾아갈까요?

저장소 안의 **`.claude-plugin` 디렉터리에 있는 `marketplace.json` 파일**입니다. 이 파일에 **어떤 플러그인들이 있고 각각 어디에 위치하는지**가 정의되어 있습니다.

| 요소                   | 역할                                    |
|------------------------|-----------------------------------------|
| **GitHub 저장소**      | 마켓플레이스의 실체                     |
| **`marketplace.json`** | 플러그인 정의와 위치 정보 (주소록 본문) |

공식 마켓플레이스인 `anthropic/claude-code` 저장소를 직접 열어 보면 이 구조를 눈으로 확인할 수 있습니다. **남이 만든 것을 뜯어보는 것**이 내 마켓플레이스를 만드는 가장 빠른 길이기도
합니다.

### 설치가 안 될 때

플러그인 설치가 정상적으로 되지 않는 경우도 있습니다. 강사는 이럴 때의 초기화 방법을 공유합니다.

> **문제 해결 순서**
> 1. 등록된 **마켓플레이스를 모두 제거**합니다.
> 2. 사용자 홈 디렉터리의 **`.claude` 디렉터리를 삭제**합니다.
> 3. **Claude Code를 재설치**합니다.

> **꼭 확인하세요.** `.claude` 디렉터리에는 그동안 만든 커스텀 커맨드·서브 에이전트·설정이 들어 있습니다. 삭제 전에 **반드시 백업**해 두세요.

### 실전 데모: 프론트엔드 디자인 플러그인

개념을 익혔으니 실제로 써 볼 차례입니다. 강의에서는 설치한 플러그인으로 **맥주 큐레이션 서비스**를 만들어 봅니다.

| 플러그인              | 역할                                    |
|-----------------------|-----------------------------------------|
| **`feature-dev`**     | 개발 워크플로우를 체계적으로 지원       |
| **프론트엔드 디자인** | 독창적이고 개성 있는 UI를 자동으로 생성 |

먼저 `feature-dev` 플러그인으로 **PRD 문서**를 만들고, 이어서 프론트엔드 디자인 플러그인으로 **랜딩 페이지**를 개발합니다. 기술 스택은 익숙한 **Next.js + shadcn/ui**입니다.

주목할 점은 이 디자인 플러그인이 **단순히 코드만 뽑아내지 않는다**는 것입니다. **디자인 씽킹을 기반으로** 다음 요소까지 함께 고려합니다.

- **타이포그래피** — 서비스 성격에 맞는 글꼴과 위계
- **컬러 · 테마** — 브랜드 톤에 맞는 색 구성
- **레이아웃** — 화면 구성과 시선 흐름
- **애니메이션** — 디테일한 인터랙션

결과물은 맥주 테마에 맞는 색상과 로고, 타이포그래피, 레이아웃을 갖추고 — **탄산 기포가 올라오는 애니메이션**까지 구현된 랜딩 페이지입니다. 앞선 챕터에서 tweakcn으로 테마를 손볼 때 느꼈던 "디자인이
막막하다"는 갈증을, 잘 만들어진 플러그인 하나가 상당 부분 해소해 주는 셈입니다.

### 정리하며

이번 챕터에서는 만든 기능을 **어떻게 재사용하고 공유할지**를 배웠습니다.

1. 기능을 프로젝트마다 **복사 붙여넣기 하던 문제**에서 출발해,
2. 확장 기능들을 하나로 묶는 **플러그인** 개념을 이해하고,
3. 플러그인의 주소록인 **마켓플레이스** (로컬 디렉터리 또는 GitHub 저장소)를 등록했으며,
4. `.claude-plugin/marketplace.json` 이라는 **실제 구조**를 확인하고,
5. **프론트엔드 디자인 플러그인**으로 완성도 높은 랜딩 페이지까지 만들어 봤습니다.

핵심 메시지는 **"내가 만든 무기를 무기고에 넣어 두라"** 입니다. 어렵게 만든 커스텀 커맨드와 서브 에이전트를 프로젝트에 묻어 두면 그 프로젝트에서 끝나지만, 플러그인으로 패키징해 두면 **다음 프로젝트,
그리고 팀 전체의 자산**이 됩니다. 그리고 반대로 — 전 세계 개발자들이 이미 만들어 둔 무기고를 **가져다 쓸 수도** 있다는 것. 이것이 플러그인과 마켓플레이스가 열어 주는 가능성입니다.

## 클로드 코드 스킬 생성하기: 클로드 코드를 선호하는 이유!

앞서 스킬이 무엇인지, 플러그인으로 어떻게 공유하는지를 배웠습니다. 이번 챕터는 그 마무리입니다. **Claude Code에서 직접 스킬을 만들어 보고**, 언제 스킬을 꺼내 써야 하는지, 그리고 최근 추가된
기능들까지 살펴봅니다. 마지막에는 **왜 Claude Code를 선호하는가**라는 질문에 대한 답도 함께 나옵니다.

### 복습: 스킬이 강력한 두 가지 이유

먼저 앞 챕터의 핵심을 한 번만 다시 짚고 갑니다.

> "클로드 스킬은 점진적 로딩으로 시작 시에는 최소한의 메타 데이터만 로딩을 하고, 그다음에는 필요한 문서만 선택적으로 로딩을 하기 때문에 토큰을 획기적으로 절약할 수 있었어요."

| 특징            | 효과                                                    |
|-----------------|---------------------------------------------------------|
| **점진적 로딩** | 시작 시 메타데이터만, 이후 **필요한 문서만 선택적**으로 |
| **직접 실행**   | 스크립트를 컨텍스트에 올리지 않고 **바로 실행**         |

이 두 가지가 실제로 어떤 문제를 풀어 주는지 — 이번 챕터는 거기서 출발합니다.

### 활용 사례 ① 방대한 참고자료 관리

여러 프로젝트를 다루다 보면 Claude가 알아야 할 **배경 지식이 어마어마하게 많아집니다.** 이걸 전부 `CLAUDE.md`에 적어 두면 어떻게 될까요?

**매 대화마다 그 내용이 통째로 로딩**됩니다. 지금 필요하지도 않은 정보까지 전부 컨텍스트를 차지하는 것이죠.

스킬은 이 문제를 다르게 풉니다. 참고자료를 **링크로 분리**해 두고, **필요한 순간에 필요한 만큼만** 컨텍스트에 올립니다.

> "즉, 컨텍스트를 효과적으로 사용함으로써 토큰을 절약하고 **AI가 바보가 될 확률을 줄이는** 거죠."

이 표현이 핵심을 정확히 찌릅니다. 컨텍스트 윈도우는 무한하지 않습니다. 쓸데없는 정보로 가득 차면 정작 중요한 것에 집중하지 못하고, **AI의 판단력이 떨어집니다.** 토큰 절약은 돈 문제이기도 하지만, 그보다
**결과 품질의 문제**입니다.

### 활용 사례 ② MCP의 토큰 낭비 막기

두 번째 사례는 꽤 실용적입니다. **MCP를 붙이면 그 도구 정의들이 컨텍스트에 미리 로딩**됩니다. 쓰든 안 쓰든 말이죠.

> **예시.** Playwright MCP를 연결하면 **23개의 도구**가 미리 로딩됩니다. 그런데 실제로 쓰는 건 그중 몇 개뿐입니다. 나머지는 **자리만 차지하는 토큰**입니다.

여기에 스킬의 점진적 로딩을 적용하면 어떻게 될까요? MCP를 붙여 두는 대신, **필요한 순간에만 Playwright를 사용하도록** 스킬로 감싸는 것입니다. 평소에는 100토큰짜리 메타데이터만 들고 있다가,
브라우저 테스트가 필요한 순간에 펼치는 방식이죠.

MCP가 만능이 아니라는 것, 그리고 **때로는 스킬이 MCP의 대안이 될 수 있다**는 것 — 실무에서 꽤 유용한 관점입니다.

### 활용 사례 ③ 어디서든 쓰는 범용성

스킬은 Claude Code 전용이 아닙니다. **Claude 앱을 포함한 Claude 생태계 전체**에서 동일하게 작동합니다.

강의에서는 **나만의 PPT 제작 스킬**로 프레젠테이션을 만들고, `.pptx`로 저장한 뒤 구글 드라이브에서 열어 수정하는 과정을 보여 줍니다. 한 번 만든 스킬이 도구를 넘나들며 쓰이는 모습입니다.

### 스킬 만들기 ① 직접 만들기

이제 본론입니다. Claude Code에서 스킬을 직접 만드는 방법은 생각보다 간단합니다.

```
.claude/
 └─ skills/
     └─ git-commit/          # 스킬 폴더 (이름은 자유)
         └─ SKILL.md          # 필수 파일
```

`.claude/skills/` 아래에 폴더를 하나 만들고, 그 안에 **`SKILL.md`** 파일을 넣으면 끝입니다. 파일 구성은 앞 챕터에서 배운 그대로입니다.

| 위치           | 내용                        |
|----------------|-----------------------------|
| **메타데이터** | 스킬의 **이름**과 **설명**  |
| **본문**       | 스킬이 수행할 **실제 지침** |

강의에서는 예시로 **Git 커밋 메시지를 자동 생성하는 스킬**을 만들어 봅니다. 커밋 메시지 컨벤션처럼 **팀마다 규칙이 다르고 매번 반복되는 작업**이 스킬로 만들기에 딱 좋은 소재입니다.

### 스킬 만들기 ② 스킬 크리에이터 활용

직접 쓰는 게 막막하다면 **스킬을 만들어 주는 스킬**을 쓰면 됩니다. 바로 **`skill-creator`** 입니다. 새 스킬을 생성하는 것은 물론, **기존 스킬을 업데이트**하는 데도 도움을 줍니다.

설치는 앞 챕터에서 배운 **플러그인 기능**을 그대로 활용합니다. Anthropic의 스킬 저장소 (`anthropic/skills`)를 마켓플레이스로 등록하고 `skill-creator`를 설치하면 됩니다. 앞
챕터에서 배운 것이 바로 여기서 쓰이는 셈입니다.

생성된 스킬은 **사용자 레벨 디렉터리**에 저장되어, 프로젝트를 옮겨 다녀도 계속 쓸 수 있습니다.

### 최신 업데이트 ① 슬래시 커맨드 자동 등록

여기서부터는 Claude Code에 새로 추가된 기능들입니다. 첫 번째가 특히 반갑습니다.

**스킬을 만들면 슬래시 커맨드로 자동 등록**됩니다.

| 시점                | 스킬 사용 방법                                   |
|---------------------|--------------------------------------------------|
| **이전**            | Claude가 알아서 인식하거나, 명시적으로 프롬프팅  |
| **2.1.0 버전 이후** | `/git-commit` 처럼 **슬래시 커맨드로 직접 호출** |

즉, 스킬이 **커스텀 커맨드의 편의성까지 흡수**한 것입니다. 자동 인식에 맡길 수도 있고, 확실하게 쓰고 싶으면 슬래시로 직접 부를 수도 있습니다.

### 최신 업데이트 ② 자동 Hot Reload

스킬 파일을 수정한 뒤 **Claude Code를 껐다 켤 필요가 없어졌습니다.** 파일을 고치면 **즉시 반영**됩니다.

사소해 보이지만 체감 차이가 큽니다. 스킬을 만들 때는 지침을 조금씩 다듬으며 여러 번 시행착오를 거치는데, 그때마다 재시작해야 한다면 흐름이 계속 끊기니까요.

### 최신 업데이트 ③ `context: fork` — 독립 컨텍스트로 실행

스킬 메타데이터에 **`context` 필드**가 추가되었습니다. 값을 **`fork`** 로 지정하면 스킬이 **별도의 서브 에이전트로 실행**됩니다.

> **무슨 의미인가요?** 스킬이 **독립된 컨텍스트**에서 작업하므로, 그 과정에서 오간 내용이 **메인 대화의 컨텍스트를 오염시키지 않습니다.** 결과만 받아 오는 것이죠.

앞선 프로젝트들에서 서브 에이전트를 쓰며 얻었던 **"컨텍스트 격리"** 효과를, 이제 스킬 정의에 한 줄 적는 것만으로 얻을 수 있습니다.

### 최신 업데이트 ④ 에이전트 유형 지정

`context: fork` 를 켰다면, **어떤 성격의 에이전트로 실행할지**까지 지정할 수 있습니다.

| 에이전트 유형  | 특화 영역                   |
|----------------|-----------------------------|
| **Plan**       | 복잡한 작업의 **계획 수립** |
| **Explorer**   | **탐색과 정보 수집**        |
| *(지정 안 함)* | 기본 에이전트로 실행        |

앞선 프로젝트 챕터들에서 배운 흐름이 떠오릅니다. 계획이 필요한 작업엔 Plan 모드, 자료 수집이 필요한 작업엔 탐색 — 그 판단을 **스킬 안에 미리 박아 둘 수 있게** 된 것입니다.

### 최신 업데이트 ⑤ 훅 사용 가능

스킬에서 **`hook` 필드**를 통해 훅을 쓸 수 있습니다. 스킬 **사용 전·후 또는 종료 시** 특정 이벤트를 실행할 수 있습니다. 스킬이 단순한 지침 문서를 넘어, **실행 흐름까지 제어하는 단위**로
발전한 셈입니다.

### 실전 예시: Next.js 스킬

마지막으로 강사가 직접 만든 **Next.js 스킬**을 소개합니다. 문제 의식은 앞의 활용 사례 ①과 같습니다.

Next.js 개발을 제대로 하려면 알아야 할 스펙이 방대합니다. 그렇다고 이 내용을 전부 `CLAUDE.md`에 넣으면 **토큰 낭비가 심각**합니다.

그래서 스킬을 이렇게 설계했습니다.

| 위치           | 담은 내용                                     |
|----------------|-----------------------------------------------|
| **`SKILL.md`** | 핵심 내용과 **자주 실수하는 부분**만 간략하게 |
| **참고자료**   | 공식 문서별 중요 파트를 **별도 문서로 분리**  |

이렇게 해두면 "레이아웃과 페이지 구조를 만들어 줘"라고 요청했을 때, **그 주제에 해당하는 참고자료만** 로딩되어 가이드를 제공합니다. 나머지 방대한 문서는 그대로 잠들어 있고요.

이것이 **점진적 로딩을 실무에 적용하는 정석적인 형태**입니다. (해당 스킬은 강의 설명란에서 받을 수 있습니다.)

### 그래서, 왜 Claude Code인가

챕터 제목의 후반부에 대한 답이 여기 있습니다. 강사는 Claude Code를 선호하는 이유를 두 가지로 정리합니다.

**첫째, 터미널 기반이라는 것.**

> "클로드 코드는 터미널 기반에서 실행되는 도구이기 때문에, 꼭 커서 AI가 아니더라도 터미널이 있는 어디에서든 실행할 수 있어요."

특정 IDE에 종속되지 않습니다. 터미널만 있으면 어디서든 같은 도구를 씁니다.

**둘째, 그리고 더 중요한 것 — 컨텍스트 관리.**

> "이렇게 엔트로픽이 만든 클로드 코드는 다른 AI 도구와 확실히 다른 점이 있어요. 바로 **컨텍스트 관리에 진심**이라는 거죠."

`CLAUDE.md`, 서브 에이전트, `/compact`, 그리고 이번에 배운 스킬의 점진적 로딩까지 — 이 모든 기능이 결국 **"무엇을 알려주고 무엇을 알려주지 않을지"** 를 다루는 장치들입니다.

> "결국 AI 시대의 개발은 어떤 모델, 어떤 인터페이스를 선택하느냐도 중요하지만, 우리가 정말 집중해야 할 건 **컨텍스트를 얼마나 잘 관리하느냐** 이거예요."

모델 성능은 계속 좋아지고 도구도 계속 바뀝니다. 하지만 **컨텍스트를 다루는 능력**은 어떤 모델을 쓰든 결과를 좌우하는, 개발자 쪽에 남는 실력입니다.

### 정리하며

이번 챕터에서는 스킬을 **직접 만들고 활용하는 법**을 익혔습니다.

1. **방대한 참고자료·MCP 토큰 낭비**를 스킬의 점진적 로딩으로 해결하고,
2. `.claude/skills/` 아래 **`SKILL.md`** 로 스킬을 직접 만들거나 **`skill-creator`** 로 생성하며,
3. **슬래시 커맨드 자동 등록·Hot Reload·`context: fork`·에이전트 유형·훅** 등 새 기능을 확인하고,
4. **Next.js 스킬** 사례로 실무 적용 형태를 살펴봤으며,
5. Claude Code의 정체성이 **컨텍스트 관리**에 있다는 결론에 도달했습니다.

이 시리즈를 관통하는 메시지로 마무리하면 이렇습니다. **AI에게 더 많이 알려 주는 것이 좋은 것이 아닙니다.** 필요한 것을, 필요한 순간에, 필요한 만큼만 알려 주는 것 — 스킬은 그 원칙을 도구로 구현한
기능이고, Claude Code는 그 원칙 위에 세워진 도구입니다.

## 커스텀 커맨드와 스킬 통합 총정리

앞선 챕터들에서 커스텀 커맨드와 스킬을 각각 배웠습니다. 둘은 성격이 다른 별개의 기능이었죠. 그런데 그 전제가 바뀌었습니다.

> "그런데 최근 Claude Code가 업데이트되면서 이러한 Custom Command와 Skill이 하나로 통합되었습니다."

이번 챕터는 **무엇이 어떻게 통합됐고, 그래서 무엇이 달라졌는지**를 정리하는 시간입니다. 결론부터 말하면 — **잃은 것은 없고 얻은 것만 있습니다.**

### 무엇이 통합되었나: 내부 도구의 통합

먼저 '통합'의 정확한 의미부터 짚어야 합니다. Claude Code는 작업할 때 **내부 도구 (tool)** 를 사용합니다. 파일을 읽을 땐 `Read`, 편집할 땐 `Edit`를 쓰는 식이죠.

커스텀 커맨드와 스킬도 각각 다른 도구를 쓰고 있었습니다.

| 구분              | 이전 (~v2.1.2) | 이후 (v2.1.3~) |
|-------------------|----------------|----------------|
| **커스텀 커맨드** | `SlashCommand` | **`Skill`**    |
| **스킬**          | `Skill`        | `Skill`        |

**v2.1.3 버전부터 커스텀 커맨드도 내부적으로 `Skill` 도구를 사용**하게 된 것입니다.

> **중요.** 이것은 **내부 도구의 통합**입니다. 사용자가 보는 인터페이스나 **파일 구조에는 변화가 없습니다.** 기존에 만들어 둔 커스텀 커맨드와 스킬은 그대로 잘 동작합니다.

> "그리고 여기서 통합을 명확히 설명드리면,"

즉, 마이그레이션 작업 같은 건 필요 없습니다. 쓰던 그대로 쓰면 됩니다.

### 그래서 무엇이 달라졌나: 커스텀 커맨드의 확장

> "그러면 이러한 통합으로 어떠한 변화, 즉 업그레이드가 있었는지 살펴보도록 할게요."

변화는 **한쪽 방향으로만** 일어났습니다.

| 기능              | 변화                                    |
|-------------------|-----------------------------------------|
| **스킬**          | **이전과 완전히 동일** — 달라진 것 없음 |
| **커스텀 커맨드** | **스킬의 기능을 물려받아 확장**         |

커스텀 커맨드가 `Skill` 도구를 쓰게 되면서, **스킬에서만 가능했던 것들이 커스텀 커맨드에서도 가능**해졌습니다. 대표적으로 **자동 호출**과 **프론트메터 (frontmatter)** 지원입니다.

### 실습으로 확인하기

강의에서는 두 기능을 실제로 만들어 보며 확인합니다.

**커스텀 커맨드 만들기** — `commands` 디렉터리에 `hello.md` 파일 하나면 끝입니다.

```
.claude/
 └─ commands/
     └─ hello.md          # 파일 하나 = 커맨드 하나
```

**스킬 만들기** — 앞 챕터에서 배운 그대로 디렉터리 구조를 갖춥니다.

```
.claude/
 └─ skills/
     └─ greeting/
         └─ SKILL.md
```

둘 다 이전과 똑같이 잘 동작합니다. 통합됐다고 해서 기존 사용법이 깨지지 않는다는 것을 눈으로 확인하는 과정입니다.

### 핵심 변화: 커스텀 커맨드도 프론트메터를 쓴다

이번 통합의 실질적인 수확이 여기 있습니다. 커스텀 커맨드에서 **스킬이 지원하는 모든 프론트메터 옵션**을 그대로 쓸 수 있게 되었습니다.

가장 체감되는 것은 **`description`을 통한 자동 호출**입니다.

> **시연.** `hello.md`의 프론트메터에 `description`을 적어 두면, 사용자가 **"안녕"** 이라고 입력했을 때 Claude가 알아서 그 커스텀 커맨드를 꺼내 씁니다. `/hello`
> 라고 직접 치지 않아도 되는 것이죠.

앞 챕터에서 다뤘던 **스킬은 자동으로 호출되고, 커스텀 커맨드는 직접 호출한다**는 구분이 이제 흐려졌습니다. 커스텀 커맨드도 **대화 흐름 속에서 자동으로 불려 나올 수 있습니다.**

물론 앞서 살펴본 `context: fork`, 에이전트 유형 지정, `hook` 같은 옵션들도 마찬가지로 사용할 수 있습니다. **파일 하나짜리 커맨드가 꽤 강력해진** 셈입니다.

### 그럼 둘의 차이는 무엇으로 남는가

기능이 통합됐다면, 이제 커스텀 커맨드와 스킬을 구분할 이유가 있을까요? 있습니다. 남은 차이는 **구조**입니다.

| 구분           | 커스텀 커맨드               | 스킬                                  |
|----------------|-----------------------------|---------------------------------------|
| **파일 구조**  | 단일 마크다운 파일 (`*.md`) | **디렉터리** (`SKILL.md` + 보조 파일) |
| **보조 파일**  | 프롬프트만 정의 가능        | **참고자료·스크립트를 함께 묶음**     |
| **프론트메터** | 지원 (통합 이후)            | 지원                                  |

핵심은 **보조 파일을 품을 수 있느냐**입니다. 커스텀 커맨드는 여전히 **프롬프트 하나**만 담을 수 있고, 스킬은 **참고자료와 스크립트까지 세트로** 묶을 수 있습니다.

그래서 선택 기준도 명확해집니다.

> "그러니까 간단한 프롬프트 하나면 커스텀 커맨드로 충분하고, 추가 파일이 필요한 복잡한 워크플로우라면 스킬로 만들 수 있을 거예요."

| 이런 경우                                   | 이렇게 만드세요   |
|---------------------------------------------|-------------------|
| 프롬프트 한 덩어리로 끝나는 반복 작업       | **커스텀 커맨드** |
| 참고 문서·스크립트가 함께 필요한 워크플로우 | **스킬**          |

### 이름이 겹치면 누가 이기나

실무에서 마주칠 수 있는 상황도 짚고 갑니다. **커스텀 커맨드와 스킬의 이름이 같다면** 어떻게 될까요?

> **우선순위: 스킬이 이깁니다.**
> `hello`라는 이름의 커스텀 커맨드와 스킬이 모두 있을 때 `hello`를 호출하면 — **스킬이 실행**됩니다.

이름 충돌은 의외로 잘 생깁니다. 커스텀 커맨드를 스킬로 옮기는 과정에서 원본을 지우지 않으면 바로 이 상황이 되죠. **의도한 쪽이 실행되지 않는다면 이름 충돌을 먼저 의심**해 보면 됩니다.

### 실무에서 이 사실이 필요한 순간

강사는 이 지식이 실제로 언제 쓰이는지도 짚어 줍니다.

> "그리고 실무에서 회사 프로젝트나 오픈소스를 열었을 때, 이러한 커스텀 커맨드와 스킬이 있으면 해당 스펙이 통합되었다는 걸 알고 있기 때문에, 필요하다면 커스텀 커맨드를 스킬로도 전환할 수 있을 거예요."

남의 프로젝트를 열었을 때 `.claude/commands/`와 `.claude/skills/`가 뒤섞여 있는 상황을 만나게 됩니다. 그때 **둘이 같은 도구 위에서 돈다는 사실을 알고 있으면** 당황하지 않고,
필요에 따라 **커스텀 커맨드를 스킬로 승격**시킬 수도 있습니다.

승격이 필요한 신호는 간단합니다 — **프롬프트 하나로는 부족해지고, 참고 문서나 스크립트를 곁들이고 싶어질 때**입니다.

### 정리하며

이번 챕터는 짧지만 알아 두면 헷갈리지 않을 내용이었습니다.

1. **v2.1.3 버전부터** 커스텀 커맨드도 내부적으로 **`Skill` 도구**를 사용합니다.
2. 이는 **내부 통합**이라 파일 구조·사용법은 **그대로**입니다.
3. 스킬은 변화 없고, **커스텀 커맨드가 프론트메터와 자동 호출을 얻었습니다.**
4. 남은 차이는 **단일 파일 vs 디렉터리 (+보조 파일)** 구조입니다.
5. 이름이 겹치면 **스킬이 우선**합니다.

기능이 통합됐다고 해서 둘 중 하나를 버릴 필요는 없습니다. **간단한 것은 가볍게, 복잡한 것은 구조를 갖춰서** — 이 원칙만 기억하면 충분합니다. 그리고 이 통합은 앞 챕터에서 확인한 **"Claude
Code는 컨텍스트 관리에 진심"** 이라는 방향과도 이어집니다. 흩어져 있던 확장 기능들이 하나의 체계로 수렴하고 있는 것이죠.
