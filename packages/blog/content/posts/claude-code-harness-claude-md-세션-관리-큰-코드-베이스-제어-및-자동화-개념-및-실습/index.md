## 프로젝트 규칙, 코딩 스타일, 금지사항을 CLAUDE.md에 영구 고정하는 실전 패턴

새 섹션이 시작됩니다. 이번 섹션의 주제는 **Context Harness의 구현**입니다. 앞 섹션들이 개념과 도구를 다뤘다면, 여기서부터는 **실제 파일을 쓰는** 이야기입니다. 섹션 전체가 다룰 범위는
이렇습니다.

```
  CLAUDE.md  →  세션 관리  →  큰 코드베이스 제어
        →  Harness Engineering 워크플로 구축
        →  GitHub 자동화  →  Worktree 병렬 세션
```

그 첫 번째가 **`CLAUDE.md`** 입니다.

### `CLAUDE.md`는 메모장이 아니다

이 챕터는 개념 교정부터 시작합니다.

> "하지만 이 파일을 **Claude가 기억하는 메모장 정도로 이해하면 좀 부족하고요.**"

그럼 무엇으로 봐야 할까요. 강사 **미국달팽이**님의 표현이 강렬합니다.

> "실무에서 **`CLAUDE.md`를 프로젝트의 하나의 법처럼 설계를 해야** 됩니다. **하나의 규칙**인 거죠."

**법 (法)** 이라는 단어가 핵심입니다. 메모는 참고하는 것이고, 법은 **판단의 기준**입니다. 이 차이가 작성 방식을 완전히 바꿉니다.

| `CLAUDE.md`를 메모로 볼 때 | 법으로 볼 때                      |
|----------------------------|-----------------------------------|
| 생각날 때 적어 둠          | **판단 기준을 의도적으로 설계**함 |
| 길어져도 상관없음          | **구조와 우선순위**가 있음        |
| 개인 편의                  | **팀이 공유하는 기준**            |

### `CLAUDE.md`가 하는 네 가지 일

`CLAUDE.md`는 팀의 코딩 스타일, 아키텍처 경계, 테스트 명령, 금지된 변경 범위를 **Startup context로 고정**합니다. 그 결과 다음 네 가지를 얻습니다.

| # | 역할                    | 효과                                     |
|---|-------------------------|------------------------------------------|
| 1 | **반복 제거**           | Claude가 **규칙을 반복해서 묻지 않는다** |
| 2 | **아키텍처 경계 지정**  | 어디까지가 이 레이어의 책임인지 명시     |
| 3 | **금지 범위 명시**      | **어떤 파일을 왜** 건드리면 안 되는지    |
| 4 | **검증·완료 기준 제시** | Claude가 **스스로 검증**하게 만든다      |

세 번째의 **"왜"** 가 중요합니다. "이 파일 건드리지 마"보다 "이 파일은 외부 계약이라 바꾸면 클라이언트가 깨진다"가 훨씬 잘 지켜집니다. 이유가 있어야 **경계 사례에서도 판단**할 수 있기 때문입니다.

네 번째도 짚고 갈 만합니다. 완료 기준을 파일에 박아 두면, 앞 시리즈 Verification Harness 챕터에서 본 **"테스트 없이 완료를 선언하는"** 문제를 매 세션 반복해서 말하지 않아도 됩니다.

### 세 개의 레이어

> "**`CLAUDE.md` 같은 경우에는 3개의 layer가 있어요.**"

공식 메모리 문서 기준으로 정리하면 이렇습니다. 각 층이 **담는 내용과 공유 범위**가 다릅니다.

| 계층                    | 담는 내용                                                      | 공유 범위          |
|-------------------------|----------------------------------------------------------------|--------------------|
| **Enterprise**          | 조직의 **보안 정책**, 회사 표준                                | 조직 전체          |
| **User `CLAUDE.md`**    | 개인 선호, 자주 쓰는 명령, 개인적인 스타일                     | **나만**           |
| **Project `CLAUDE.md`** | 팀 공통 프로젝트 규칙, 아키텍처 경계, 테스트 명령, 코딩 컨벤션 | **팀 전체 (커밋)** |
| **`CLAUDE.local.md`**   | 로컬 환경, 실험적 지침, **공유하면 안 되는 개인 메모**         | 나만 (커밋 안 함)  |

```
  Enterprise        조직 표준 · 보안 정책
       ↓
  User              내 개인 선호 (모든 프로젝트 공통)
       ↓
  Project           팀 규칙 ← 저장소에 커밋되어 공유
       ↓
  CLAUDE.local.md   내 로컬 실험 (공유 안 함)
```

**Project `CLAUDE.md`가 Source control로 공유된다**는 점이 핵심입니다. 앞 시리즈에서 반복해서 강조한 **"개인의 노하우가 팀의 규칙이 된다"** 는 지점이 바로 이 파일입니다.

그리고 `CLAUDE.local.md`의 존재 이유도 명확합니다. **공유하면 안 되는 것을 Project 파일에 섞지 않기 위해서**입니다. "내 로컬은 포트가 달라서…" 같은 내용이 팀 규칙 파일에 들어가면
곤란하죠.

### 짧을수록 잘 따른다

작성 방식에 대한 조언이 반직관적입니다.

> 실제 프로젝트용 `CLAUDE.md`는 **길기만 해서는 안 되며, 짧고 강하게** 작성해야 합니다.

공식 메모리 문서에 따르면 `CLAUDE.md`는 **전체가 로드**됩니다. 그런데도 짧게 쓰라고 합니다. 이유는 **로딩 여부가 아니라 준수율**의 문제이기 때문입니다.

```
  CLAUDE.md는 전부 로드된다
       ↓
  하지만 짧을수록 Claude가 더 잘 따른다
       ↓
  길게 쓰면 오히려 준수율이 떨어진다
```

이건 앞 시리즈 Context Harness 챕터에서 본 **"많이 주는 게 아니라 정확히 주는 것"** 과 정확히 같은 원리입니다. 규칙이 50줄이면 다 지키지만, 500줄이면 어느 것이 중요한지 모릅니다.

### Auto memory의 로딩 제한

여기서 실무적으로 꼭 알아야 할 수치가 나옵니다. **Auto memory**는 `CLAUDE.md`와 달리 **전부 로드되지 않습니다.**

| 대상            | 로딩 방식                                        |
|-----------------|--------------------------------------------------|
| **`CLAUDE.md`** | **전체 로드**                                    |
| **Auto memory** | 시작 시 **첫 200줄 또는 25KB 중 작은 쪽**만 로드 |
| **토픽 파일**   | **필요할 때** 읽힘                               |

그래서 실전 규칙이 하나 생깁니다. **핵심 내용을 앞쪽에 배치**해야 합니다. 뒤에 묻힌 중요한 규칙은 아예 읽히지 않을 수 있습니다.

### Worktree를 써도 메모리는 격리되지 않는다

이 챕터에서 가장 놓치기 쉬운 함정입니다.

> Auto memory는 **같은 Git 저장소의 Worktree 및 서브 디렉터리에서 하나의 메모리 디렉터리를 공유**합니다.

앞 시리즈 Subagent & Worktree Harness 챕터에서 "Worktree는 파일 시스템을 격리한다"고 했습니다. 맞는 말이지만, **메모리까지 격리되는 건 아닙니다.**

| 격리되는 것     | 격리되지 않는 것 |
|-----------------|------------------|
| **파일 시스템** | **Auto memory**  |
| **브랜치**      |                  |
| **테스트 결과** |                  |

```
  repo/            ┐
  repo-bugfix/     ├─→  파일은 분리, 하지만 메모리 디렉터리는 하나
  repo-refactor/   ┘
```

**병렬 워크트리를 쓴다고 메모리가 완전히 격리된다고 착각하면 안 됩니다.** 한쪽 세션에서 남긴 자동 메모리가 다른 워크트리 세션에도 영향을 줄 수 있습니다.

### 세션 · 에이전트 · 워크트리는 각각 다른 단위다

관련해서 세 개념의 단위를 정리하고 갑니다.

| 개념         | 단위                        |
|--------------|-----------------------------|
| **세션**     | **대화** 단위               |
| **에이전트** | **실행** 단위               |
| **워크트리** | **파일 시스템·브랜치** 단위 |

셋이 다른 축이라는 걸 알아야 "어디까지 분리되는가"를 정확히 판단할 수 있습니다. 앞의 메모리 공유 문제도 결국 **메모리가 이 셋 중 어느 축에도 완전히 묶여 있지 않다**는 데서 나옵니다.

### 실전 `CLAUDE.md`는 규칙을 분류한다

좋은 `CLAUDE.md`의 특징은 **모든 규칙이 종류별로 분리되어 있다**는 점입니다. 강의의 예시는 이런 카테고리로 나뉩니다.

| 카테고리         | 담기는 것                             |
|------------------|---------------------------------------|
| **Architecture** | 레이어 경계, 의존 방향, 설계 원칙     |
| **Testing**      | 테스트 명령, 커버리지 기준, 통과 조건 |
| **Safety**       | 금지 파일, 건드리면 안 되는 범위      |
| **Workflow**     | 작업 순서, 완료 기준, PR 규칙         |

형태로 보면 이런 모습입니다.

```markdown
# Architecture

- 컨트롤러에 비즈니스 로직을 작성하지 않는다
- 도메인 레이어는 인프라 레이어를 참조하지 않는다

# Testing

- 테스트 명령: `./gradlew test`
- 테스트 없이 "완료"를 선언하지 않는다

# Safety

- `.env`, `secrets/` 는 읽지 않는다
- DB 스키마와 Public API 응답 형태는 변경하지 않는다

# Workflow

- 수정 전에 관련 파일을 먼저 탐색하고 계획을 제시한다
- 변경은 작은 단위로 커밋한다
```

이렇게 분류해 두면 **Claude가 수정할 때 어떤 기준을 적용해야 하는지 쉽게 찾습니다.** 반대로 규칙이 한 덩어리로 나열되어 있으면, 앞 시리즈에서 본 **"많이 줬는데 흐린 정보"** 가 됩니다.

### 그런데 `.env` 규칙은 여기 있으면 안 된다

이 챕터의 가장 중요한 경고입니다. 위 예시의 Safety 항목을 다시 보겠습니다.

```markdown
# Safety

- `.env`, `secrets/` 는 읽지 않는다
```

이 줄은 **실제로 막지 못합니다.**

> `.env` 파일은 읽지 말라는 내용은 `CLAUDE.md`에만 두면 **가이던스일 뿐**입니다. 실제로 막고 싶다면 `settings.json`의 `permissions.deny`에도 넣어 줘야 합니다.

그리고 강사는 `CLAUDE.md`의 한계를 분명히 못 박습니다.

> "**`CLAUDE.md`는 모든 위험을 막아주는 보안적인 장치는 아니라고** 보시면 됩니다."

앞 시리즈 Context Harness와 Permission Harness 챕터에서 반복된 구분이 여기서 **실제 파일 두 개**로 구체화됩니다.

| 파일                                     | 성격                  | 강제력                              |
|------------------------------------------|-----------------------|-------------------------------------|
| **`CLAUDE.md`**                          | 가이드라인, 판단 기준 | **소프트** (지켜질 수도, 아닐 수도) |
| **`settings.json`의 `permissions.deny`** | 실제 차단             | **하드** (시도해도 차단됨)          |

```
  CLAUDE.md에 "읽지 마"        →  Claude가 읽으려 시도할 수 있음
  permissions.deny에 등록      →  실행하려 해도 실제로 차단됨
```

공식 Settings 문서 역시 **민감한 파일 접근을 막기 위해 `permissions.deny`를 사용하는 예시**를 제공합니다. 즉 이건 응용이 아니라 **문서가 안내하는 기본 사용법**입니다.

> **핵심.** `CLAUDE.md`에도 쓰고, `permissions.deny`에도 넣습니다. 둘 중 하나가 아니라 **둘 다**입니다. `CLAUDE.md`는 **왜 안 되는지**를 알려 주고,
> `permissions.deny`는 **실제로 막습니다.**

### 팀 하네스와 개인 하네스를 분리한다

`settings.json`에도 계층이 있습니다. 그리고 이 분리가 `CLAUDE.md`의 Project / local 분리와 정확히 짝을 이룹니다.

| 파일                      | 담는 것                                            | 공유        |
|---------------------------|----------------------------------------------------|-------------|
| **`settings.json`**       | 팀이 공유해야 할 `permissions.deny` / `allow` 정책 | **팀 공유** |
| **`settings.local.json`** | 개인 실험용 설정                                   | **개인**    |

전체를 한 장으로 놓으면 이렇게 대칭이 보입니다.

```
              규칙·가이드            강제·차단
            ─────────────       ──────────────────
  팀 공유    CLAUDE.md      +    settings.json
  개인      CLAUDE.local.md  +   settings.local.json
```

`.gitignore` 대상이나 개인 실험용 파일을 블로킹하는 것도 `settings` 쪽에서 처리할 수 있습니다.

### 정리

강사가 마지막에 원칙을 이렇게 요약합니다.

> "**`CLAUDE.md` 같은 경우에는 팀의 판단 기준을 고정하는 규칙 또는 프로젝트를 설명하는 설정 파일이고요. 그리고 규칙을 분리하는 겁니다.**"

1. **`CLAUDE.md`는 메모장이 아니라 프로젝트의 법이다.** 팀의 판단 기준을 고정하는 파일로 설계한다.
2. **네 가지를 담는다.** 반복 제거 · 아키텍처 경계 · **왜 금지인지** · 검증과 완료 기준.
3. **계층을 구분해서 쓴다.** Enterprise (조직) / User (개인 선호) / **Project (팀 공유·커밋)** / `CLAUDE.local.md`(공유 안 함).
4. **짧을수록 잘 따른다.** 전체가 로드되지만, **길게 쓰면 준수율이 떨어진다.**
5. **Auto memory는 첫 200줄 또는 25KB만 로드된다.** 핵심은 앞쪽에 둔다.
6. **Worktree를 써도 메모리는 공유된다.** 파일 시스템 격리 ≠ 메모리 격리.
7. **Guidance와 Enforcement를 분리한다.** 반드시 막아야 할 것은 `CLAUDE.md`가 아니라 **`settings.json`의 `permissions.deny`** 로 간다.

## clear/compact/요약 갱신으로 세션 오염 방지 전략 실습

앞 챕터에서 규칙을 파일로 고정했습니다. 그런데 파일을 아무리 잘 써 놔도, **세션이 길어지면 결과가 나빠지는** 현상은 여전히 남습니다. 이번 챕터는 그 문제를 다룹니다.

### 처음엔 똑똑하던 Claude가 왜 빗나가나

누구나 겪는 상황입니다.

> "처음에는 분명히 **똑똑하게 잘하던 Claude가 대화도 길어지고, 파일도 많이 읽고, 로그도 많이 붙이다 보면 이상하게 방향이 빗나갈 때**가 있어요."

이때 우리는 자연스럽게 모델을 의심합니다. 강사 **미국달팽이**님은 그 해석을 정정합니다.

> "이럴 때 **모델이 멍청해졌다고 생각하실 수도 있는데, 사실은 컨텍스트가 불필요한 정보를 팽창시키면서 초기 제약이 희석이 된** 겁니다."

**"초기 제약의 희석"** 이 정확한 표현입니다. 세션 초반에 준 규칙과 범위가 사라진 게 아니라, **뒤에 쌓인 정보에 묻힌** 것이죠.

```
 [세션 초반]                     [세션 후반]
 ┌──────────────┐               ┌──────────────┐
 │ 규칙·제약    │  ← 선명       │ 규칙·제약    │  ← 묻힘
 ├──────────────┤               ├──────────────┤
 │              │               │ 파일 내용    │
 │              │               │ 로그         │
 │              │               │ 틀린 가설    │
 │              │               │ 실패한 시도  │
 └──────────────┘               └──────────────┘
```

세션이 길어질수록 **좋은 정보와 함께 잡음도 같이 쌓입니다.** 그래서 결론이 이렇게 됩니다.

> 작업 품질은 **모델 성능뿐만 아니라, 컨텍스트를 얼마나 깨끗하게 유지했는지**에 크게 좌우됩니다.

### 두 개의 명령: 분리와 압축

세션 오염에 대응하는 운영 루틴은 두 명령으로 구성됩니다.

| 명령           | 하는 일                     | 이전 대화         |
|----------------|-----------------------------|-------------------|
| **`/clear`**   | 대화 기록을 **완전히 리셋** | **버린다**        |
| **`/compact`** | 대화를 **요약해서 남긴다**  | **압축해 남긴다** |

```
  /clear    ──→  분리 (Separation)
  /compact  ──→  압축 (Compression)
```

이 둘은 대체 관계가 아니라 **용도가 다른 도구**입니다.

#### `/clear` — 작업 단위가 바뀔 때

`/clear`는 대화 기록을 완전히 지웁니다. 목적은 **이전 작업 맥락이 다음 작업에 섞이는 것을 막는 것**입니다.

기준은 명확합니다. **작업 단위가 바뀌면 끊습니다.**

```
  로그인 버그 수정 완료
       ↓
     /clear      ← 여기서 끊는다
       ↓
  결제 기능 리팩터링 시작
```

앞 시리즈 Context Harness 챕터에서 "오염된 컨텍스트를 이어 가면 **더 정교한 오답**이 나온다"고 했던 것에 대한 실무적 대응이 바로 이것입니다.

#### `/compact` — 작업이 길어질 때

같은 작업을 계속해야 하는데 대화만 길어진 경우에는 `/clear`가 답이 아닙니다. 지금까지의 맥락이 필요하니까요. 이때 쓰는 것이 `/compact`입니다.

Claude Code의 설명 문구 그대로 **`Keep a summary in context`** — 이전 대화를 요약해서 컨텍스트에 남깁니다.

| 상황                | 선택           |
|---------------------|----------------|
| **작업이 바뀐다**   | **`/clear`**   |
| **작업이 길어진다** | **`/compact`** |

### `/compact`만 치면 안 된다

이 챕터에서 가장 실전적인 지적입니다. 대부분 `/compact`를 그냥 칩니다. 그런데 그러면 안 됩니다.

> `/compact`만 사용해서는 안 되며, **무엇을 남길지 구체적으로 지시**해야 합니다. 그렇지 않으면 **정작 중요한 맥락이 빠지고 요약만 남아, 다음 턴에서 또 벗어날** 수 있습니다.

Claude Code는 `/compact` 실행 시 **`Optional Custom Summarization Instruction`** 을 받습니다. 즉 **어떻게 압축할지 지시할 수 있습니다.**

남길 항목을 명시하는 게 핵심입니다.

```
[/compact에 함께 줄 지시 항목]

  · 변경한 파일 목록
  · 실행한 커맨드
  · 통과한 테스트 / 실패한 버그
  · 남은 To-Do 리스트
```

실제로는 이런 식으로 씁니다.

```
/compact 변경한 파일 목록, 실행한 명령, 현재까지 통과한 테스트와
         실패한 버그, 남은 작업을 항목별로 정리해서 남겨 줘
```

```
  ❌ /compact                    →  요약은 남지만 중요한 게 빠질 수 있음
  ⭕ /compact + 남길 항목 명시   →  다음 턴에 필요한 것만 정확히 남음
```

앞 시리즈에서 **"압축은 언제나 손실을 동반한다"** 고 했습니다. 손실이 불가피하다면, **무엇을 잃을지 사람이 고르는 것**이 맞습니다.

### 가장 중요한 건 요약 갱신이다

`/clear`와 `/compact`보다 더 중요한 것이 있습니다. **요약 갱신**, 즉 **파일로의 승격**입니다.

> 대화 중 나온 **중요한 결론, 금지 사항, 테스트 커맨드, 결정 사항**을 `CLAUDE.md` 같은 **규칙 파일로 승격**시켜야 합니다.

이유가 명쾌합니다.

> "쉽게 말해서 **대화 속 규칙은 휘발성이고, 파일 속 규칙은 지속성**이라고 보시면 됩니다."

| 위치     | 성격       | `/compact` 후      | 다음 세션     |
|----------|------------|--------------------|---------------|
| **대화** | **휘발성** | **사라질 수 있음** | 없음          |
| **파일** | **지속성** | 영향 없음          | **다시 읽힘** |

```
  대화에서 나온 결정
        ↓
  파일로 승격 (CLAUDE.md 등)
        ↓
  이후 세션마다 프로젝트 컨텍스트로 다시 로드
```

앞 챕터의 `CLAUDE.md` 이야기가 여기서 **운영 루틴으로 연결**됩니다. `CLAUDE.md`는 처음에 한 번 쓰고 끝나는 파일이 아니라, **세션에서 얻은 규칙이 계속 쌓여 올라가는 목적지**입니다.

### 실습 1. 일부러 오염된 세션 만들기

이론만으로는 세션 오염이 잘 체감되지 않습니다. 그래서 강의는 **일부러 지저분한 세션을 만들어 봅니다.**

간단한 프로젝트를 열어 놓고, 성격이 다른 작업들을 **섞어서** 던집니다.

```
[의도적으로 오염시키는 프롬프트 조합]

  1. 로그인 버튼 스타일 좀 수정해 줘      ← UI 변경
  2. 이 에러 로그 분석해 줘               ← 로그 분석
  3. 테스트 파일들 좀 읽어 봐             ← 파일 읽기
  4. (금지사항 언급)                      ← 제약 조건
  5. 테스트도 돌려 줘                     ← 검증 요구
```

결과는 예상대로입니다.

> 이렇게 막 섞어서 던지면 **처음에는 잘 따라가다가 점점 맥락이 산만해지는 것**을 느낄 수 있습니다.

특히 **파일 읽기 · 로그 분석 · UI 변경 · 금지사항 · 테스트 요구**가 한 세션에 뒤섞이면 금방 체감됩니다. 앞 섹션에서 "조사 세션과 수정 세션, 검토 세션을 섞지 말라"고 했던 이유를 몸으로 확인하는
실습인 셈이죠.

### 실습 2. `/clear`로 리셋하고 범위를 좁히기

오염된 세션에서 새 작업을 시작할 때 `/clear`를 씁니다. 강의에서 관찰되는 변화가 흥미롭습니다.

```
  [오염된 세션]   "모든 페이지"를 탐색하려 함   ← 범위가 넓음
        ↓ /clear
  [리셋 후]       "모든 파일"을 파악하는 쪽으로 ← 범위가 좁혀짐
```

`/clear`가 **탐색 범위 자체를 좁혀 준다**는 점이 포인트입니다. 이전 세션에서 넓게 벌려 놓은 관심사가 사라지니, Claude가 지금 작업에만 집중하게 됩니다.

이어지는 실습에서는 **애니메이션이 적용되지 않은 프로그레스 UI 버그**를 다룹니다. 흐름은 앞 시리즈에서 계속 강조한 순서 그대로입니다.

```
  원인 후보 3개 분석  →  해당 코드 추출  →  범위를 좁혀 수정  →  빌드로 검증
```

**"먼저 수정하지 말고 원인 후보를 좁혀라"** 는 Debugging Harness의 원칙이 실습에서 그대로 적용됩니다.

### 실습 3. 지시와 함께 `/compact` 걸기

여러 테스트와 검증, 배치 작업을 거친 뒤 세션이 무거워졌을 때 `/compact`를 겁니다. 앞에서 강조한 대로 **그냥 치지 않습니다.**

```
[커스텀 요약 지시와 함께]

  · 변경한 파일 목록
  · 실행한 명령
  · 현재까지 통과한 테스트
  · 실패한 버그
```

> **남길 항목을 명시한 다음에 compact를 거는 것**이 중요합니다.

### 실습 4. 대화 내용을 파일로 승격

마지막 단계입니다. 대화로만 남아 있던 사실들을 **파일로 옮깁니다.**

| 남길 것                  | 어디에                       |
|--------------------------|------------------------------|
| **테스트 결과**          | 저장소 (VCS)                 |
| **변경 파일 목록**       | 저장소 (VCS)                 |
| **확정된 규칙·금지사항** | **`CLAUDE.md`** 등 규칙 파일 |

이렇게 해 두면 다음 세션은 **빈손으로 시작하지 않습니다.** 앞 챕터에서 본 것처럼 `CLAUDE.md`는 매 세션 시작 시 다시 로드되니까요.

### 세 가지를 한 줄로

강사가 마지막에 운영 원칙을 이렇게 정리합니다.

> "**작업이 바뀌면 clear, 작업이 길어지면 compact를 시켜주고요, 만약에 계속 유지해야 되는 규칙은 파일로 옮겨** 주시면 됩니다."

| 상황                      | 조치                  | 효과                        |
|---------------------------|-----------------------|-----------------------------|
| **작업 단위가 바뀐다**    | **`/clear`**          | 맥락 **분리**               |
| **작업이 길어진다**       | **`/compact` + 지시** | 맥락 **압축**               |
| **계속 유지해야 할 규칙** | **파일로 승격**       | **지속성** 확보 · 토큰 절약 |

```
        작업이 바뀌었나?
             ├─ 예 ──────────────→  /clear
             └─ 아니오
                  ├─ 세션이 길어졌나? ──→  /compact (+ 남길 항목 지시)
                  └─ 계속 쓸 규칙인가? ──→  CLAUDE.md로 승격
```

세 번째가 **토큰 효율**과도 직결됩니다. 매 세션 같은 규칙을 대화로 다시 설명하면 그만큼 토큰을 씁니다. 파일에 두면 한 번 쓰고 계속 재사용됩니다.

### 정리

1. **세션이 길어지면 "모델이 멍청해진" 게 아니라 초기 제약이 희석된 것이다.** 좋은 정보와 잡음이 같이 쌓인다.
2. **작업 품질은 컨텍스트를 얼마나 깨끗하게 유지했는지에 좌우된다.** 모델 성능만의 문제가 아니다.
3. **`/clear`는 분리, `/compact`는 압축이다.** 작업이 바뀌면 `/clear`, 작업이 길어지면 `/compact`.
4. **`/compact`는 그냥 치지 마라.** 변경 파일·실행 명령·테스트 결과·남은 To-Do 등 **남길 항목을 명시**해야 중요한 맥락이 살아남는다.
5. **대화 속 규칙은 휘발성, 파일 속 규칙은 지속성이다.** 확정된 결론·금지사항·테스트 커맨드는 `CLAUDE.md`로 승격시킨다.
6. **`CLAUDE.md`는 한 번 쓰고 끝이 아니다.** 세션에서 얻은 규칙이 계속 쌓여 올라가는 목적지다.

## Claude가 엉뚱한 수정안을 내놓을 때 context 재설계 방법 실습

앞 챕터가 **세션이 길어져서** 생기는 문제였다면, 이번 챕터는 **처음부터 방향이 어긋나는** 문제입니다. 강사 **미국달팽이**님이 상황을 정확히 묘사합니다.

> "**클로드가 분명히 뭔가 많이 하긴 했는데 결과를 보면 원한 건 이게 아닌** 경우들이 많기 때문에"

일을 안 한 게 아닙니다. **많이 했는데 원한 게 아닌** 것이죠. 그래서 더 답답합니다.

### 원인은 모델이 아니라 세 가지 부재

왜 이런 일이 생길까요. 원인은 모델의 결함이 아니라 **주지 않은 것들**에 있습니다.

| 부재한 것          | 결과                         |
|--------------------|------------------------------|
| **명확한 지시**    | 어디까지 건드릴지 모른다     |
| **금지 범위**      | 건드리면 안 되는 곳을 모른다 |
| **완료 판단 기준** | 언제 끝인지 모른다           |

가장 흔한 예시가 이것입니다.

```
  "로그인 버튼 고쳐 주세요"
```

한 줄짜리 요청이 Claude에게 **너무 많은 선택지**를 줍니다.

- 어디까지 건드려야 하나?
- 어디는 건드리면 안 되나?
- 마지막에 무엇을 확인해야 하나?

세 질문에 답이 없으니 **Claude가 스스로 답을 만들어 냅니다.** 그리고 그 답이 우리가 생각한 것과 다를 뿐입니다.

### 해결책은 설명을 더 하는 게 아니다

여기서 이 강의가 계속 반복해 온 원칙이 다시 나옵니다.

> "여기서 중요한 건 **설명을 더 길게 하는 게 아니에요. 컨텍스트를 다시 설계를 해야** 됩니다."

`설명 추가`와 `컨텍스트 재설계`는 완전히 다른 행동입니다.

```
  ❌ 설명 추가   :  같은 요청에 문장을 덧붙인다        →  범위는 그대로 넓음
  ⭕ 재설계      :  범위·금지·조건·검증을 새로 정한다  →  헤맬 여지가 줄어듦
```

### 컨텍스트 재설계 4단계

이 챕터의 핵심 도구입니다.

| 단계 | 하는 일                                            |
|------|----------------------------------------------------|
| 1    | **문제를 한 문장으로** 명확히 한다                 |
| 2    | **수정 가능 범위**와 **수정 금지 범위**를 분리한다 |
| 3    | **절대 깨지면 안 되는 조건**을 명시한다            |
| 4    | **무엇을 실행해야 끝인지** 명확히 한다             |

강사가 이 넷을 한 문장으로 압축합니다.

> "그렇기 때문에 **'알아서 잘 고쳐주세요' 방식이 아니라 '이 범위 안에서 고치고, 이 파일은 건드리지 말고, 이 조건은 유지하고, 마지막에 이러한 테스트로 검증을 해줘'** 라고 바꿔 주는 겁니다."

```
  이 범위 안에서 고치고        ← 수정 가능 범위
  이 파일은 건드리지 말고      ← 수정 금지 범위
  이 조건은 유지하고           ← 유지 조건
  이 테스트로 검증해 줘        ← 검증 기준
```

목적은 하나입니다. **Claude가 헤맬 수 있는 범위를 줄이는 것.**

앞 시리즈 Context Harness 챕터의 **Context Pack**(목표·증거·파일 후보·수정 금지·검증)과 사실상 같은 구조입니다. 이번에는 그것을 **실패한 뒤 다시 짜는** 상황에 적용하는 것이죠.

### 실습 1. 일부러 애매하게 요청해 보기

강의는 먼저 **일부러 애매한 요청**을 던집니다. 대상은 일론 머스크의 시간 관리법을 구현한 프로젝트입니다.

```
  "왼쪽 사이드 메뉴에 로그인 버튼을 추가해 줘"
```

결과가 흥미롭습니다.

| 요청한 것        | 나온 것                              |
|------------------|--------------------------------------|
| 로그인 버튼 추가 | 버튼은 추가됨 — **위치는 대략 맞음** |
|                  | 그런데 **아무 동작도 하지 않음**     |

**틀린 건 아니지만 쓸 수 없는 결과**입니다. 요청에 "클릭하면 어떻게 되어야 하는지"가 없었으니, Claude 입장에서는 요청을 완수한 셈이기도 합니다.

### 실습 2. 4단계로 재설계하기

같은 문제를 이번에는 재설계해서 다시 던집니다. 강의에서 실제로 구성한 내용을 항목별로 옮기면 이렇습니다.

| 항목               | 내용                                                                                         |
|--------------------|----------------------------------------------------------------------------------------------|
| **목표**           | 로그인 버튼 클릭 시 **로그인 페이지로 이동**하고, 그 페이지는 **디자인 컨셉에 맞게 UI 구성** |
| **재현**           | 로그인 버튼 추가 후 **아무 동작도 하지 않음**                                                |
| **수정 가능 범위** | `layout-sidebar.tsx` 컴포넌트                                                                |
| **수정 금지 범위** | **환경 파일**, **GitHub 워크플로우**                                                         |
| **유지 조건**      | 로그인 버튼의 **위치·디자인은 수정하지 말 것**                                               |
| **검증 기준**      | `npm run build`, `npm test`                                                                  |
| **보고 항목**      | 변경 파일 목록, 핵심 수정 내용, 실행한 검증 결과                                             |

프롬프트 형태로 정리하면 이런 모습입니다.

```
[목표]
  로그인 버튼을 클릭하면 로그인 페이지로 이동해야 한다.
  로그인 페이지는 기존 디자인 컨셉에 맞게 구성한다.

[재현]
  현재 로그인 버튼을 눌러도 아무 동작이 없다.

[수정 가능 범위]
  layout-sidebar.tsx

[수정 금지]
  환경 파일, GitHub 워크플로우

[유지 조건]
  로그인 버튼의 위치와 디자인은 변경하지 않는다.

[검증]
  npm run build
  npm test

[완료 시 알려 줄 것]
  변경 파일 목록 / 핵심 수정 내용 / 실행한 검증 결과
```

여기서 **재현**과 **보고 항목**이 4단계에 덧붙은 실전 요소입니다. 재현은 앞 시리즈 Debugging Harness의 `Symptom`에 해당하고, 보고 항목은 **사람이 검토할 재료를 미리 요구**하는
장치입니다.

### 재설계의 결과

같은 문제, 같은 모델인데 결과가 달라집니다.

| 관찰 항목          | 애매한 요청   | 재설계 후                              |
|--------------------|---------------|----------------------------------------|
| **작업 범위**      | 넓게 움직임   | **덜 넓게 움직임**                     |
| **허용 범위 준수** | 불확실        | **허용 범위 안에 머무름**              |
| **보고**           | 없음          | **변경 파일·수정 내용·검증 결과 제시** |
| **기능**           | 동작하지 않음 | **클릭 시 로그인 페이지로 이동**       |

주목할 점은 **"덜 넓게 움직였다"** 는 표현입니다. 재설계의 효과는 "더 똑똑해졌다"가 아니라 **"덜 헤맸다"** 입니다. 이 강의가 처음부터 말해 온 **"모델을 똑똑하게 만드는 게 아니라 주변 구조를
설계하는 것"** 이 실습으로 확인되는 대목이죠.

### 이미 어긋난 세션에 설명을 덧붙이면 더 위험하다

이 챕터에서 가장 중요한 경고입니다.

> "**이미 클로드가 잘못된 방향으로 간 뒤에 그 상태에서 설명만 계속 덧붙여주는** 거예요. 그렇게 되면 좀 더 위험해지는데 **컨텍스트가 이미 오염된 상태이기 때문에 좋은 지시도, 좋은 프롬프트도 희석되는**
> 경우가 많아요."

**"좋은 지시도 희석된다"** 가 핵심입니다. 문제는 지시의 품질이 아니라 **그 지시가 놓이는 자리**입니다. 오염된 컨텍스트 위에 얹으면 아무리 정확한 지시도 묻힙니다.

```
 [오염된 세션에 설명 추가]
  틀린 가설 + 틀린 수정 + 좋은 새 지시
        ↓
  모델은 셋을 모두 "합의된 맥락"으로 취급
        ↓
  더 정교한 오답

 [방향을 끊고 재정의]
  /clear 또는 새 세션
        ↓
  좁은 범위로 명확히 재정의
        ↓
  깨끗한 판단
```

그래서 순서가 이렇습니다. **방향을 먼저 끊고, 좁은 범위의 작업으로 명확하게 재정의합니다.** 앞 챕터에서 배운 `/clear`가 여기서 쓰이는 것이죠.

### 큰 작업이면 "수정하지 말고 계획만 줘"

범위가 큰 작업에서 특히 유용한 기술입니다.

> "그래서 만약에 엉뚱한 방향으로 갔다라고 한다면, **'지금은 수정하지 말고, 어떤 파일을 검색할지, 왜 그 파일을 먼저 보는 것인지 먼저 계획만 제시해줘'** 라고 해줄 겁니다."

두 가지를 요구한다는 점이 포인트입니다.

| 요구                         | 확인할 수 있는 것          |
|------------------------------|----------------------------|
| **어떤 파일을 검색할지**     | 탐색 범위가 적절한가       |
| **왜 그 파일을 먼저 보는지** | **판단의 근거가 타당한가** |

두 번째가 특히 중요합니다. 파일 목록만 받으면 맞는지 판단하기 어렵지만, **이유까지 받으면 그 논리가 어긋난 지점을 짚어낼 수 있습니다.** 수정이 일어나기 **전에** 방향을 교정할 수 있는 것이죠.

이 방식이 필요한 신호는 이렇습니다.

| 신호                                   |
|----------------------------------------|
| 관련 없는 파일을 건드린다              |
| 수정은 끝났는데 **테스트가 비어 있다** |
| **작업 범위가 점점 넓어진다**          |
| **건드리면 안 되는 경로**가 있다       |

### 언제 쓰지 말아야 하나

균형을 잡는 대목입니다. 이 방식은 **공짜가 아닙니다.**

> 너무 작은 작업에는 **오버헤드**가 될 수 있습니다. **단순 오타 수정이나 문장 수정** 등 검증 범위가 명확한 작은 변경에는 쓰지 않습니다.

| 쓸 때                           | 쓰지 말 때                            |
|---------------------------------|---------------------------------------|
| **수정 범위가 불명확**할 때     | 단순 오타·문장 수정                   |
| 작업 범위가 넓을 때             | **검증 범위가 이미 명확**한 작은 변경 |
| 건드리면 안 되는 경로가 있을 때 |                                       |

앞 섹션 Plan/Thinking Mode 챕터에서 **"바로 실행도 정당한 선택"** 이라고 했던 것과 같은 이야기입니다. 도구는 상황에 맞게 고르는 것이지, 항상 켜 두는 게 아닙니다.

### 정리

1. **"많이 했는데 원한 게 아닌" 결과의 원인은 모델이 아니다.** 명확한 지시·금지 범위·완료 기준, 이 셋의 부재다.
2. **해결책은 설명을 늘리는 게 아니라 컨텍스트 재설계다.** 같은 요청에 문장을 덧붙여도 범위는 그대로 넓다.
3. **4단계로 재설계한다.** 문제를 한 문장으로 → 수정 가능/금지 범위 분리 → 유지 조건 명시 → 완료 판정 기준 제시.
4. **효과는 "똑똑해짐"이 아니라 "덜 헤맴"이다.** 재설계 후 Claude는 **허용 범위 안에서** 움직이고 검증 결과까지 보고한다.
5. **이미 어긋난 세션에 설명을 덧붙이지 마라.** 오염된 컨텍스트 위에서는 **좋은 지시도 희석된다.** 방향을 먼저 끊는다.
6. **큰 작업이면 "수정하지 말고 계획만" 요청하라.** 파일 목록과 **그 파일을 먼저 보는 이유**까지 받아야 방향을 교정할 수 있다.
7. **작은 작업에는 쓰지 않는다.** 오타 수정에 재설계는 오버헤드다.

## GitHub Issue → PR 자동화 워크플로우 실습

지금까지는 **내 터미널 안**의 이야기였습니다. 이번 챕터는 그 경계를 넘습니다. GitHub 이슈를 트리거로 Claude가 **브랜치를 만들고, 코드를 고치고, Draft PR까지 올리는** 워크플로우입니다.

그런데 강사 **미국달팽이**님은 시작부터 제동을 겁니다.

> "그런데 여기서 많이 하시는 착각이 있을 수 있는데 **자동화가 가능하다고 해서 끝까지 자동으로 가는 게 항상 좋은 건 아닙니다.**"

### 이슈에는 무엇이 섞여 들어오는가

왜 전면 자동화가 위험할까요. **이슈라는 입력의 성격** 때문입니다.

| 이슈에 섞여 있는 것 | 왜 위험한가                       |
|---------------------|-----------------------------------|
| **모호한 요청**     | 해석의 여지가 크다                |
| **외부 입력**       | 신뢰할 수 없는 사람이 쓸 수 있다  |
| **미검토 요구사항** | 팀이 합의하지 않은 내용일 수 있다 |

이슈는 **누구나 쓸 수 있는 텍스트**입니다. 그리고 그게 자동으로 코드 변경으로 이어진다면, 앞 시리즈 Tool Harness 챕터에서 본 **프롬프트 인젝션**의 통로가 됩니다.

### 기준은 하나: 어디까지 자동화하고, 어디서 사람이 보는가

> "그래서 저는 이슈에서 PR 자동화에서 **가장 중요하게 보는 기준이 하나 있습니다. 어디까지 자동화하고 어디서 사람 검토를 남길 것인가**입니다."

이 기준으로 작업을 두 덩어리로 나눕니다.

| 자동화해도 되는 것 | **사람이 해야 하는 것** |
|--------------------|-------------------------|
| 이슈 읽기          | **최종 리뷰**           |
| 작업 브랜치 생성   | **위험 파일 확인**      |
| **초안** 코드 수정 | **CI 통과 확인**        |
| 커밋 생성          | **머지 승인**           |
| **Draft** PR 연결  |                         |

```
 ─────────── 자동화 구간 ───────────┃───── 사람 구간 ─────
 이슈 → 브랜치 → 초안 수정 → 커밋 → Draft PR ┃ 리뷰 → CI 확인 → 머지
                                              ↑
                                    여기가 넘으면 안 되는 선
```

**Draft PR에서 멈춘다**는 점이 핵심 설계입니다. 자동화는 **초안까지**, 판정은 사람이 합니다.

그 이유가 명쾌합니다.

> "**자동화는 빠르지만 최종 판단까지 없애는 순간 사고 비용이 훨씬 커지기** 때문입니다."

앞 시리즈 Permission Harness 챕터의 **실패 비용** 기준이 여기서 워크플로 단위로 적용되는 셈입니다.

### 사람 검토가 반드시 필요한 파일

특히 다음 영역이 변경에 포함되면 **무조건** 사람이 봐야 합니다.

| 영역           | 예시                     |
|----------------|--------------------------|
| **워크플로우** | `.github/workflows/`     |
| **인프라**     | Terraform, 배포 스크립트 |
| **배포 설정**  | 환경별 config            |
| **인증·권한**  | 인증 로직, 권한 정책     |
| **비밀 정보**  | 시크릿, 키 관련 파일     |

> **자동화가 초안을 만들어도, 반드시 사람이 다시 확인해야 합니다.**

`.github/workflows/`가 목록 맨 앞에 있는 게 의미심장합니다. **자동화를 정의하는 파일 자체가 자동으로 바뀔 수 있다면**, 경계선을 스스로 지우는 셈이니까요.

### 실습: 이슈 하나로 Draft PR까지

강의는 **"회원가입 버튼이 동작하지 않는다"** 는 이슈로 실습을 진행합니다.

#### 준비: `ANTHROPIC_API_KEY` 등록

먼저 GitHub Secrets에 API 키를 넣어야 합니다.

```
  GitHub 저장소 → Settings → Secrets → ANTHROPIC_API_KEY 등록
```

> **주의.** 키는 반드시 **Secrets**로 관리합니다. 워크플로우 파일이나 코드에 하드코딩하면, 이 챕터가 경계하는 **키 노출**이 바로 현실이 됩니다.

#### 트리거: 이슈 댓글에서 멘션

자동화의 시작은 간단합니다. **이슈 댓글에서 Claude를 멘션**하는 것이죠.

```
  Issue 작성
      ↓
  댓글에서 @claude 멘션      ← 여기가 트리거
      ↓
  GitHub Actions 실행
```

#### Claude가 수행한 작업

멘션 이후 Claude가 자동으로 처리한 흐름입니다.

| 단계 | 수행 내용                                        |
|------|--------------------------------------------------|
| 1    | **프로젝트 구조 분석**                           |
| 2    | 회원가입 **모달 컴포넌트 설계**                  |
| 3    | 픽셀아트 회원가입 **폼 구현**                    |
| 4    | **테스트 결과 · 기술 스택 · 수정된 핸들러** 보고 |
| 5    | **Draft PR 생성**                                |

4번이 눈에 띕니다. 앞 챕터에서 컨텍스트 재설계의 마지막 항목으로 **"변경 파일 목록, 핵심 수정 내용, 실행한 검증 결과를 알려 줘"** 를 넣었는데, 그것이 자동화 워크플로에서는 **PR 본문**으로 나타나는
셈입니다. 사람이 검토할 재료를 자동화가 미리 준비해 주는 것이죠.

이 과정을 구성하려면 **Claude Issue Automation 설정과 워크플로우 YAML 구조**를 이해해야 합니다.

#### 사람 구간: 검토 → 머지 → 확인

Draft PR이 올라온 뒤부터가 사람의 몫입니다.

```
  Draft PR
      ↓
  사람이 최종 검토
      ↓
  main 브랜치에 머지
      ↓
  빌드 후 실제 동작 확인
```

실습에서는 머지 후 **회원가입 모달 · 약관 동의 · 입력 폼 · 필수 필드 입력 경고**까지 정상 동작하는지 직접 확인합니다. **PR이 올라온 것과 기능이 동작하는 것은 다른 이야기**이므로, 마지막 확인이
빠지면 안 됩니다.

### 언제 쓰고, 언제 쓰지 말아야 하나

이 챕터에서 가장 실용적인 판단표입니다.

| 자동화가 **유용한** 환경                | 자동화를 **지양해야 할** 환경        |
|-----------------------------------------|--------------------------------------|
| **반복적인 이슈**가 많다                | **레포 권한 구조가 정리되지 않았다** |
| 유사한 **브랜치 생성·초안 작업**이 잦다 | **리뷰 문화가 없다**                 |
| **팀의 리뷰·CI 체계가 갖춰져** 있다     | **보안 파일이 자주 섞인다**          |
|                                         | **외부 입력을 신뢰할 수 없다**       |

오른쪽 열을 보면 공통점이 있습니다. 전부 **"사람 구간이 제대로 작동하지 않는 상태"** 입니다. 자동화는 뒤에 받쳐 줄 검토 체계가 있을 때만 이득입니다. **리뷰가 없는 팀에서 자동화는 사고를 더 빨리 만들어
낼 뿐입니다.**

### 흔히 저지르는 네 가지 실수

| 실수                          | 왜 위험한가                    |
|-------------------------------|--------------------------------|
| **머지까지 자동화**           | 최종 판단이 사라짐             |
| **과도한 권한 부여**          | 필요 이상으로 넓은 행동 반경   |
| **키·토큰 노출**              | 로그나 설정을 통해 유출        |
| **외부 입력 프롬프트를 신뢰** | **이슈 본문이 곧 지시문**이 됨 |

네 번째가 이 챕터에서 가장 무서운 항목입니다. 이슈는 누구나 열 수 있고, 그 내용이 그대로 Claude에게 전달됩니다. **외부인이 쓴 텍스트를 검증 없이 실행 지시로 취급하면**, 앞 시리즈에서 경고한 프롬프트
인젝션이 그대로 성립합니다.

### 자동화를 멈추고 설계에 시간을 쓰라

마무리 메시지가 이 챕터의 성격을 잘 보여 줍니다.

> "그래서 **자동화가 되니까 끝까지 자동화를 해야 된다라고 생각하시면 잘못된 것**이고, 실제로는 **자동화를 멈추신 다음에 검토하고 설계하는 방안에 대해서 좀 더 시간을 투자하시는 것이 좋습니다.**"

```
  ❌ "되니까 끝까지 간다"     →  사고 비용 ↑
  ⭕ "여기서 멈추고 설계한다" →  반복 초안은 줄이고, 판단은 남긴다
```

자동화의 목적은 **반복적인 초안 작업을 줄이는 것**이지, 판단을 없애는 것이 아닙니다. 이 강의가 첫 챕터부터 말해 온 **"무한 자율성이 아니라 검증 가능한 경계"** 가, 여기서는 **Draft PR이라는
정지선**으로 구현된 셈입니다.

### 정리

1. **자동화가 가능하다고 끝까지 가는 게 좋은 건 아니다.** 이슈에는 모호한 요청·외부 입력·미검토 요구가 섞인다.
2. **기준은 하나다.** 어디까지 자동화하고, **어디서 사람 검토를 남길 것인가.**
3. **자동화는 Draft PR까지, 판정은 사람이.** 최종 리뷰·위험 파일 확인·CI 통과·머지 승인은 넘기지 않는다.
4. **워크플로우·인프라·배포·인증·시크릿 파일은 무조건 사람이 본다.** 특히 `.github/workflows/`는 경계선 자체를 정의하는 파일이다.
5. **트리거는 이슈 댓글 멘션, 키는 GitHub Secrets로.** 하드코딩은 그 자체가 사고다.
6. **리뷰·CI 체계가 없으면 자동화하지 마라.** 자동화는 검토 체계가 받쳐 줄 때만 이득이다.
7. **네 가지 실수를 피하라.** 머지 자동화 · 과도한 권한 · 키 노출 · **외부 입력 신뢰**.

## worktree + 병렬 세션 실행으로 멀티 태스크 병렬 처리

이 섹션의 마지막 챕터입니다. 앞 시리즈에서 **"병렬 처리보다 중요한 것은 격리"** 라고 개념을 잡았다면, 이번에는 그것을 **실제 명령어로 실행**합니다.

### 같은 디렉터리에서 세션을 여러 개 띄우면

문제 상황부터 봅니다. Claude 세션 여러 개를 **같은 디렉터리**에서 실행하면 무슨 일이 벌어질까요.

| 문제                   | 결과                           |
|------------------------|--------------------------------|
| **파일 시스템 공유**   | 서로의 변경을 덮어쓴다         |
| **충돌**               | 누가 무엇을 바꿨는지 추적 불가 |
| **테스트 결과 불명확** | 어느 세션의 결과인지 모른다    |

터미널만 여러 개 여는 것은 **병렬이 아니라 혼란**입니다.

### Worktree는 Git 기능이 아니라 격리 장치다

여기서 관점의 전환이 일어납니다.

> "**Worktree가 단순히 Git 기능이 아니라 컨텍스트와 파일 시스템을 함께 격리하는 장치**로 쓰일 수 있기 때문이에요."

목표도 명확합니다.

> "그래서 **Claude 세션을 여러 개 띄우는 게 아니라, 각 세션이 자기 파일 시스템 그리고 브랜치, 작업 범위를 갖도록 격리를 해주는** 겁니다."

**"세션을 여러 개 띄운다"** 와 **"각 세션에 자기 영역을 준다"** 는 전혀 다른 이야기입니다. 전자는 개수의 문제, 후자는 **구조의 문제**입니다.

그리고 Worktree의 성격에 대해 중요한 단서가 붙습니다.

> "**Worktree는 충돌을 없애는 도구가 아니라 충돌 시점과 비용을 통제하는 도구**로 봐주시면 됩니다."

```
  ❌ 오해 : Worktree를 쓰면 충돌이 사라진다
  ⭕ 실제 : 충돌이 "작업 중 아무 때나"가 아니라 "머지 시점에" 발생하도록 미룬다
```

이 구분이 왜 중요하냐면, **충돌은 어차피 일어나기 때문**입니다. 중요한 건 그것이 **작업 도중에 뒤섞인 채로** 터지느냐, **머지라는 통제된 시점에** 터지느냐입니다.

### 격리는 세 층이다

Worktree를 컨텍스트 하네스로 쓸 때 필요한 격리는 세 가지입니다. 그리고 **각각 제공 주체가 다릅니다.**

| 격리 대상         | 무엇이 제공하나                      | 완전한가             |
|-------------------|--------------------------------------|----------------------|
| **파일 시스템**   | **Worktree**                         | ⭕ 완전              |
| **대화 컨텍스트** | **별도 Claude 세션 / 서브 에이전트** | ⭕ 완전              |
| **메모리**        | —                                    | ❌ **완전하지 않음** |

```
 ┌──────────────────────────────────────────┐
 │  세션 A          세션 B          세션 C   │  ← 대화 격리 (세션이 제공)
 ├──────────────────────────────────────────┤
 │  worktree-a     worktree-b     worktree-c │  ← 파일 격리 (worktree가 제공)
 ├──────────────────────────────────────────┤
 │        하나의 auto memory 디렉터리        │  ← 격리 안 됨 (직접 관리 필요)
 └──────────────────────────────────────────┘
```

세 번째가 이 챕터의 함정입니다.

> "**Worktree를 만들었다고 해서 Claude의 오토 메모리까지 완전히 분리되는 것은 아니라고** 보시면 됩니다."

앞의 `CLAUDE.md` 챕터에서 짚었던 그 문제입니다. Auto memory는 **같은 Git 저장소 안에서 공유**됩니다. 그래서 대응책이 필요합니다.

| 메모리 종류                      | 관리 방법                           |
|----------------------------------|-------------------------------------|
| **Worktree별 `CLAUDE.local.md`** | 각 워크트리에서 **명시적으로 관리** |
| **Auto memory**                  | 공유된다는 전제로 **구분해서 다룸** |

즉 파일과 대화는 **저절로** 나뉘지만, 메모리는 **의도적으로** 나눠야 합니다.

### 핵심 명령어

실행은 의외로 간단합니다.

```bash
claude --worktree
```

이 한 줄로 다음이 일어납니다.

| 자동으로 되는 것              |
|-------------------------------|
| **Worktree 이름 생성**        |
| **독립 브랜치에서 세션 시작** |

그리고 각 워크트리는 **독립된 터미널 세션**에서 병렬로 실행됩니다.

기준점 확인과 정리에 쓰이는 명령들도 함께 알아 둡니다.

```bash
# 현재 상태 확인
git status

# 로컬 origin HEAD 재동기화 — 기준점 확인
git remote set-head origin -a

# 다 쓴 워크트리 제거
git worktree remove <경로>
```

생성된 워크트리 경로는 **`.gitignore`에 추가**해 두는 것이 좋습니다. 작업용 디렉터리가 저장소 추적 대상에 들어가면 곤란하니까요.

### 병렬 작업 예시

강의에서 든 구성입니다. **기능 단위로 워크트리를 나눕니다.**

```
  main worktree      ← 기준. 여기서 최종 머지
      │
      ├── auth-validate    ← 세션 1: 인증 검증 로직
      └── auth-errors      ← 세션 2: 인증 에러 처리
```

같은 인증 영역이지만 **책임이 다른 작업**이라 나눌 가치가 있습니다. 앞 시리즈에서 본 원칙 — **"역할이 겹치면 만들지 않고, 분명할 때만 만든다"** — 이 워크트리에도 그대로 적용됩니다.

### 진짜 중요한 건 마지막 병합이다

이 챕터에서 가장 실무적인 지적입니다.

> **Worktree 생성 자체보다 중요한 것은 마지막 병합 작업입니다.**

병렬로 벌려 놓는 건 쉽습니다. 문제는 **다시 하나로 모으는 것**이죠.

| 각 워크트리의 책임 | 메인 워크트리의 책임 |
|--------------------|----------------------|
| **자체 diff**      | **순차적 merge**     |
| **자체 테스트**    |                      |

```
  auth-validate  →  자기 diff·테스트 책임
  auth-errors    →  자기 diff·테스트 책임
        ↓
  main worktree  →  하나씩 순차적으로 merge
```

**순차적**이라는 조건이 중요합니다. 한꺼번에 몰아서 머지하면 어느 변경이 문제를 일으켰는지 특정할 수 없습니다. 앞 시리즈 Verification Harness의 **"되돌릴 지점이 촘촘한 히스토리"** 와 같은
원리입니다.

### 충돌이 나면 바로 고치게 하지 마라

병합 과정에서 충돌은 필연입니다. 그때의 대응이 이 챕터의 하이라이트입니다.

> "**충돌이 생기면 Claude에게 바로 해결시키지 말고 먼저 원인 분석과 merge 계획을 요구해야** 합니다."

왜일까요. 바로 시키면 **기계적인 덮어쓰기**가 나오기 때문입니다. 양쪽 변경의 의도를 이해하지 않은 채 한쪽을 취하면, 컴파일은 되는데 로직이 사라진 코드가 남습니다.

그래서 순서를 지킵니다.

```
  1. 원인 분석   →  왜 충돌했는가
  2. 병합 계획   →  어떻게 합칠 것인가
  3. 수정        →  계획대로 반영
  4. 테스트      →  실제로 맞는지 확인
```

충돌 해결 프롬프트는 이런 형태가 됩니다.

```
[충돌 해결 요청]

  1. 이 충돌이 왜 발생했는지 원인을 설명해 줘
  2. 양쪽 변경이 각각 어떤 논리 영역을 수정했는지 설명해 줘
  3. 병합 계획을 먼저 제시해 줘
  4. 계획에 동의하면 그때 수정하고 테스트까지 진행해 줘
```

2번 항목이 특히 좋습니다. **"어떤 논리 영역을 수정했는지"** 를 물으면, 두 변경이 실제로 같은 의도를 건드린 것인지 아니면 우연히 같은 줄에 놓인 것인지가 드러납니다. 같은 줄이라고 같은 관심사는
아니니까요.

이건 앞 챕터의 **"수정하지 말고 계획만 줘"** 와 정확히 같은 기술입니다. 위험한 구간일수록 **실행 전에 계획을 받아 검토**합니다.

### 병렬 작업 체크리스트

강의는 마지막으로 단계별 체크리스트를 제시합니다.

| 시점        | 확인할 것                                                                 |
|-------------|---------------------------------------------------------------------------|
| **시작 전** | 작업 경계가 겹치지 않는가 / 워크트리 브랜치 기준점이 맞는가               |
| **진행 중** | 각 워크트리가 자기 diff와 테스트를 책임지고 있는가                        |
| **완료 후** | 순차적으로 머지했는가 / 충돌은 계획 후 해결했는가 / 워크트리를 정리했는가 |

```
  시작 전  :  경계를 나눈다
  진행 중  :  각자 책임진다
  완료 후  :  순서대로 합치고 치운다
```

### 정리

1. **같은 디렉터리에서 세션을 여러 개 띄우면 병렬이 아니라 혼란이다.** 파일이 섞이고 테스트 결과의 주인이 사라진다.
2. **Worktree는 Git 기능이 아니라 컨텍스트·파일 시스템을 함께 격리하는 장치다.** 세션 개수가 아니라 **각 세션에 자기 영역을 주는 것**이 핵심이다.
3. **Worktree는 충돌을 없애지 않는다.** 충돌의 **시점과 비용을 통제**할 뿐이다.
4. **격리는 세 층이고, 메모리만 자동으로 안 된다.** 파일은 Worktree가, 대화는 세션이 나눠 주지만 **Auto memory는 공유된다.** `CLAUDE.local.md`로 명시 관리한다.
5. **`claude --worktree` 한 줄로 시작한다.** 이름과 브랜치는 자동 생성되고, 끝나면 `git worktree remove`로 정리한다.
6. **생성보다 병합이 중요하다.** 각 워크트리가 자기 diff·테스트를 책임지고, 메인에서 **순차적으로** 머지한다.
7. **충돌은 바로 고치게 하지 마라.** `원인 분석 → 병합 계획 → 수정 → 테스트` 순서를 지켜야 기계적 덮어쓰기를 피한다.
