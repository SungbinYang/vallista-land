## 하네스 엔지니어링이란?

이 시리즈의 첫 챕터는 **개념을 다시 정의하는 것**에서 시작합니다. 우리가 흔히 "Claude Code를 잘 쓴다"고 말할 때 떠올리는 이미지는 대개 **프롬프트를 잘 쓰는 것**입니다. 하지만 강사
**미국달팽이**님은 출발점 자체를 다르게 잡습니다.

> "클로드 코드를 AI가 실제 개발 작업을 수행할 수 있도록 둘러싼 **작업 시스템**으로 알아봐 주시면 됩니다."

즉 Claude Code는 "똑똑한 채팅 상대"가 아니라 **작업을 수행하는 시스템**이고, 그 시스템을 설계하는 일이 바로 **하네스 엔지니어링 (Harness Engineering)** 입니다.

### 채팅창의 Claude와 CLI의 Claude Code는 다르다

먼저 이 구분이 전제되어야 합니다. 둘은 같은 모델을 쓰지만, **결과가 세상에 미치는 영향**이 완전히 다릅니다.

| 구분            | 채팅창의 Claude              | CLI의 Claude Code                     |
|-----------------|------------------------------|---------------------------------------|
| **하는 일**     | 답변 텍스트를 생성           | **파일을 직접 수정하고 명령을 실행**  |
| **실패의 결과** | 답이 틀림 → 다시 물어보면 됨 | **코드가 망가짐 / 브랜치가 더러워짐** |
| **필요한 것**   | 좋은 질문                    | **좋은 질문 + 실행 경계**             |

채팅창에서는 모델이 헛소리를 해도 비용이 "내 시간 조금"입니다. 그런데 CLI에서는 모델의 판단이 **실제 파일 시스템과 셸에 반영**됩니다. 그래서 CLI에서는 답의 품질만큼이나 **"어디까지 실행해도
되는가"** 가 중요해집니다.

### Claude Code의 핵심 루프는 놀랄 만큼 단순하다

강의에서 가장 인상적인 지점은 여기입니다. Claude Code의 중심에 있는 루프는 사실 **아주 단순한 반복**입니다.

```
 ┌──────────────────────────────────────────────┐
 │                                              │
 │   1. 모델(Claude)을 호출한다                 │
 │            ↓                                 │
 │   2. 모델이 "이 도구를 써 줘"라고 요청한다   │
 │            ↓                                 │
 │   3. 하네스가 그 도구를 실제로 실행한다      │
 │            ↓                                 │
 │   4. 실행 결과를 다시 모델에게 돌려준다      │
 │            ↓                                 │
 │   (반복)                                     │
 └──────────────────────────────────────────────┘
```

`호출 → 도구 요청 → 실행 → 결과 반환`. 이게 전부입니다. 겉으로 보기엔 굉장히 지능적인 시스템처럼 보이지만, 루프 자체는 이렇게 심심합니다.

그렇다면 그 "지능적으로 보이는 느낌"은 어디서 나오는 걸까요?

> "모델 자체보다 **모델 주변에 있는 실행구조**예요. 이 구조가 바로 **하네스**예요."

**모델은 판단을 하고, 하네스는 그 판단을 실행할지 말지 결정합니다.** 그리고 실무 품질을 좌우하는 쪽은 대개 후자입니다.

### 모델은 작고, 하네스는 크다

Claude Code를 한 문장으로 정의하면 **"셸 커맨드 실행과 파일 에디트를 호출할 수 있는 에이전틱 코딩 도구"** 입니다. 그런데 이 도구의 코드 대부분은 "모델 호출"이 아니라 **모델 주변을 감싸는 운영
구조 (Operational Harness)** 입니다.

| 하네스 구성 요소                    | 하는 일                               |
|-------------------------------------|---------------------------------------|
| **Permission System**               | 이 명령을 실행해도 되는지 판단·차단   |
| **Tool Routing**                    | 어떤 도구를 어떤 형태로 노출할지 결정 |
| **Context Management / Compaction** | 컨텍스트를 채우고, 넘치면 압축        |
| **Hooks**                           | 실행 전후에 규칙을 강제               |
| **Skills**                          | 반복 절차를 재사용 가능한 형태로 고정 |
| **MCP**                             | 외부 시스템과의 연결 지점             |
| **Sub-agent Delegation**            | 작업을 분리해 별도 세션에 위임        |
| **Session Persistence**             | 세션을 저장·복원해 작업을 이어가게 함 |

그림으로 보면 이렇게 포개집니다.

```
┌────────────────────────────────────────────────┐
│                  H A R N E S S                 │
│   permission · context · hooks · skills · MCP  │
│   sub-agent · session persistence · routing    │
│                                                │
│        ┌──────────────────────────────┐        │
│        │      핵심 루프 (Model)       │        │
│        │  호출 → 도구요청 → 결과반환  │        │
│        └──────────────────────────────┘        │
│                                                │
└────────────────────────────────────────────────┘
     ↑ 실무 품질을 결정하는 건 대부분 바깥쪽
```

여기서 이 강의 전체를 관통하는 주장이 나옵니다. **모델의 성능만큼이나, 아니 실무에서는 그 이상으로, 하네스의 품질이 Claude Code의 결과 품질을 결정합니다.**

### 그래서 하네스 엔지니어링이란

강의에서 내리는 정의는 명확합니다.

> **Harness Engineering은 AI 모델이 실제 작업을 안전하게 수행할 수 있도록 주변 실행 구조를 설계하는 일이다.**

핵심은 **"모델을 더 똑똑하게 만드는 일이 아니다"** 라는 부정형에 있습니다. 우리가 할 수 있는 일은 모델의 가중치를 바꾸는 게 아니라, **모델이 무엇을 보고 무엇을 할 수 있는지를 설계하는 것**입니다.

| 하네스 엔지니어링이 **아닌** 것 | 하네스 엔지니어링**인** 것               |
|---------------------------------|------------------------------------------|
| 모델을 더 똑똑하게 만드는 것    | **모델 주변의 실행 구조를 설계**하는 것  |
| 프롬프트 문구를 다듬는 것       | 모델이 **볼 정보와 할 행동**을 정하는 것 |
| 더 좋은 모델을 기다리는 것      | 지금 모델을 **안전하게 굴리는 것**       |

### "모델이 멍청해서"가 아니라 "하네스가 약해서"

실무에서 Claude Code를 쓰다 보면 반드시 마주치는 증상들이 있습니다. 엉뚱한 파일을 고치고, 위험한 명령을 실행하려 하고, 멀쩡하던 테스트가 깨지고, 여러 세션을 돌리다 머지 컨플릭트가 터집니다.

이때 우리는 보통 "모델이 오늘따라 이상하네"라고 생각합니다. 강사는 그 해석을 정면으로 반박합니다.

> "클로드 코드가 **엉뚱한 파일을 고치는 문제**는 단순히 모델이 멍청해서가 아니라 **컨텍스트 하네스가 약하기 때문**일 수도 있고요."

문제의 원인을 모델이 아니라 **하네스의 약한 지점**으로 옮겨 보면, 증상마다 손볼 곳이 달라집니다. 이 매핑이 이 섹션 전체의 뼈대입니다.

| 증상                                           | 의심해야 할 하네스               |
|------------------------------------------------|----------------------------------|
| 엉뚱한 파일을 고친다 / 맥락을 잃는다           | **Context Harness**              |
| 위험한 명령을 실행하려 한다 / `.env`를 읽는다  | **Permission Harness**           |
| "다 됐습니다" 했는데 테스트가 깨진다           | **Verification Harness**         |
| 반복 작업을 매번 다르게 한다 / 도구가 뒤엉킨다 | **Tool Harness**                 |
| 여러 세션에서 머지 컨플릭트가 난다             | **Sub-Agent & Worktree Harness** |
| 재현 안 되는 버그 앞에서 헤맨다                | **Debugging Harness**            |

즉 **"뭐가 문제인지 모르겠다"의 실체는 대부분 "어느 하네스가 비어 있는지 모른다"** 입니다.

### 자율성은 공짜가 아니다

AI 에이전트 이야기를 하다 보면 자연스럽게 따라붙는 통념이 있습니다. "에이전트는 자율적으로 많이 움직일수록 좋다"는 것이죠.

> "AI Agent는 **자율적으로 많이 움직일수록 좋다**, 라는 생각이 있는데, 처음에는 그럴듯해 보일 수 있어요."

"처음에는"이라는 단서가 핵심입니다. 자율성이 커질수록 **성공했을 때의 이득**만 커지는 게 아니라 **실패했을 때의 비용**도 함께 커지기 때문입니다.

실무에서 이 실패 비용은 아주 구체적인 모습으로 나타납니다.

- 관련 없는 **잘못된 파일을 수정**한다
- `.env`, Secret 파일을 **읽으려 시도**한다
- 시키지도 않은 **광범위한 리팩터링**을 한다
- **Git 브랜치를 지저분하게** 만들어 놓는다

하나같이 "데모에서는 안 보이다가 실제 프로젝트에서 터지는" 종류의 문제입니다.

### 목표는 무한 자율성이 아니라 검증 가능한 경계

그래서 좋은 하네스가 겨냥하는 지점은 자율성의 **최대화**가 아닙니다.

> "좋은 Harness Engineering의 목적은 **AI에게 무한 자율성을 주는 것이 아니라, 적절한 자율성을 검증 가능한 Boundary 안에, 경계 안에 넣어주는 것**이에요."

```
   자율성 없음              적절한 자율성 + 경계             무한 자율성
 ┌──────────────┐        ┌──────────────────────┐        ┌──────────────┐
 │ 매번 내가 다 │        │  스스로 움직이되      │        │ 알아서 다 하고│
 │ 확인해야 함  │  ←──   │  경계를 넘으면 멈춤   │   ──→  │ 사고도 알아서 │
 │ (느림)       │        │  결과는 검증 가능     │        │ (복구 불가)   │
 └──────────────┘        └──────────────────────┘        └──────────────┘
                              ↑ 하네스가 노리는 지점
```

여기서 **"검증 가능한 (verifiable)"** 이라는 수식어가 중요합니다. 경계를 긋는 것만으로는 부족하고, 그 경계 안에서 나온 결과가 **맞는지 확인할 수 있어야** 비로소 자율성을 맡길 수 있습니다.

### 하네스 엔지니어링은 결국 질문의 목록이다

이 챕터를 실무 체크리스트로 압축하면, 하네스 엔지니어링은 다음 질문들에 답을 만들어 두는 작업입니다.

| 영역           | 던져야 할 질문                                                                                        |
|----------------|-------------------------------------------------------------------------------------------------------|
| **컨텍스트**   | Claude가 **반드시 알아야 하는 정보**는 무엇인가?                                                      |
| **권한(금지)** | **절대 보면 안 되는 파일**은 무엇인가?                                                                |
| **권한(허용)** | **자유롭게 실행해도 되는 명령**은 무엇인가?                                                           |
| **권한(확인)** | 실행 전에 **반드시 물어봐야 하는 명령**은 무엇인가?                                                   |
| **검증**       | **어떤 테스트가 통과해야** 완료로 볼 수 있는가?                                                       |
| **정지 조건**  | 수정 범위가 예상보다 넓어졌을 때 **어디서 멈춰야** 하는가?                                            |
| **분리**       | 어떤 작업을 **서브 에이전트**로 빼고, 어떤 작업을 메인 세션에서 할 것인가?                            |
| **도구**       | 어떤 반복 작업을 **Skill**로, 어떤 외부 연결을 **MCP**로, 어떤 실행 규칙을 **Hooks**로 강제할 것인가? |

프롬프트 엔지니어링이 **"어떻게 말해야 좋은 답이 나올까"** 를 묻는다면, 하네스 엔지니어링은 **"무엇을 보게 하고, 무엇을 못 하게 하고, 어떻게 확인할까"** 를 묻습니다. 질문의 층위 자체가 다릅니다.

### 이 섹션에서 다룰 6가지 하네스

앞의 질문들을 실제 설계 단위로 묶은 것이 이 섹션의 **6가지 하네스**입니다. Claude Code를 실무 워크플로우에 넣을 때 **반드시 설계해야 하는 항목들**이라고 이해하면 됩니다.

| # | 하네스                           | 설계하는 대상                                         |
|---|----------------------------------|-------------------------------------------------------|
| 1 | **Context Harness**              | Claude가 **무엇을 보는가**                            |
| 2 | **Permission Harness**           | Claude가 **무엇을 할 수 있는가 / 없는가**             |
| 3 | **Verification Harness**         | 결과를 **무엇으로 완료라고 판정하는가**               |
| 4 | **Tool Harness**                 | Built-in Tools · Skills · MCP · Hooks의 **역할 분담** |
| 5 | **Sub-Agent & Worktree Harness** | 작업의 **분리와 격리**                                |
| 6 | **Debugging Harness**            | 재현 어려운 문제를 **풀 수 있는 형태로 만들기**       |

이 여섯 개는 서로 독립적인 기능 목록이 아니라, **하나의 작업 시스템을 여섯 방향에서 자르는 단면**에 가깝습니다. 컨텍스트가 좋아도 권한이 열려 있으면 사고가 나고, 권한을 잠가도 검증이 없으면 "다 됐다"는
말을 믿을 수 없습니다.

### 좋은 시스템의 기준: Safe · Reviewable · Recoverable

이 여섯 하네스를 갖추면 무엇이 달라지느냐. 강의는 세 단어로 정리합니다.

| 기준            | 의미                                             |
|-----------------|--------------------------------------------------|
| **Safe**        | 위험한 행동을 **애초에 못 하게** 한다            |
| **Reviewable**  | 무엇을 했는지 **diff와 테스트로 검토**할 수 있다 |
| **Recoverable** | 잘못됐을 때 **되돌릴 수 있다**                   |

그리고 여기서 "좋은 시스템"의 기준이 다시 정의됩니다.

> 좋은 시스템은 **한 번 데모가 잘 되는 것**이 아니라, 실수했을 때 **멈출 수도 있고, 검증할 수도 있고, 되돌릴 수도 있으며, 팀이 같은 기준으로 반복**할 수 있어야 한다.

마지막의 **"팀이 같은 기준으로 반복"** 이 특히 중요합니다. 하네스는 개인의 노하우가 아니라 **파일로 고정되어 저장소에 커밋되는 것**이기 때문입니다. `CLAUDE.md`, 권한 설정, Hooks,
Skill — 이것들은 전부 팀이 공유할 수 있는 형태를 가집니다. 개인의 감각을 팀의 규칙으로 승격시킬 수 있다는 뜻이죠.

### 정리

이 챕터에서 챙겨야 할 것은 딱 세 가지입니다.

1. **Claude Code의 핵심 루프는 단순하다.** 지능적으로 보이게 만드는 건 모델이 아니라 그 주변을 감싼 **하네스**다.
2. **문제의 원인을 모델에서 하네스로 옮겨 보라.** "엉뚱한 파일을 고친다"는 모델의 지능 문제가 아니라 **컨텍스트 하네스의 설계 문제**일 수 있다.
3. **목표는 무한 자율성이 아니라 검증 가능한 경계다.** Safe · Reviewable · Recoverable 한 시스템을 만드는 것이 하네스 엔지니어링의 종착점이다.

> "Claude Code를 잘 쓴다"는 말의 의미는 결국 **좋은 Context를 만들고, 실행 가능한 Tool Surface를 제한하고, 위험한 행동을 Permission으로 막고, 결과를 검증하는** 시스템
> 전반을
> 설계한다는 뜻입니다.

다음 챕터에서는 이 하네스가 Claude Code 안에서 **실제로 어떤 구조로 배치되어 있는지**를 들여다봅니다.

## Claude Code 클로드 코드의 하네스 구조

앞 챕터에서 "하네스가 중요하다"는 결론까지 왔습니다. 그렇다면 이제 그 하네스가 **Claude Code 안에서 실제로 어떻게 배치되어 있는지**를 봐야 합니다. 강사 **미국달팽이**님도 순서를 이렇게 잡습니다.

> "Harness 엔지니어링을 위해서는 **Harness 구조를 먼저 이해**를 해야 되는데요."

구조를 모르면 문제가 생겼을 때 **어디를 손봐야 할지**를 알 수 없기 때문입니다.

### 답변 시스템과 작업 시스템의 차이

Claude Code CLI는 채팅형 Claude와 무엇이 다를까요. 표면적으로는 "터미널에서 쓰는 Claude"입니다. 하지만 강사는 그 표면적 해석을 명확히 부정합니다.

> "이 차이는 **UI 차이가 아니라** 단순한 차이가 아니죠. 그래서 **답변 시스템과 작업 시스템의 차이**를 알아야 됩니다."

| 구분          | 답변 시스템 (채팅형 Claude) | 작업 시스템 (Claude Code CLI)                   |
|---------------|-----------------------------|-------------------------------------------------|
| **출력물**    | 텍스트                      | **파일 변경 · 명령 실행 결과**                  |
| **접근 범위** | 대화창 안                   | **프로젝트 폴더 · 셸**                          |
| **하는 일**   | 답을 만든다                 | 파일을 읽고, 코드를 고치고, **테스트를 돌린다** |
| **필요한 것** | 좋은 프롬프트               | **좋은 프롬프트 + 실행 구조(하네스)**           |

같은 모델이라도 "답을 만드는 시스템"과 "작업을 수행하는 시스템"은 요구되는 설계가 다릅니다. 후자에는 **실행을 중개하고 통제하는 층**이 반드시 필요합니다.

### Claude Code를 구성하는 7가지 요소

강의에서는 Claude Code를 **7개의 구성 요소**로 분해합니다. 사용자의 요청이 결과로 바뀌기까지의 경로를 그대로 따라가면 이렇습니다.

| # | 구성 요소                  | 역할                                                |
|---|----------------------------|-----------------------------------------------------|
| 1 | **User Input / Interface** | 사용자의 프롬프트와 태스크가 들어오는 입구          |
| 2 | **Agent Loop**             | 전체 흐름을 돌리는 중앙 루프                        |
| 3 | **Context Assembly**       | 모델에게 넘길 컨텍스트를 **조립**                   |
| 4 | **Model**                  | 조립된 컨텍스트를 보고 **판단**하고 Tool use를 요청 |
| 5 | **Permission**             | 그 요청을 **승인할지 차단할지** 결정                |
| 6 | **Tools**                  | 승인된 도구가 실제로 **호출**됨                     |
| 7 | **Execution**              | 실행이 일어나고 **결과가 Agent Loop로 회귀**        |
| + | **State & Persistence**    | 위 전 과정을 **기록·유지**하는 별도 레이어          |

흐름으로 그리면 이렇습니다.

```
 [1] User Input / Interface
          |
          v
 [2] Agent Loop  <--------------------+
          |                           |
          v                           |
 [3] Context Assembly                 |
          |                           |
          v                           |
 [4] Model  --- "이 도구 써 줘" ---+   |
                                   |   |
                                   v   |
                        [5] Permission |
                                   |   |
                          (승인)   v   |
                             [6] Tools |
                                   |   |
                                   v   |
                          [7] Execution|
                                   |   |
                                   +---+
                                  (결과 반영)

 ─────────────────────────────────────────
 [+] State & Persistence Layer (전 구간 기록)
     Session Transcript / Memory /
     Compact Boundary / Sub-Agent / Sidechain
```

여기서 놓치기 쉬운 것이 **State & Persistence 레이어**입니다. 이 레이어는 흐름에 끼어들지 않지만, 다음 것들을 계속 유지합니다.

| 항목                   | 유지하는 것                         |
|------------------------|-------------------------------------|
| **Session Transcript** | 이번 세션에서 오간 기록             |
| **Memory**             | 세션을 넘어 남는 기억               |
| **Compact Boundary**   | 컨텍스트를 압축한 **경계 지점**     |
| **Sub-Agent**          | 분리해서 돌린 별도 에이전트의 작업  |
| **Sidechain**          | 본 흐름에서 갈라져 나간 곁가지 기록 |

세션이 오래갈수록 결과가 이상해지는 현상은 대개 **이 레이어에 쌓인 것들** 때문입니다. 구조상 어디에 무엇이 쌓이는지를 알아야 "세션 오염"을 진단할 수 있습니다.

### 한 번 하고 끝나는 게 아니라, 반복한다

이 7단계에서 가장 중요한 성질은 **선형이 아니라 순환**이라는 점입니다.

> "이 구조를 보면 Claude Code는 한번 다 파고 끝나는 게 아니라 **관찰, 판단, 그리고 실행, 그리고 결과를 반영**하고요. 그 결과를 바탕으로 **다시 재판단**을 합니다. **이걸 반복하는
시스템**이라고
> 보시면 돼요."

```
 관찰(Observe) → 판단(Decide) → 실행(Act) → 결과 반영(Reflect) → 재판단
      ^                                                             |
      +-------------------------------------------------------------+
```

이 순환 구조가 하네스 엔지니어링에서 갖는 의미는 큽니다. **한 사이클의 오염이 다음 사이클의 입력이 되기 때문**입니다. 초반에 엉뚱한 파일을 읽으면, 그 내용이 컨텍스트에 남아 다음 판단까지 흔듭니다. 그래서
하네스는 "마지막에 결과를 검사하는 장치"가 아니라 **루프의 매 지점에 개입하는 장치**여야 합니다.

### 하네스는 모델과 실행 환경 사이에 있다

이제 하네스의 정확한 **위치**를 짚습니다. 하네스는 모델 안에도, 운영체제 안에도 없습니다. **모델과 실행 환경 사이**에 있습니다.

```
 ┌─────────┐        ┌──────────────────────┐        ┌──────────────┐
 │  Model  │  ───>  │       HARNESS        │  ───>  │   실행 환경  │
 │ (판단)  │        │  permission 확인      │        │  파일시스템  │
 │         │  <───  │  hook / sandbox      │  <───  │  셸 / 네트워크│
 └─────────┘        │  deny rule 적용       │        └──────────────┘
                    └──────────────────────┘
     요청                   중개·통제                   실제 자원
```

모델이 "이 파일을 읽겠다", "이 명령을 실행하겠다"고 **요청**하면, 하네스가 그 요청을 받아 다음을 수행합니다.

1. **Tool request 수신** — 모델의 요청을 받는다
2. **Permission 확인** — 이 행동이 허용되는지 판단한다
3. **Hook / Sandbox / Deny rule 적용** — 실행 전 규칙을 강제하고 격리한다
4. **실행** — 통과한 것만 실제로 수행한다
5. **결과 반환** — 실행 결과를 모델에게 돌려준다

이 분리가 왜 중요할까요. **모델이 파일 시스템에 직접 손대지 못하게 하기 위해서**입니다. 모델은 "요청"까지만 할 수 있고, "실행"은 언제나 하네스를 거칩니다.

> "하네스는 **모델의 자율성을 실행 가능한 형태로 바꾸면서도, 자율성을 통제 가능한 바운더리 안에, 경계 안에 둬야** 됩니다."

앞 챕터의 "검증 가능한 경계"가 여기서 **아키텍처로 구현된 모습**입니다. 경계는 추상적인 원칙이 아니라 **모델과 실행 환경 사이에 실재하는 층**입니다.

### 실무 품질 = 모델 성능 × 하네스 품질

이 챕터에서 가장 기억할 문장은 이것입니다.

> "따라서 Claude Code의 **실무 품질은 모델 성능과 하네스 품질의 곱**에 가깝다는 겁니다. 모델이 좋아도 **하네스가 약하면 결과는 불안정**하죠."

**합 (+)이 아니라 곱 (×)** 이라는 점이 핵심입니다. 합이라면 한쪽이 0이어도 다른 쪽으로 메울 수 있지만, 곱은 **한쪽이 0에 가까우면 전체가 0에 수렴**합니다.

| 모델 성능 | 하네스 품질 | 실무 결과                               |
|-----------|-------------|-----------------------------------------|
| 높음      | 높음        | **안정적으로 반복 가능**                |
| 높음      | **낮음**    | 잘될 때는 놀랍지만 **언제 터질지 모름** |
| 낮음      | 높음        | 느리지만 **사고는 나지 않음**           |
| 낮음      | 낮음        | 말할 것도 없음                          |

모델이 아무리 좋아도 다음 중 하나라도 무너지면 결과는 흔들립니다.

- **컨텍스트 흐름이 좋지 않다** → 엉뚱한 판단의 재료가 들어간다
- **퍼미션이 느슨하다** → 하지 말아야 할 행동이 그대로 나간다
- **Verification 하네스가 없다** → **틀린 수정안을 확신 있게** 내놓는다
- **세션이 오염됐다** → 뒤로 갈수록 판단이 무너진다

세 번째 항목이 특히 무섭습니다. 검증 장치가 없으면 모델은 틀렸다는 사실 자체를 모른 채 **자신 있게 완료를 선언**합니다.

### 프롬프트가 아니라 설정과 정책으로 굴러가는 시스템

그래서 Claude Code는 애초에 **프롬프트 한 방으로 제어하는 도구로 설계되지 않았습니다.**

> "즉 Claude Code는 애초에 **프롬프트 하나 잘 쓴다고 해서 되는 게 아니라**, 프로젝트와 팀 단위로 동작을 조정할 수 있는 **설정과 정책 기반으로 돌아가는 시스템**으로 설계되어 있다, 라고 아시면
> 됩니다."

실제로 하네스를 조정하는 손잡이는 **파일**입니다.

| 파일                | 조정하는 것                                                         |
|---------------------|---------------------------------------------------------------------|
| **`settings.json`** | `permissions` (허용·차단), `environmentVariables`, `hooks`, `model` |
| **`CLAUDE.md`**     | 시작 시 주입되는 **초기 컨텍스트와 인스트럭션**                     |

```
CLAUDE.md      →  Claude가 "무엇을 알고 시작하는가"
settings.json  →  Claude가 "무엇을 할 수 있는가"
```

이 둘이 파일이라는 사실이 중요합니다. **파일이므로 저장소에 커밋되고, 커밋되므로 팀이 공유하며, 공유되므로 같은 기준으로 반복**됩니다. 앞 챕터에서 말한 "개인의 감각을 팀의 규칙으로 승격"이 가능한 이유가
여기 있습니다.

### 문제가 생기면 어느 하네스를 볼 것인가

구조를 이해했다면, 이제 증상을 구조 위의 좌표로 옮길 수 있습니다. 이 매핑이 이 챕터의 **실용적인 결론**입니다.

| 실제로 겪는 증상                   | 점검할 하네스                    | 손댈 지점                        |
|------------------------------------|----------------------------------|----------------------------------|
| **관련 없는 파일을 건드렸다**      | **Context Harness**              | `CLAUDE.md`, 컨텍스트 조립 범위  |
| **위험한 명령을 실행하려 한다**    | **Permission Harness**           | `settings.json`의 `permissions`  |
| **수정만 하고 검증이 없다**        | **Verification Harness**         | 테스트·diff 등 완료 판정 기준    |
| **MCP나 Hooks에서 오류가 난다**    | **Tool Harness**                 | 도구·Skill·MCP·Hooks의 역할 분담 |
| **병렬 작업이 서로 충돌한다**      | **Sub-Agent & Worktree Harness** | 작업 분리와 격리 방식            |
| **로그만 봐서는 원인을 못 찾겠다** | **Debugging Harness**            | 증상·증거·검증 경로의 구조화     |

증상을 모델 탓으로 돌리면 할 수 있는 일이 "더 좋은 모델 기다리기"밖에 없습니다. 반면 증상을 **하네스 좌표로 번역**하면 **오늘 당장 고칠 파일**이 나옵니다. 강사가 "Claude Code 사용은
**시스템 설계에 가깝다**"고 말하는 이유입니다.

### 정리

1. **Claude Code는 답변 시스템이 아니라 작업 시스템이다.** 채팅형 Claude와의 차이는 UI가 아니라 **실행 능력**에 있다.
2. **7개 구성 요소는 순환한다.** `Input → Agent Loop → Context → Model → Permission → Tools → Execution → 다시 Agent Loop`, 그리고 그 전
   구간을 **State & Persistence**가 기록한다.
3. **하네스는 모델과 실행 환경 사이의 중개층이다.** 모델은 요청만 하고, 실행은 언제나 권한·훅·샌드박스를 거친다.
4. **실무 품질은 모델 성능 × 하네스 품질이다.** 곱이므로 한쪽이 약하면 전체가 무너진다.
5. **조정 수단은 프롬프트가 아니라 파일이다.** `CLAUDE.md`는 아는 것을, `settings.json`은 할 수 있는 것을 정한다.

다음 챕터부터는 6가지 하네스를 하나씩 파고듭니다. 첫 순서는 **Context Harness** — Claude가 길을 잃지 않게 만드는 설계입니다.

## Context Harness 컨텍스트 하네스 설계 - Claude가 길을 잃지 않게 만드는 하네스 엔지니어링

6가지 하네스 중 첫 번째는 **Context Harness**입니다. 이름 그대로 Claude가 **무엇을 보는가**를 설계하는 일이고, 강사 **미국달팽이**님은 그 목적을 이렇게 표현합니다.

> "Claude가 **목적의식을 잃지 않게** 만들어주는 하네스 엔지니어링이에요."

핵심 목표는 한 문장으로 정리됩니다. **필요한 정보는 충분히 보게 하고, 필요 없는 정보는 보지 않게 하는 것.**

### 문제는 "정보 부족"이 아니라 "작업면이 흐려진 것"

큰 코드베이스에서 Claude가 엉뚱한 파일을 건드릴 때, 우리는 보통 두 가지 중 하나를 의심합니다. "모델이 멍청한가?" 아니면 "내가 설명을 덜 했나?" 강사는 둘 다 아닐 수 있다고 말합니다.

> "Claude가 보는 **작업면이 흐려진** 겁니다. **너무 적은 정보를 줘도 문제지만, 너무 많은 정보를 주는 것도 문제**예요."

그리고 실무에서는 오히려 후자가 더 흔합니다.

> "큰 코드베이스에서는 **컨텍스트 부족보다 컨텍스트 과잉이 더 자주 문제**를 만드는 경우도 있습니다."

컨텍스트 과잉 (Context Overload)은 이런 것들이 한 화면에 섞여 있는 상태입니다.

- **관련 없는 파일**
- **오래된 대화**
- **이미 틀린 것으로 판명된 가설**
- **길기만 한 로그**
- **애매한 요구사항**

이 상태에서 모델은 판단을 멈추지 않습니다. 재료가 흐려도 **그럴듯한 결론**을 만들어 냅니다. 그래서 결과가 "명백히 틀린 답"이 아니라 **"그럴듯하지만 잘못된 방향"** 으로 나옵니다. 이게 더 잡아내기
어렵습니다.

```
 정보 부족                     적절한 작업면                  컨텍스트 과잉
 ┌────────────┐              ┌────────────┐              ┌────────────┐
 │ 근거 없이  │              │ 관련 있는  │              │ 관련·무관  │
 │ 추측한다   │   <───       │ 것만 선명  │       ───>   │ 전부 뒤섞임│
 │            │              │            │              │ 정교한 오답│
 └────────────┘              └────────────┘              └────────────┘
                        ↑ Context Harness가 노리는 지점
```

### Claude Code의 메모리: FreshContext, CLAUDE.md, Auto Memory

Context Harness를 설계하려면 먼저 **Claude Code가 컨텍스트를 어떻게 얻는지**를 알아야 합니다. 공식 메모리 문서가 설명하는 구조는 이렇습니다.

각 세션은 **`FreshContext` 윈도우로 시작**합니다. 즉 기본값은 "아무것도 기억하지 못한 상태"입니다. 그 위에 세션을 넘어 지식을 실어 나르는 메커니즘이 두 가지 붙습니다.

| 메커니즘        | 누가 쓰는가       | 성격                               |
|-----------------|-------------------|------------------------------------|
| **`CLAUDE.md`** | **사용자가 작성** | 프로젝트·팀 규칙을 명시적으로 고정 |
| **Auto Memory** | **Claude가 작성** | 작업하며 스스로 남기는 기억        |

그런데 여기에 **반드시 짚고 넘어가야 할 함정**이 있습니다.

> `CLAUDE.md`와 Auto Memory는 **강제 설정이 아니라 Claude에게 제공되는 컨텍스트**입니다.

즉 `CLAUDE.md`에 "`.env`를 절대 읽지 마"라고 써 두는 것은 **부탁이지 차단이 아닙니다.** 모델이 참고할 재료일 뿐이므로, 컨텍스트가 길어지거나 압축되면 흐려질 수 있습니다.

| 성격                    | 어디에 둬야 하는가                       |
|-------------------------|------------------------------------------|
| **알려주고 싶은 것**    | `CLAUDE.md` (컨텍스트)                   |
| **반드시 막아야 할 것** | **`Permissions`, `Hooks`** (실행 하네스) |

이 구분이 흐려지면 "분명 CLAUDE.md에 쓰라고 했는데 왜 안 지키지?"라는 상황이 반복됩니다. **막아야 하는 것은 컨텍스트가 아니라 실행 층에서 막아야 합니다.**

### 컨텍스트를 네 가지로 쪼개라: Instruction · Context · Evidence · State

이 챕터의 핵심 도구입니다. Context Harness를 설계할 때 **가장 먼저 구분해야 할 네 가지**입니다.

| 요소            | 정의                          | 구체적인 내용                                                                                  |
|-----------------|-------------------------------|------------------------------------------------------------------------------------------------|
| **Instruction** | **어떻게 행동해야 하는가**    | 테스트 없이 완료 선언 금지, API 응답 스키마 임의 변경 금지, 컨트롤러에 비즈니스 로직 작성 금지 |
| **Context**     | **작업을 이해할 배경**        | 프로젝트 구조, 관련 파일, 현재 브랜치, 프레임워크, 런타임 환경                                 |
| **Evidence**    | **문제를 보여주는 관찰 자료** | 실패한 테스트 출력, Stack trace, Docker 빌드 에러, CI 로그                                     |
| **State**       | **지금까지의 작업 기록**      | 이미 시도한 해결책, 실패한 가설, 변경된 파일, 압축된 요약, 서브 에이전트 결과                  |

> "**Instruction은 Claude가 어떻게 행동해야 하는지에 대한 규칙**입니다."

왜 굳이 나눠야 할까요. **섞여 있으면 모델이 무게를 다르게 줄 수 없기 때문**입니다. 규칙 (Instruction)과 관찰 (Evidence)이 한 덩어리로 들어가면, 모델은 "지켜야 할 것"과 "참고할 것"을
구분하지 못합니다.

> 이 네 가지가 구분되지 않으면, **많은 정보를 줬는데도 실제로는 흐린 정보를 준 것**이 됩니다.

"많이 줬다"와 "잘 줬다"는 전혀 다른 이야기라는 뜻입니다.

### Context Pack: 프로젝트를 던지지 말고 작업면을 잘라 줘라

네 가지 요소를 실제 작업 단위로 묶은 것이 **Context Pack**입니다. 정의는 간단합니다.

> Context Pack은 Claude에게 **전체 프로젝트를 던지는 것이 아니라, 작업에 필요한 작업면을 잘라서 주는 것**입니다.

Context Pack에 반드시 들어가야 할 항목은 다음과 같습니다.

| 항목               | 담는 내용                     |
|--------------------|-------------------------------|
| **Objective**      | **무엇을 달성해야 하는가**    |
| **Evidence**       | 현재 에러와 실패 로그         |
| **관련 파일 후보** | 어디를 봐야 하는가            |
| **수정 금지 범위** | 건드리면 안 되는 파일·경로    |
| **검증 방법**      | 무엇으로 완료를 판정할 것인가 |

강의에서 든 **로그인 버그** 예시로 보면 차이가 확 드러납니다.

```
[나쁜 요청]
  "로그인 버그 좀 고쳐 줘"
      → 어디를 볼지, 무엇을 건드리면 안 되는지, 언제 끝인지 전부 모델이 추측
```

```
[Context Pack으로 준 요청]
  Objective   : 로그인 API의 500 에러를 해결한다
  Evidence    : (현재 발생 중인 에러 로그 전문)
  파일 후보    : Service / Controller / Strategy / Test
  수정 금지    : DB Schema, Public API Response Shape
  진행 규칙    : 원인 후보를 3개 이하로 좁힐 것
                수정 전에 볼 파일을 먼저 제한할 것
  검증        : (통과해야 하는 테스트)
```

이렇게 잘라 주는 것만으로 **작업 실패 확률이 확 줄어듭니다.** 모델이 추측해야 할 변수가 그만큼 사라지기 때문입니다.

특히 `원인 후보를 3개 이하로 좁힐 것`, `수정 전에 볼 파일을 먼저 제한할 것` 같은 항목이 중요합니다. 이건 결과물에 대한 요구가 아니라 **작업 절차에 대한 제약**입니다. 모델이 곧바로 코드를 고치러
달려가는 것을 막아 줍니다.

### 세션의 기본 진행 순서: Explore → Plan → Edit → Verify

Context Pack이 제대로 설계되면 세션은 자연스럽게 이 순서를 따릅니다.

```
 Explore  →  Plan  →  Edit  →  Verify
 (탐색)      (계획)   (수정)    (검증)
```

| 단계        | 하는 일                          |
|-------------|----------------------------------|
| **Explore** | 관련 파일을 **찾는다**           |
| **Plan**    | 원인 후보를 세우고 계획을 만든다 |
| **Edit**    | 그제서야 **수정**한다            |
| **Verify**  | 검증 명령으로 **확인**한다       |

큰 코드베이스에서 사고가 나는 대부분의 경우는 **Explore와 Plan을 건너뛰고 바로 Edit으로 들어갈 때**입니다. Context Harness는 이 순서를 지키게 만드는 장치이기도 합니다.

### 컨텍스트는 무한한 기억이 아니라 매번 조립되는 작업면이다

여기서 중요한 인식 전환이 하나 더 필요합니다. Claude Code는 컨텍스트를 **희소 자원 (Scarce Resource)** 으로 다룹니다.

> 컨텍스트 윈도우는 **무한한 기억이 아니라, 매번 `model call` 전에 조립되는 제한된 작업면**입니다.

매 호출마다 다음 재료들이 섞여 하나의 윈도우로 조립됩니다.

| 조립 재료              | 설명                          |
|------------------------|-------------------------------|
| **시스템 프롬프트**    | Claude Code 자체의 지시       |
| **환경 정보**          | OS, 경로, 브랜치 등           |
| **`CLAUDE.md`**        | 사용자가 고정한 프로젝트 규칙 |
| **Auto Memory**        | Claude가 남긴 기억            |
| **툴 메타데이터**      | 사용 가능한 도구 정의         |
| **대화 히스토리**      | 지금까지의 주고받음           |
| **툴 결과**            | 파일 내용, 명령 출력          |
| **서브 에이전트 요약** | 위임한 작업의 결과            |
| **압축된 요약**        | Compact로 줄여 놓은 과거      |

정해진 크기 안에 이 모두를 넣어야 하니, 커지면 **압축 (Compaction)** 이 일어납니다. 그런데 여기에 중요한 성질이 있습니다.

> **압축은 언제나 손실을 동반합니다.**

그래서 **중요한 팀 규칙이나 반복되는 아키텍처를 대화 컨텍스트 안에만 두면, 컴팩트 이후 흐려집니다.** 앞에서 언급한 저장 위치 문제가 여기서 다시 등장하는데, 이번에는 이유가 더 분명해집니다.

| 성격                   | 두어야 할 곳                | 이유                                     |
|------------------------|-----------------------------|------------------------------------------|
| **일회성 정보**        | 대화 컨텍스트               | 이번 작업만 필요                         |
| **반복되는 규칙**      | **`CLAUDE.md`**             | 압축돼도 매 세션 다시 주입됨             |
| **강제해야 하는 규칙** | **`Permissions` / `Hooks`** | 컨텍스트와 무관하게 **실행 층에서 차단** |

"세션 초반에는 잘하더니 뒤로 갈수록 규칙을 잊는다"는 현상의 정체가 바로 이것입니다. 잊은 게 아니라 **압축 과정에서 흐려진 것**입니다.

### Claude가 헛돌 때 하지 말아야 할 것

이 챕터에서 가장 실전적인 조언입니다. Claude가 헛돌면 우리는 본능적으로 **설명을 더 붙입니다.**

> "클로드가 헛돌게 되면 **설명을 더 많이 붙여주면 된다** 라고 생각을 하고, 더 많은 정보를 **구조 없이 그냥 막** 줄 수도 있어요. **실제로는 반대인 경우가 많죠.**"

이미 흐려진 작업면에 정보를 더 부으면 더 흐려질 뿐입니다. 필요한 건 **추가**가 아니라 **재설계**입니다.

| 헛돌 때의 반사 행동 (❌)       | 해야 할 일 (⭕)                         |
|--------------------------------|-----------------------------------------|
| 설명을 길게 덧붙인다           | **관련 파일 / 관련 없는 파일을 나눈다** |
| 자료를 구조 없이 더 던진다     | **수정 금지 범위를 명확히 한다**        |
| 같은 대화에서 계속 밀어붙인다  | **현재 가설을 폐기하거나 갈아탄다**     |
| 어떻게든 이 세션을 살리려 한다 | **필요하면 새 세션을 연다**             |

마지막 항목이 특히 중요합니다. 오염된 컨텍스트에서 대화를 이어가면 어떻게 될까요.

> Claude는 **이전의 잘못된 가설을 대화의 흐름으로 받아들이고, 더 정교한 오답을 만들어냅니다.**

틀린 전제가 대화 기록에 남아 있는 한, 모델은 그것을 "이미 합의된 사실"로 취급합니다. 그래서 오답이 **점점 더 그럴듯해집니다.** 세션을 새로 여는 것은 포기가 아니라 **오염된 State를 버리는 정당한
설계 행위**입니다.

### 작업 로그를 보라

그리고 하나 더. 컨텍스트 설계는 한 번에 완성되지 않습니다. **Claude의 작업 로그를 상세하게 보면서** 조정해 나가야 합니다.

- 지금 **어떤 파일을 보고 있는가**
- **어떤 수정**을 하고 있는가
- 제대로 된 방향으로 **작업하고 있는가**

로그를 보지 않으면 결과물만 보고 판단하게 되는데, 그때는 이미 늦습니다. **작업면이 흐려지는 순간을 로그에서 먼저 발견**해야 개입할 수 있습니다.

### 목적은 "많이 주는 것"이 아니라 "올바른 첫 행동"

이 챕터의 결론입니다.

> Context Harness의 목적은 Claude에게 **많은 정보를 주는 것이 아니라, Claude가 올바른 첫 번째 행동을 하게 만드는 것**입니다.

첫 행동이 왜 그렇게 중요할까요. 앞 챕터에서 본 것처럼 Claude Code는 **순환 구조**이기 때문입니다. 첫 행동이 잘못되면 그 결과가 다음 판단의 입력이 되고, 오염이 누적됩니다.

```
 [잘못된 첫 행동]                   [올바른 첫 행동]
 바로 코드 수정                     먼저 탐색
      ↓                                  ↓
 엉뚱한 파일 변경                   관련 파일 특정
      ↓                                  ↓
 그 변경이 컨텍스트에 남음          원인 후보 수립
      ↓                                  ↓
 더 정교한 오답                     검증 명령으로 확인
                                         ↓
                                    그 다음에 수정
```

이 기준이 서면 요청의 문장 자체가 달라집니다. "그냥 고쳐 줘" 대신 **"먼저 살펴보고, 문제를 짚고, 원인을 분석하고, 계획을 작성해 줘"** 라고 컨텍스트를 설계하게 됩니다.

### 정리

1. **문제는 대개 정보 부족이 아니라 작업면이 흐려진 것이다.** 큰 코드베이스에서는 **컨텍스트 과잉**이 더 자주 사고를 만든다.
2. **컨텍스트를 네 가지로 쪼개라.** `Instruction`(규칙) · `Context`(배경) · `Evidence`(관찰) · `State`(기록). 안 나누면 많이 줘도 흐린 정보다.
3. **Context Pack으로 작업면을 잘라 줘라.** 목표 · 증거 · 파일 후보 · 수정 금지 범위 · 검증 방법을 명시한다.
4. **컨텍스트는 매번 조립되는 희소 자원이다.** 압축은 손실을 동반하므로, 반복 규칙은 `CLAUDE.md`로, 강제 규칙은 `Permissions`/`Hooks`로 옮긴다.
5. **헛돌 때는 설명을 더하지 말고 재설계하라.** 오염된 컨텍스트를 이어가면 **더 정교한 오답**이 나온다. 새 세션을 여는 것도 설계다.
6. **목표는 올바른 첫 번째 행동이다.** `Explore → Plan → Edit → Verify` 순서를 지키게 만드는 것이 Context Harness의 역할이다.

다음 챕터는 **Permission Harness** — AI가 할 수 있는 행동 반경을 설계하는 이야기입니다. 이번 챕터에서 "컨텍스트로는 막을 수 없다"고 미뤄 둔 것들이 바로 거기서 다뤄집니다.

## Permission Harness 하네스 권한 - AI가 할 수 있는 행동 반경 설계

앞 챕터에서 컨텍스트로는 **막을 수 없는 것**이 있다고 미뤄 뒀습니다. 그 몫을 받는 것이 두 번째 하네스, **Permission Harness**입니다. 강사 **미국달팽이**님의 정의는 간결합니다.

> "퍼미션 하네스는 **클로드가 할 수 있는 행동과 할 수 없는 행동을 설계하는 구조**다 라고 아시면 되는데"

Context Harness가 **"무엇을 보는가"** 를 설계했다면, Permission Harness는 **"무엇을 할 수 있는가"** 를 설계합니다.

### 권한은 부가 기능이 아니다

Claude Code는 파일을 읽고, 코드를 고치고, 셸 커맨드를 실행할 수 있습니다. 그래서 실제 프로젝트에 투입할 수 있는 것이고, **동시에 바로 그 이유로 위험**합니다.

| 능력               | 따라오는 위험              |
|--------------------|----------------------------|
| **파일 읽기**      | **시크릿 노출**            |
| **파일 수정**      | **실제 코드 변경·삭제**    |
| **셸 커맨드 실행** | **되돌리기 어려운 부작용** |

능력과 위험은 같은 동전의 양면입니다. 그래서 강사는 권한의 위상을 분명히 못 박습니다.

> "클로드 코드에서 **퍼미션은 부가 기능이 아니라 실무 하네스의 핵심**이에요."

"일단 써 보고 나중에 설정하지"의 대상이 아니라, **처음부터 설계해야 하는 축**이라는 뜻입니다.

### 가장 나쁜 질문: "Claude를 믿을 수 있나?"

권한 설계를 시작할 때 사람들이 가장 흔히 던지는 질문이 있습니다. 그리고 그게 **가장 나쁜 출발점**입니다.

> "Permission Harness를 설계할 때 **가장 나쁜 접근은 '클로드를 믿을 수 있나' 라는 질문으로 시작하는 건데, 이 질문은 너무 추상적이죠.**"

"믿을 수 있나"는 답이 나오지 않는 질문입니다. 믿음의 정도를 숫자로 잴 수도 없고, 잰다 한들 설정 파일에 옮겨 적을 수도 없습니다. 대신 던져야 할 질문은 이것입니다.

> **"이 행동이 실패했을 때 비용이 얼마인가?"**

이 질문은 답이 나옵니다. 그리고 **명령어 단위로 분류**할 수 있습니다.

| 실패 비용 | 해당하는 행동                                                                   |
|-----------|---------------------------------------------------------------------------------|
| **낮음**  | `grep`, `npm test` 등 읽기·검증 명령                                            |
| **높음**  | `rm`, `git push`, **DB Migration**, **Production Deploy**, **Secret File Read** |

여기서 이 챕터의 핵심 문장이 나옵니다.

> **Permission은 신뢰의 문제가 아니라, 실패 비용을 기반으로 한 행동 반경 설계입니다.**

"Claude가 착한가"가 아니라 **"이게 터지면 내가 얼마를 무는가"** 로 기준을 옮기는 것. 이것이 권한 설계의 출발점입니다.

### 세 단계로 나눠라: Safe · Needs Approval · Deny

실패 비용을 기준으로 행동을 분류하면 자연스럽게 **세 단계**가 나옵니다.

| 단계               | 의미                      | 예시                                                   |
|--------------------|---------------------------|--------------------------------------------------------|
| **Safe**           | 승인 없이 **그냥 실행**   | Read Files, `grep`, `npm test`                         |
| **Needs Approval** | 실행 전 **사람에게 확인** | Edit, `git commit`, Migration, 패키지 수정, Docker     |
| **Deny**           | **절대 자동 실행 불가**   | `rm -rf`, 시크릿 파일 읽기, Kubernetes Delete, DB Drop |

```
       실패 비용 낮음                              실패 비용 높음
  ┌──────────────┐      ┌──────────────────┐      ┌──────────────┐
  │     SAFE     │      │  NEEDS APPROVAL  │      │     DENY     │
  │  그냥 실행   │ ───> │   물어보고 실행   │ ───> │  아예 차단   │
  │ read / grep  │      │ edit / commit    │      │ rm -rf / .env│
  └──────────────┘      └──────────────────┘      └──────────────┘
```

이 분류가 그대로 Claude Code의 **Fine-grained Permission Rules**로 옮겨집니다. Read-only 작업은 승인 없이 통과하고, 셸 실행이나 파일 수정은 승인 흐름을 탑니다.

### "안전한 명령"과 "되돌릴 수 있는 명령"은 다르다

여기서 실무 감각이 필요한 지점이 나옵니다. 되돌릴 수 있다고 해서 자동으로 Safe가 아닙니다.

| 명령                 | 되돌릴 수 있나 | 그런데 왜 ASK인가                       |
|----------------------|----------------|-----------------------------------------|
| **`git commit`**     | 되돌릴 수 있음 | **팀 워크플로우에 영향**을 준다         |
| **`npm install`**    | 되돌릴 수 있음 | **Dependency Tree가 바뀐다**            |
| **`docker-compose`** | 되돌릴 수 있음 | **포트 충돌 · 볼륨 변경** 가능성이 있다 |
| **`.env` 읽기**      | —              | **시크릿이 노출되면 되돌릴 수 없다**    |

앞의 셋은 **복구는 되지만 파장이 있는** 행동이라 `ASK`(Ask for Confirmation)가 적절합니다. 반면 `.env` 읽기는 성격이 다릅니다. **한번 노출된 시크릿은 되돌릴 수 없습니다.**
그래서 `ASK`가 아니라 **`Deny`** 가 맞습니다.

이 구분을 정리하면 이렇습니다.

```
  되돌릴 수 있는가?  ──── 아니오 ───→  DENY
        │
       예
        │
        ↓
  파장이 있는가?    ──── 예 ─────→  ASK (Needs Approval)
        │
      아니오
        │
        ↓
       SAFE
```

참고로 Claude Code 설정 문서 자체가 **Credential 파일 접근을 막는 `permissions.deny` 예시**를 제시합니다. 공식 문서가 예시로 들 만큼 기본적인 항목이라는 뜻입니다.

### Deny First: 권한은 여러 층으로 적용된다

Permission System의 작동 원칙은 **Deny First**입니다. 모델이 도구를 요청하면 하네스는 **가장 먼저 Deny 규칙부터** 확인합니다.

```
  모델의 Tool 요청
        ↓
  ┌───────────────┐
  │ 1. Deny 규칙  │  ← 여기서 걸리면 끝. 아래로 못 감
  └───────────────┘
        ↓
  ┌───────────────┐
  │ 2. Mode       │
  └───────────────┘
        ↓
  ┌───────────────┐
  │ 3. Hooks      │
  └───────────────┘
        ↓
  ┌───────────────┐
  │ 4. Classifier │
  └───────────────┘
        ↓
  ┌───────────────┐
  │ 5. Sandbox    │
  └───────────────┘
        ↓
      실행
```

그리고 이 구조에서 반드시 기억해야 할 성질이 하나 있습니다.

> **Deny된 툴은 다른 레벨에서 Allow할 수 없습니다.**

즉 `Deny`는 "기본값" 같은 것이 아니라 **하위 설정이 뒤집을 수 없는 상위 정책**입니다.

> "즉 **Deny는 단순 옵션이 아니라 상위 정책으로 행동 경계를 강제하는 수단**이라고 보시면 됩니다."

Context Harness 챕터에서 `CLAUDE.md`는 "부탁"이라고 했던 것과 정확히 대비됩니다. `CLAUDE.md`의 금지는 흐려질 수 있지만, **`Deny`의 금지는 뒤집히지 않습니다.**

| 어디에 쓰는가             | 성격                 | 뒤집힐 수 있나     |
|---------------------------|----------------------|--------------------|
| `CLAUDE.md`에 "하지 마"   | 컨텍스트 (**부탁**)  | **흐려질 수 있음** |
| `permissions.deny`에 등록 | 실행 정책 (**차단**) | **불가능**         |

### 좋은 권한 설계는 인간의 집중력에 기대지 않는다

왜 이렇게까지 층을 쌓아 둘까요. 승인 프롬프트를 잘 읽으면 되는 것 아닐까요. 강사는 그 전제를 부정합니다.

> "좋은 Permission Harness는 **인간의 집중력 하나에 의존하지 않는** 겁니다. **실수를 할 수 있다라는 것을 의도적으로 설계**를 한 거죠."

반복되는 승인 프롬프트 앞에서 사람은 반드시 **무감각**해집니다. 처음 열 번은 읽지만, 백 번째에는 그냥 엔터를 칩니다. 이것은 개인의 성실성 문제가 아니라 **예측 가능한 인간의 특성**입니다.

그래서 설계는 이렇게 갈립니다.

| 잘못된 전제                       | 설계에 반영해야 할 전제                   |
|-----------------------------------|-------------------------------------------|
| 사람이 프롬프트를 매번 잘 읽을 것 | **사람은 결국 대충 승인하게 된다**        |
| 위험한 건 그때그때 판단하면 됨    | **위험한 건 애초에 물어보지도 않게 한다** |

정말 위험한 것은 **승인 대상이 아니라 차단 대상**이어야 한다는 뜻입니다. 물어보는 순간, 언젠가는 승인됩니다.

### Permission Harness를 구성하는 수단들

권한은 `settings.json` 하나로 끝나지 않습니다. 여러 수단이 함께 작동합니다.

| 수단                 | 역할                                    |
|----------------------|-----------------------------------------|
| **Policies**         | 조직·상위 레벨의 정책                   |
| **Settings**         | `permissions`의 allow / ask / deny 규칙 |
| **Hooks**            | 실행 전후에 규칙을 **강제**             |
| **Sandbox**          | 실행 자체를 **격리**                    |
| **Session Boundary** | 세션 단위로 행동 범위를 제한            |

그리고 이 모두가 겨냥하는 목표는 하나입니다.

> **반복적이고 안전한 검증 명령은 열어 주고, 실패 비용이 큰 행동은 막는 것.**

여기서 오해하기 쉬운 점을 짚어야 합니다. Permission Harness는 **Claude를 굼뜨게 만드는 장치가 아닙니다.** 오히려 반대입니다.

```
  퍼미션이 없을 때          →  전부 물어봄 → 사람이 계속 붙어 있어야 함 → 느림
  퍼미션이 잘 설계됐을 때   →  안전한 건 알아서 → 위험한 것만 사람이 봄 → 빠름 + 안전
```

**안전한 명령을 열어 주는 것도 권한 설계의 절반**입니다. `npm test`를 매번 승인받게 만들면 Claude는 아무 일도 못 합니다. 열 곳을 확실히 열어야 막을 곳을 확실히 막을 수 있습니다.

### 보안팀만의 문제가 아니다

마지막으로 강사가 강조하는 지점입니다. 권한 설계는 **보안 담당자의 일**로 미뤄지기 쉽지만, 그렇지 않습니다.

> 중급 백엔드 개발자든, 엔지니어든, 테크 리드든 **자기 프로젝트에서 AI에게 맡길 수 있는 행동과 사람이 통제해야 하는 행동을 스스로 정의**해야 합니다.

이유는 간단합니다. **어떤 명령이 이 프로젝트에서 위험한지는 그 프로젝트를 아는 사람만 압니다.** 일반적인 `rm -rf`는 누구나 알지만, "이 배치 잡을 로컬에서 돌리면 스테이징 DB가 물린다" 같은 것은
팀만 압니다.

| 기준이 없을 때                | 기준이 있을 때                                            |
|-------------------------------|-----------------------------------------------------------|
| Claude Code는 **위험한 도구** | **반복 작업은 줄이고, 실패 비용이 큰 행동만 사람이 검토** |

### 정리

1. **권한은 부가 기능이 아니라 실무 하네스의 핵심이다.** 파일·셸 접근 능력은 곧 위험이다.
2. **"믿을 수 있나"는 나쁜 질문이다.** 대신 **"실패하면 비용이 얼마인가"** 를 물어야 설정 파일로 옮겨 적을 수 있다.
3. **Safe · Needs Approval · Deny 세 단계로 나눠라.** 되돌릴 수 있어도 파장이 있으면 `ASK`, 되돌릴 수 없으면 `Deny`.
4. **Deny First이고, Deny는 뒤집히지 않는다.** `CLAUDE.md`의 금지는 흐려지지만 `permissions.deny`의 금지는 상위 정책으로 강제된다.
5. **인간의 집중력에 기대지 마라.** 정말 위험한 것은 승인 대상이 아니라 **차단 대상**이어야 한다.
6. **막는 것만큼 여는 것도 설계다.** 안전한 검증 명령을 열어 줘야 Claude가 실제로 일을 한다.

다음 챕터는 **Verification Harness** — "다 됐습니다"라는 Claude의 말을 무엇으로 검증할 것인가에 대한 이야기입니다.

## Verification Harness 하네스 검증 - Claude 작업 검증

세 번째 하네스는 **Verification Harness**입니다. Context Harness가 "무엇을 보는가", Permission Harness가 "무엇을 할 수 있는가"를 설계했다면, 이번에는 **"
끝났다는 말을 무엇으로 확인하는가"** 입니다.

### 가장 위험한 순간은 "틀렸는데 그럴듯하게 완료됐다"고 할 때

Claude Code를 쓰다 보면 가장 곤란한 상황이 있습니다. 명백히 실패하는 경우가 아닙니다.

> "가장 위험한 순간은 **Claude가 틀렸는데도 그럴듯하게 '완료됐다'라고 하는 경우**도 되게 많습니다."

에러를 뱉으면 오히려 다행입니다. 문제는 **작업이 매끄럽게 끝난 것처럼 보일 때**입니다. 구체적으로는 이런 것들입니다.

- 코드베이스 전체의 **컨벤션을 깨는** 수정
- **테스트를 우회**하는 방식의 해결
- 요청하지도 않은 **관련 없는 리팩터링**이 섞여 들어감

전부 "돌아가긴 하는" 상태라 겉으로는 성공처럼 보입니다. 그래서 강사는 검증의 위상을 이렇게 못 박습니다.

> "하네스 엔지니어링에서 **Verification 검증은 선택 사항이 아니라 필수적인 요소**라고 보시면 됩니다."

### 좋은 로컬 판단이 나쁜 결과를 만든다

왜 이런 일이 생길까요. 모델이 게으르거나 부정확해서가 아닙니다. **역량 (capability)과 신뢰성 (reliability)이 충돌**하기 때문입니다.

모델은 빠르게 코드를 생성합니다. 그런데 그 판단은 **제한된 컨텍스트 안에서** 이루어집니다. 앞선 Context Harness 챕터에서 본 것처럼, 컨텍스트 윈도우는 **매번 조립되는 제한된 작업면**입니다. 그
좁은 창 안에서는 최선의 선택이었더라도, 프로젝트 전체로 보면 잘못된 선택일 수 있습니다.

> "좋은 local decision, 그러니까 **좋은 판단을 하기 위해서는 나쁜 결과를 만들 수도 있다**는 것입니다."

```
  [Claude가 보는 것]              [실제 프로젝트]
  ┌──────────────┐               ┌────────────────────────┐
  │ 이 파일      │               │ 아키텍처 경계          │
  │ 이 함수      │   ⊂           │ 테스트 전략            │
  │ 이 에러 로그 │               │ API Contract           │
  └──────────────┘               │ 마이그레이션 정책      │
   여기선 최선의 판단             └────────────────────────┘
                                   여기선 위반일 수 있음
```

여기서 반드시 버려야 할 가정이 하나 있습니다. **Claude가 만든 코드가 프로젝트 전체의 아키텍처 경계, 테스트 전략, API Contract, 마이그레이션 정책을 자동으로 보존한다고 가정하면 안 됩니다.**
모델은 보이지 않는 것을 지킬 수 없습니다.

> "이 **검증 하네스는 바로 이 갭을 메꿔주는 구조**라고 보시면 됩니다."

### 검증은 세 겹으로 설계한다

Verification Harness는 **자동 검증 · 구조 검증 · 반례 검증**의 세 레이어로 구성됩니다. 각각 잡아내는 문제의 종류가 다릅니다.

| 레이어        | 무엇을 보는가       | 잡아내는 문제              |
|---------------|---------------------|----------------------------|
| **자동 검증** | **동작하는가**      | 깨진 빌드, 실패하는 테스트 |
| **구조 검증** | **범위를 지켰는가** | 범위 이탈, 계약 위반       |
| **반례 검증** | **틀릴 수 있는가**  | 엣지 케이스, 경합, 회귀    |

```
 Claude의 수정안
       ↓
 ┌──────────────────────────────────────┐
 │ 1. 자동 검증  test / lint / build    │  "돌아가는가?"
 ├──────────────────────────────────────┤
 │ 2. 구조 검증  diff review            │  "약속한 범위 안인가?"
 ├──────────────────────────────────────┤
 │ 3. 반례 검증  edge / race / regress  │  "어디서 틀릴 수 있나?"
 └──────────────────────────────────────┘
       ↓
    완료 판정
```

#### 1. 자동 검증 (Automated Checks)

**반복 가능하고 자동화된 검증**입니다. 매번 돌려야 하는 것들이죠.

| 항목           | 확인하는 것            |
|----------------|------------------------|
| **Test**       | 기존 동작이 유지되는가 |
| **Lint**       | 스타일 규칙을 지켰는가 |
| **Type check** | 타입이 맞는가          |
| **Build**      | 빌드가 통과하는가      |
| **Smoke test** | 최소한의 동작이 되는가 |

기계가 대신 봐 주는 층이므로 **가장 먼저, 가장 자주** 돌려야 합니다.

#### 2. 구조 검증 (Diff Review)

여기부터가 사람의 눈이 필요한 영역입니다. **변경 사항 (diff)을 보고 범위를 확인**합니다.

- 수정 범위가 **예상과 일치하는가**
- **공개 API나 Schema를 변경**하지 않았는가
- **불필요한 리팩터링이 섞이지** 않았는가
- **Secret을 건드리지** 않았는가

자동 검증은 이걸 못 잡습니다. **API 시그니처를 바꿔도 테스트가 함께 수정됐다면 초록불이 뜨기 때문**입니다. "돌아간다"와 "약속을 지켰다"는 다른 이야기입니다.

#### 3. 반례 검증 (Counter-example Verification)

가장 놓치기 쉬운 층입니다. **이 수정안이 어떤 입력에서 틀릴 수 있는지**를 능동적으로 찾습니다.

| 항목                    | 묻는 것                            |
|-------------------------|------------------------------------|
| **Edge Case**           | 경계값에서 깨지지 않는가           |
| **Invalid Input**       | 잘못된 입력을 어떻게 처리하는가    |
| **Race Condition**      | 동시성 상황에서 깨지지 않는가      |
| **Regression Scenario** | 예전에 고쳤던 게 되살아나지 않는가 |
| **Configuration**       | 다른 설정 환경에서도 동작하는가    |

앞의 두 층이 "지금 상태를 확인"한다면, 반례 검증은 **"미래에 터질 지점을 찾는"** 작업입니다.

### 테스트 통과는 충분조건이 아니다

이 챕터에서 반드시 짚어야 할 함정입니다. 우리는 초록불을 보면 안심하지만, **테스트 통과는 중요한 시그널일 뿐 충분조건이 아닙니다.**

| 상황                  | 왜 신뢰할 수 없나                                                                                       |
|-----------------------|---------------------------------------------------------------------------------------------------------|
| **테스트가 통과했다** | 레거시 코드베이스는 **커버리지가 낮다**. Claude가 고친 영역이 애초에 **테스트되지 않은 영역**일 수 있다 |
| **테스트가 실패했다** | **테스트 자체가 만료**됐을 수 있다. 코드가 아니라 테스트가 낡은 경우                                    |

```
  테스트 통과 = 검증 완료   ❌
  테스트 통과 = 시그널 하나 ⭕
```

그래서 **자동 검증만으로 완료를 판정하면 안 됩니다.** 세 층이 필요한 이유가 여기 있습니다.

### "코드 좋아 보여?"라고 묻지 마라

검증의 일부를 Claude에게 맡길 수도 있습니다. 그런데 **묻는 방식**이 결과를 가릅니다.

가장 쓸모없는 질문이 **"이 코드 괜찮아 보여?"** 입니다. 기준이 없으니 답도 "괜찮아 보입니다"로 돌아옵니다. 대신 **구체적인 검토 기준**을 줘야 합니다.

```
[검증 요청 프롬프트에 넣을 항목]

  1. 원래 요청 범위를 벗어난 변경이 있는가?
  2. Public API 또는 Response Schema를 변경했는가?
  3. 기존 테스트 없이 비즈니스 로직을 변경했는가?
  4. 이 수정이 실패할 수 있는 반례 입력은 무엇인가?
  5. 추가해야 할 Regression 테스트는 무엇인가?
```

이 다섯 항목이 앞의 세 레이어와 그대로 대응합니다. 1~3번은 **구조 검증**, 4~5번은 **반례 검증**입니다. 검증을 위임하더라도 **무엇을 볼지는 사람이 지정**하는 것이죠.

### 같은 컨텍스트에서 검토하면 같은 실수를 반복한다

여기서 중요한 함정이 하나 더 있습니다. **Claude가 만든 패치를 같은 세션의 Claude에게 검토시키는 것**입니다.

같은 세션 안에서는 **컨텍스트도, 가설도 공유**됩니다. 즉 처음에 잘못된 전제로 코드를 짰다면, 검토할 때도 **그 전제를 그대로 깔고** 봅니다. 그래서 블라인드 스팟이 사라지는 게 아니라 **반복**됩니다.

Context Harness 챕터에서 "오염된 컨텍스트를 이어가면 **더 정교한 오답**이 나온다"고 했던 것과 같은 구조입니다.

| 방식                       | 결과                     |
|----------------------------|--------------------------|
| 같은 세션에서 자기 검토    | **블라인드 스팟 반복**   |
| **Sub-agent로 분리**       | 컨텍스트를 공유하지 않음 |
| **새 세션에서 리뷰**       | 가설을 새로 세움         |
| **Worktree에서 별도 검증** | 작업 공간 자체를 분리    |

그리고 어느 방식을 쓰든 원칙은 같습니다. **AI에게 검증을 맡기더라도, 검증 기준은 사람이 설계해야 합니다.**

### 좋은 자동화는 실패하지 않는 자동화가 아니다

이 챕터의 결론이자 가장 기억할 문장입니다.

> "**좋은 자동화는 실패하지 않는 자동화가 아니라, 실패해도 되돌릴 수 있는 자동화**라고 할 수 있습니다."

첫 챕터에서 좋은 시스템의 기준으로 **Safe · Reviewable · Recoverable**을 꼽았는데, 그중 **Recoverable**이 여기서 구체적인 실무 습관으로 내려옵니다.

| 실천 항목                             | 목적                           |
|---------------------------------------|--------------------------------|
| **브랜치를 나눈다**                   | 본류를 오염시키지 않는다       |
| **작은 단위로 커밋한다**              | 되돌릴 지점을 촘촘히 만든다    |
| **테스트 커맨드를 기록한다**          | 재현 가능한 검증 절차를 남긴다 |
| **PR description에 검증 내용을 쓴다** | 무엇을 확인했는지 남긴다       |
| **Rollback 방법을 적어 둔다**         | 터졌을 때 헤매지 않는다        |

작은 단위 커밋이 특히 중요합니다. **되돌릴 수 있는 자동화의 실체는 결국 "되돌릴 지점이 촘촘한 히스토리"** 이기 때문입니다.

### AI 패치를 완료로 판정하는 5가지 조건

강의는 마지막으로 체크리스트를 제시합니다. 이 다섯 개가 **모두** 충족돼야 "안전하게 검증했다"고 말할 수 있습니다.

```
  ☐ 1. Claude가 고쳤다
  ☐ 2. 테스트를 통과했다
  ☐ 3. 변경이 약속한 범위 안에 있다
  ☐ 4. 반례를 확인했다
  ☐ 5. 문제가 생기면 되돌릴 수 있다
```

대부분의 사람은 1번과 2번에서 멈춥니다. 그런데 앞에서 본 것처럼 **2번은 충분조건이 아니고, 3~5번이 빠지면 사고는 반드시 납니다.** "완료"의 정의를 이 다섯 줄로 바꾸는 것이 Verification
Harness의 실질입니다.

### 정리

1. **가장 위험한 건 실패가 아니라 "그럴듯한 완료"다.** 돌아가는 것처럼 보이는 잘못된 수정이 제일 잡기 어렵다.
2. **좋은 로컬 판단이 나쁜 전역 결과를 만든다.** 모델은 제한된 작업면 안에서 판단하므로 아키텍처 경계·API Contract를 자동으로 지켜 준다고 가정하면 안 된다.
3. **검증은 세 겹이다.** `자동 검증`(돌아가는가) · `구조 검증`(범위를 지켰는가) · `반례 검증`(어디서 틀릴 수 있나).
4. **테스트 통과는 충분조건이 아니다.** 커버리지가 낮으면 초록불도 의미가 없고, 빨간불이 낡은 테스트 탓일 수도 있다.
5. **검증을 맡기더라도 기준은 사람이 만든다.** "괜찮아 보여?"가 아니라 5개 항목을 명시하고, 같은 세션이 아니라 **Sub-agent·새 세션·Worktree**로 분리한다.
6. **좋은 자동화는 되돌릴 수 있는 자동화다.** 브랜치 분리, 작은 커밋, 검증 기록, Rollback 절차까지가 검증의 일부다.

다음 챕터는 **Tool Harness** — Built-in Tools · Skills · MCP · Hooks의 역할 차이를 가르는 이야기입니다.

## Tool Harness 하네스 엔지니어링 도구 - Built-in Tools, Skills, MCP, Hooks의 역할 차이

네 번째 하네스는 **Tool Harness**입니다. Claude Code에는 확장 메커니즘이 여럿 있습니다. Built-in Tools, Skills, MCP, Hooks, 그리고 Plugin까지. 문제는
이것들이 **"할 수 있는 일 목록"** 으로 소개되는 경우가 많다는 점입니다. 강사 **미국달팽이**님은 그 접근을 경계합니다.

> "하네스 엔지니어링 관점에서는 이 기능들을 **단순히 나열을 하면 안 되고요. 무엇을 더 붙일 수 있는지가 아니라 에이전트 루프의 어느 지점에서 개입을 할 것인가**가 중요합니다."

즉 이 챕터의 질문은 "무엇을 쓸 수 있나"가 아니라 **"어디에 꽂을 것인가"** 입니다.

### 확장 메커니즘은 각자 다른 자리에 있다

먼저 Claude Code의 확장 구조를 역할별로 나눠 봅니다.

| 메커니즘   | 하는 일                                                   |
|------------|-----------------------------------------------------------|
| **MCP**    | **외부 시스템**을 도구 인터페이스로 연결                  |
| **Skills** | **반복 절차·도메인 지침**을 낮은 컨텍스트 비용으로 불러옴 |
| **Hooks**  | 도구 실행 전후·세션 생명 주기에 **결정론적으로 개입**     |
| **Plugin** | 위 요소들을 **패키징해서 배포**                           |

여기서 **Hooks의 "결정론적 (deterministic)"** 이라는 수식어를 눈여겨봐야 합니다. Skills나 컨텍스트는 모델의 해석을 거치지만, **Hooks는 모델의 판단과 무관하게 무조건 실행**됩니다.
Permission Harness 챕터의 `Deny`와 같은 성질입니다.

### 에이전트 루프를 세 지점으로 쪼개라

이 챕터의 핵심 도구입니다. 강사는 Tool Harness를 이해하는 최선의 방법을 이렇게 제시합니다.

> "**툴 하네스를 이해하는 가장 좋은 방법은 에이전트 루프를 3개의 지점으로 나누어 주는 겁니다.**"

| 지점             | 던지는 질문                          |
|------------------|--------------------------------------|
| **`assemble()`** | 모델이 **무엇을 볼 것인가**          |
| **`model()`**    | 모델이 **무엇을 호출할 수 있는가**   |
| **`execute()`**  | 실행 전후에 **무엇을 강제할 것인가** |

이 세 지점 위에 확장 메커니즘을 얹으면 각자의 자리가 선명해집니다.

```
 ┌──────────────┐
 │  assemble()  │  ← Skills / CLAUDE.md / Context
 │  무엇을 보나 │     "어떤 절차로 생각할 것인가"
 └──────┬───────┘
        ↓
 ┌──────────────┐
 │   model()    │  ← Built-in Tools / MCP
 │  무엇을 부르나│     "어떤 도구를 호출할 수 있는가"
 └──────┬───────┘
        ↓
 ┌──────────────┐
 │  execute()   │  ← Hooks / Permissions
 │  무엇을 강제하나│  "실행을 막거나 뒤처리할 것인가"
 └──────────────┘
```

**같은 규칙이라도 어느 지점에 두느냐에 따라 힘이 완전히 달라집니다.** 이게 이 챕터의 전부라고 해도 과언이 아닙니다.

### Skills: 절차를 일관되게 만드는 것

Skills는 흔히 "기능 추가"로 오해받지만, 실제로는 **모델에게 반복 절차를 알려주는 것**에 가깝습니다.

강의에서 든 **백엔드 디버깅 스킬** 예시를 보면 성격이 분명합니다.

```
[백엔드 디버깅 스킬이 담는 절차]

  1. 로그를 정리한다
  2. 원인 후보를 좁힌다
  3. 관련 파일을 탐색한다
  4. 검증 명령을 제한한다
```

어디에도 외부 시스템 호출이 없습니다. **Claude가 현재 컨텍스트 안에서 더 일관된 절차로 생각하게 만드는 것**이 전부입니다. Context Harness 챕터에서 본 `Explore → Plan →
Edit → Verify` 순서를 매번 손으로 적지 않고 재사용하는 장치라고 보면 됩니다.

| Skills로 만들면 좋은 것 | 예시                       |
|-------------------------|----------------------------|
| **반복되는 작업 방식**  | 릴리스 노트 작성 절차      |
| **팀의 디버깅 절차**    | 로그 → 후보 좁히기 → 검증  |
| **PR 작성 규칙**        | 제목 형식, 체크리스트 구성 |

### MCP: 외부 시스템으로 손을 뻗는 것

MCP (Model Context Protocol)는 성격이 완전히 다릅니다. **외부 시스템을 Claude의 도구 인터페이스로 열어 주는 것**입니다.

| 연결 대상       | 예시            |
|-----------------|-----------------|
| **코드 호스팅** | GitHub          |
| **데이터**      | 데이터베이스    |
| **운영**        | 모니터링 시스템 |
| **사내 시스템** | 내부 API        |
| **협업 도구**   | Jira            |

MCP를 붙이면 Claude가 할 수 있는 일이 확 늘어납니다. 하지만 **손이 뻗는 범위가 넓어진다는 건 위험도 함께 커진다는 뜻**입니다.

| 위험                | 내용                                        |
|---------------------|---------------------------------------------|
| **프롬프트 인젝션** | 외부에서 가져온 내용이 지시문처럼 작동      |
| **툴 포이즈닝**     | 도구 정의 자체가 악의적으로 조작됨          |
| **오버쉐어링**      | 필요 이상의 데이터가 컨텍스트로 흘러 들어옴 |

그래서 MCP를 다룰 때는 다음을 **함께** 설계해야 합니다.

- **Scope** — 어디까지 접근하게 할 것인가
- **Permission** — 어떤 동작을 허용할 것인가
- **Server Trust** — 이 서버를 신뢰할 근거가 있는가
- **Output Size** — 결과가 컨텍스트를 잡아먹지 않는가
- **Secret Handling** — 자격 증명을 어떻게 다루는가

특히 **Output Size**는 Context Harness와 직결됩니다. MCP 응답이 통째로 컨텍스트에 들어오면, 앞 챕터에서 말한 **컨텍스트 과잉**이 그대로 재현됩니다. 도구를 붙이는 일이 컨텍스트
설계와 무관하지 않다는 뜻입니다.

### Hooks: 실행 전후에 규칙을 강제하는 것

Hooks는 **결정론적 개입 장치**입니다. 특정 이벤트에서 **반드시** 실행됩니다.

| 이벤트                 | 시점                | 활용 예시                            |
|------------------------|---------------------|--------------------------------------|
| **`PreToolUse`**       | 도구 실행 **직전**  | 특정 경로에 대한 **쓰기 차단**       |
| **`PostToolUse`**      | 도구 실행 **직후**  | Python 파일 수정 후 **포매터 실행**  |
| **`UserPromptSubmit`** | 사용자 입력 제출 시 | 입력 단계에서 규칙 주입              |
| **`Stop`**             | 세션을 마치려 할 때 | **테스트 없이 종료하려는 흐름 차단** |

`Stop` 훅의 예시가 특히 인상적입니다. Verification Harness 챕터에서 "테스트 없이 완료를 선언하면 안 된다"고 했는데, 그걸 **`CLAUDE.md`에 부탁으로 적는 것과 `Stop` 훅으로
막는 것은 전혀 다른 강도**입니다.

```
  CLAUDE.md에 "테스트 없이 끝내지 마"   →  잊거나 무시할 수 있음
  Stop Hook으로 종료 차단              →  구조적으로 못 끝냄
```

### 무엇을 언제 쓸 것인가

다섯 가지 메커니즘의 선택 기준을 한 표로 정리하면 이렇습니다.

| 하고 싶은 일                                      | 써야 할 것      |
|---------------------------------------------------|-----------------|
| **반복 절차를 재사용**하고 싶다                   | **Skills**      |
| **외부 시스템을 연결**하고 싶다                   | **MCP**         |
| **실행 전후에 규칙을 강제**하고 싶다              | **Hooks**       |
| **팀 설정·에이전트·스킬·훅을 묶어 배포**하고 싶다 | **Plugin**      |
| **행동 범위를 제한**하고 싶다                     | **Permissions** |

### 흔히 하는 세 가지 잘못된 배치

강의가 마지막에 짚는 실무 함정들입니다. 전부 **"기능은 맞는데 자리가 틀린"** 경우입니다.

#### ❌ 모든 반복 작업에 MCP를 붙인다

외부 호출이 필요 없는 절차까지 MCP로 만들면 **시스템이 불필요하게 무거워집니다.** 서버가 뜨고, 도구 정의가 컨텍스트를 차지하고, 신뢰 검토 대상이 하나 늘어납니다. 외부에 나갈 일이 없다면 **Skills로
충분합니다.**

#### ❌ 외부 접근이 필요한데 Skills로만 해결하려 한다

반대 방향의 실수입니다. Skills는 절차를 알려 줄 뿐이므로, **Claude가 실제 데이터를 가져올 수 없습니다.** "모니터링 지표를 보고 판단해 줘"라는 절차를 아무리 정교하게 써 놔도, 지표에 접근할
수단이 없으면 추측만 하게 됩니다.

#### ❌ 강제해야 할 규칙을 Skills에 적어 둔다

가장 흔하고 가장 치명적인 배치 오류입니다.

> 실행 전후의 강제 규칙을 Skills에 적어 두면 **Claude가 잊거나 무시할 수 있습니다.** 이때는 **Hooks나 Permissions로 옮겨야** 합니다.

이 시리즈에서 계속 반복된 구분이 여기서 완성됩니다.

| 성격                    | 두어야 할 자리              | 루프 지점    | 강제력                    |
|-------------------------|-----------------------------|--------------|---------------------------|
| **알려주고 싶은 것**    | `CLAUDE.md` / **Skills**    | `assemble()` | **부탁** (흐려질 수 있음) |
| **할 수 있게 하는 것**  | Built-in Tools / **MCP**    | `model()`    | 능력 부여                 |
| **반드시 지켜야 할 것** | **Hooks** / **Permissions** | `execute()`  | **강제** (뒤집히지 않음)  |

Context Harness 챕터의 "`CLAUDE.md`는 부탁이다", Permission Harness 챕터의 "`Deny`는 뒤집히지 않는다"가 결국 같은 이야기였던 셈입니다. **규칙의 성격에 맞는 루프
지점이 따로 있습니다.**

### Tool Harness는 더 붙이는 게 아니라 제자리에 두는 것

이 챕터의 결론입니다.

> "**Tool Harness, 도구에 대한 하네스는 더 많은 툴을 붙이는 것이 아니라, 각 툴의 메커니즘을 정확한 위치에 배치를 해주는 겁니다.**"

도구를 많이 붙일수록 좋아지지 않습니다. 오히려 **컨텍스트를 잡아먹고, 신뢰 검토 대상이 늘고, 어디서 규칙이 적용되는지 추적하기 어려워집니다.** 첫 챕터에서 본 "자율성은 공짜가 아니다"가 도구 층위에서
반복되는 셈입니다.

```
  ❌ 많이 붙이기      →  무거워지고, 겹치고, 추적 불가
  ⭕ 제자리에 두기    →  각 규칙이 정확히 필요한 순간에만 작동
```

### 정리

1. **질문은 "무엇을 붙일까"가 아니라 "어디에 꽂을까"다.** 에이전트 루프의 개입 지점이 설계의 축이다.
2. **루프를 세 지점으로 쪼개라.** `assemble()`(무엇을 보나) · `model()`(무엇을 부르나) · `execute()`(무엇을 강제하나).
3. **Skills는 절차, MCP는 연결, Hooks는 강제다.** Plugin은 이 셋을 묶어 배포하는 포장지다.
4. **MCP는 능력과 위험을 함께 늘린다.** Scope·Permission·Server Trust·Output Size·Secret Handling을 같이 설계해야 한다.
5. **강제해야 할 규칙을 Skills에 적지 마라.** 잊히거나 무시된다. `Hooks`나 `Permissions`로 옮겨야 실제로 지켜진다.
6. **많이 붙이는 게 아니라 제자리에 두는 것이다.** 도구 수는 품질과 비례하지 않는다.

다음 챕터는 **Subagent & Worktree Harness** — 병렬 처리보다 중요한 것은 격리라는 이야기입니다.

## Subagent & Worktree Harness - 병렬 처리보다 중요한 것은 격리

다섯 번째 하네스입니다. 제목이 이미 결론을 말하고 있습니다.

> **"병렬 처리보다 중요한 것은 격리다."**

Claude Code를 좀 쓰다 보면 누구나 같은 생각에 도달합니다. "세션을 여러 개 띄우면 더 빨라지지 않을까?" 강사 **미국달팽이**님의 답은 미묘합니다.

> "하지만 이 생각 같은 경우에는 **반쯤은 맞고 반쯤은 틀립니다.**"

맞는 절반은 **처리량**입니다. 여러 세션을 돌리면 작업 처리량 자체는 늘어납니다. 틀린 절반은 **격리 없는 병렬은 오히려 손해**라는 점입니다.

### 격리 없는 병렬은 오염을 부른다

세션을 여러 개 띄웠는데 각자 같은 저장소, 같은 파일, 같은 테스트 데이터를 건드리면 무슨 일이 벌어질까요.

- 같은 파일을 **동시에 수정**한다
- **테스트 데이터를 공유**하다 서로의 상태를 깨뜨린다
- 변경 사항이 섞여 **누가 무엇을 바꿨는지 추적 불가**해진다

> "그러니까 **자신이 프롬프트를 했고 작업을 하는 Context들, 이런 문맥들이 서로 오염이 되는 겁니다, 섞이는 거죠.**"

```
 [격리 없는 병렬]                  [격리된 병렬]
  세션 A ─┐                        세션 A ─→ 자기 작업면
  세션 B ─┼─→ 같은 작업면          세션 B ─→ 자기 작업면
  세션 C ─┘   (충돌·오염)          세션 C ─→ 자기 작업면
       ↓                                ↓
  빨라진 것 같지만                 실제로 병렬
  수습에 더 오래 걸림
```

Context Harness 챕터에서 본 **컨텍스트 오염**이 이번에는 **세션 사이에서** 일어나는 셈입니다. 그래서 병렬화의 전제 조건은 속도가 아니라 **격리**입니다.

### Subagent는 병렬화 기능이 아니라 격리 경계다

여기서 Subagent에 대한 통념을 뒤집습니다. Claude 공식 문서는 Subagent를 **특정 작업을 처리하는 전문화된 AI 보조**로 정의하고, 두 가지 성질을 명시합니다.

| 성질                 | 내용                            |
|----------------------|---------------------------------|
| **별도 Context**     | Main 대화와 **분리된** 컨텍스트 |
| **제한된 도구 권한** | 특정 도구에만 접근              |

그런데 하네스 관점에서 중요한 건 "AI를 하나 더 쓴다"가 아닙니다.

> "**Subagent는 단순한 보조 AI가 아니라 Main Context를 보완하는 격리 경계**라고 보실 수 있는데"

강의에서 인용하는 Claude Code 논문 역시 Subagent를 **병렬화 기능이 아니라 컨텍스트 격리 메커니즘**으로 분석합니다. 즉 Subagent의 본질은 "일손 추가"가 아니라 **"잡음 차단"**
입니다.

### 왜 잡음이 차단되는가: 탐색 예시

Subagent가 어떻게 메인 세션을 지켜 주는지, 강의에서 든 **인증 모듈 탐색** 예시로 보면 명확합니다.

```
[Subagent 없이 Main Session에서 직접 탐색]

  grep ... → 결과 200줄
  grep ... → 결과 150줄
  파일 읽기 → 400줄
  또 grep  → 결과 80줄
      ↓
  Main Context가 탐색 찌꺼기로 가득 참
  정작 판단할 때 작업면이 흐려짐
```

```
[탐색용 Subagent에게 위임]

  Parent Session ──(작업 위임)──> Explorer Subagent
                                    │ 제한된 컨텍스트 창에서
                                    │ 마음껏 grep / read
                                    ↓
  Parent Session <──(요약만 반환)── "인증은 A, B, C 파일에 있음"
      ↓
  Main Context는 깨끗하게 유지
```

핵심은 **Subagent가 반환하는 것이 과정이 아니라 요약·최종 보고**라는 점입니다. 지저분한 탐색 과정은 Subagent의 컨텍스트에서 소각되고, 메인에는 결론만 올라옵니다.

Context Harness 챕터에서 "컨텍스트는 매번 조립되는 희소 자원"이라고 했는데, **Subagent는 그 희소 자원을 아끼는 장치**입니다.

### 역할을 나누고, 역할마다 도구를 다르게 준다

Subagent Harness의 설계는 **역할 분리**에서 시작합니다. 강의가 제시하는 기본 구성은 셋입니다.

| 역할          | 하는 일                   | 줘야 할 권한                        |
|---------------|---------------------------|-------------------------------------|
| **Explorer**  | 관련 파일·구조를 **탐색** | **읽기 전용 도구만**                |
| **Implement** | 실제로 **구현·수정**      | Edit / Write 권한                   |
| **Verify**    | 테스트·변경분 **검증**    | **테스트 실행은 가능, 쓰기는 제한** |

그리고 여기에 반드시 지켜야 할 원칙이 붙습니다.

> **모든 Subagent에게 모든 도구를 주지 않습니다.**

Permission Harness 챕터의 원칙이 **에이전트 단위로 다시 적용**되는 셈입니다. 조사만 하는 에이전트에게 쓰기 권한을 주면, 조사하다 말고 고치기 시작합니다.

| 에이전트        | 왜 그 권한인가                                          |
|-----------------|---------------------------------------------------------|
| **Explorer**    | 읽기만 하면 되므로 쓰기는 **사고 위험**일 뿐            |
| **Verify**      | 테스트는 돌려야 하지만, **고치기 시작하면 검증이 아님** |
| **Code Review** | 변경분을 읽고 **위험을 찾는 데만 집중**                 |
| **Implement**   | 유일하게 **편집·쓰기 권한**을 갖는 자리                 |

이 구조가 낯설지 않은 이유가 있습니다.

> 사람 팀의 역할 분리와 같습니다. **리서치 · 구현 · 리뷰 · 검증**은 분리되어야 합니다.

리뷰어가 자기 코드를 리뷰하지 않는 것과 같은 이치입니다. Verification Harness 챕터에서 "같은 세션에서 자기 검토를 하면 블라인드 스팟이 반복된다"고 했던 것이, 여기서 **역할과 권한의 분리**로
구조화됩니다.

### Worktree는 파일 시스템을 격리한다

Subagent가 **대화 컨텍스트**를 격리한다면, Worktree는 **파일 시스템**을 격리합니다.

`git worktree`를 쓰면 하나의 저장소에서 **여러 워크트리**를 만들고, 각각 다른 브랜치에서 독립적으로 작업할 수 있습니다.

```
 repo/                    ← main 워크트리 (오염되지 않음)
 repo-bugfix/             ← bug/fix 브랜치     ← 세션 1: 테스트 실패 수정
 repo-refactor/           ← refactor 브랜치    ← 세션 2: 리팩터링
```

각 세션이 **서로 다른 디렉터리, 서로 다른 브랜치**에서 일하므로 다음이 자동으로 분리됩니다.

| 분리되는 것     | 효과                      |
|-----------------|---------------------------|
| **브랜치**      | 변경 이력이 섞이지 않음   |
| **디렉터리**    | 파일 충돌이 없음          |
| **테스트 결과** | 서로의 상태를 깨지 않음   |
| **변경 사항**   | diff를 **비교**할 수 있음 |

> "이 구조는 **병렬 Claude 세션을 운영할 때 매우 유용**하죠."

여기서 중요한 표현 하나가 나옵니다. 그냥 터미널을 여러 개 여는 것은 **혼란**입니다. Worktree를 쓰면 그게 **병렬 실행이 아니라 병렬 격리**가 됩니다.

```
  터미널만 여러 개    →  병렬 실행 (혼란)
  Worktree로 분리     →  병렬 격리 (관리 가능)
```

### 둘 중 하나만으로는 부족하다

이 챕터의 결론은 **두 격리가 서로 다른 축**이라는 점입니다.

| 하네스       | 격리 대상        |
|--------------|------------------|
| **Subagent** | **대화 Context** |
| **Worktree** | **파일 시스템**  |

축이 다르니 하나만 쓰면 반쪽입니다.

| 조합           | 결과                                     |
|----------------|------------------------------------------|
| **Subagent만** | 대화는 깨끗한데 **파일 변경이 충돌**한다 |
| **Worktree만** | 파일은 분리됐는데 **역할이 섞인다**      |
| **둘 다**      | **안전한 병렬 처리**                     |

둘을 결합하면 이런 구조가 나옵니다.

```
 ┌─────────────────────────────────────────────────────┐
 │                   Main Session                      │
 └───────┬─────────────────┬────────────────┬──────────┘
         │                 │                │
   [Explorer]        [Implement]        [Verify]
   읽기 전용         별도 Worktree      변경분 + 테스트
   관련 파일 탐색    작은 패치 생성      검토
         │                 │                │
   컨텍스트 격리     파일시스템 격리    컨텍스트 격리
```

- **조사 에이전트**는 읽기 전용으로 관련 파일을 찾고
- **구현 세션**은 별도 Worktree에서 **작은 변경 패치**를 만들고
- **검증 에이전트**는 변경분과 테스트를 검토합니다

"작은 변경 패치"라는 조건이 붙는 것도 우연이 아닙니다. Verification Harness 챕터의 **"되돌릴 지점이 촘촘한 히스토리"** 와 정확히 같은 이야기입니다.

### 정리

1. **"여러 개 돌리면 빠르다"는 반만 맞다.** 처리량은 늘지만, 격리가 없으면 오염과 충돌 수습에 더 오래 걸린다.
2. **Subagent는 병렬화 기능이 아니라 격리 경계다.** 별도 컨텍스트에서 일하고 **요약만 반환**해 메인 작업면을 지킨다.
3. **역할마다 도구를 다르게 줘라.** Explorer는 읽기 전용, Verify는 테스트만, 쓰기 권한은 Implement에만. 사람 팀의 역할 분리와 같다.
4. **Worktree는 파일 시스템을 격리한다.** 브랜치·디렉터리·테스트 결과·변경분이 함께 분리된다.
5. **터미널을 여러 개 여는 것은 병렬 실행이고, Worktree로 나누는 것은 병렬 격리다.**
6. **둘은 축이 다르므로 함께 써야 한다.** Subagent만으로는 파일이 충돌하고, Worktree만으로는 역할이 섞인다.

다음 챕터는 이 섹션의 마지막, **Debugging Harness** — 재현하기 어려운 버그를 Claude가 풀 수 있는 형태로 만드는 이야기입니다.

## Debugging Harness 하네스 디버깅 - 로그, 환경변수, 재현 어려운 버그를 Claude가 풀 수 있게 만들기

여섯 번째이자 마지막 하네스입니다. 그리고 아마도 **가장 자주, 가장 잘못 쓰이는** 영역입니다.

> "디버깅에서 많은 사람들이 하는 실수는 **에러 로그를 통째로 Claude에게 붙여놓고 '왜 이렇게 되냐'라고 묻는** 거예요."

솔직히 대부분 이렇게 합니다. 스택 트레이스를 복사해서 붙이고, 엔터를 치고, 답을 기다립니다. 그런데 강사 **미국달팽이**님은 이 방식의 문제를 정확히 짚습니다. **로그를 붙인 것은 정보를 준 것이지, 문제를
낸 것이 아닙니다.**

### 목적은 로그를 더 주는 게 아니라 문제 형태를 바꾸는 것

Debugging Harness의 정의는 이렇습니다.

> Claude가 실제 문제를 풀 수 있도록 **로그, 환경, 재현 조건, 가설, 검증 순서를 구조화**하는 시스템.

그리고 목적은 명확합니다.

> "그래서 디버깅 하네스의 목적은 **Claude에게 더 많은 로그를 주는 것이 아니라, 풀 수 있는 문제 형태로 바꾸는** 겁니다."

Context Harness 챕터에서 "헛돌 때 설명을 더 붙이는 건 반대"라고 했던 것과 정확히 같은 구조입니다. **양이 아니라 형태**의 문제입니다.

```
  ❌ 로그 3000줄 + "왜 이래?"      →  모델이 추측을 시작
  ⭕ 증상 + 증거 + 검증 경로       →  모델이 가설을 검증
```

### 세 가지를 분리하라: Symptom · Evidence · Verification Path

> "좋은 디버깅 하네스는 **세 가지를 분리**를 합니다. 첫째는 **관찰된 현상**이고요. 둘째는 **증거**예요. 세 번째는 **검증 경로**입니다."

| 요소                              | 답하는 질문               | 담기는 것                                                                  |
|-----------------------------------|---------------------------|----------------------------------------------------------------------------|
| **Symptom (관찰된 현상)**         | **무엇이 언제 실패했나**  | "API 서버에서 로그인 요청 시 500 에러 발생"                                |
| **Evidence (증거)**               | **무엇을 관찰했나**       | Stack Trace, 실패한 테스트 출력, Docker 로그, CI 실패 로그, 환경 변수 차이 |
| **Verification Path (검증 경로)** | **어떻게 확인할 수 있나** | 재현 명령, 실패하는 테스트, 가설 확인용 로그 추가 지점                     |

세 번째가 특히 중요합니다. 대부분의 사람은 1번과 2번까지만 줍니다. 그런데 **검증 경로가 없으면 모델은 가설을 세워도 확인할 방법이 없습니다.** 확인할 수 없는 가설은 그냥 추측입니다.

Context Harness 챕터에서 본 네 요소 (`Instruction`·`Context`·`Evidence`·`State`)의 디버깅 특화 버전이라고 봐도 좋습니다. 차이는 **
`Verification Path`가 명시적으로 포함된다**는 점입니다.

### 수정하지 말고, 원인 후보부터 좁혀라

이 챕터에서 반복되는 핵심 메시지입니다.

> "그래서 **먼저 수정하지 말고, 원인 후보를 좁혀야** 됩니다."

Claude Code는 요청을 받으면 곧바로 고치러 갑니다. 그게 문제입니다. 원인이 확정되지 않은 상태의 수정은 **증상을 가리는 수정**이 되기 쉽고, 그 변경이 다시 컨텍스트에 남아 다음 판단을 오염시킵니다.

```
 [나쁜 순서]  로그 던지기 → 바로 수정 → 증상만 사라짐 → 다른 데서 재발
 [좋은 순서]  증상 정리 → 원인 후보 나열 → 후보별 확인 방법 → 검증 → 그 다음 수정
```

Context Harness 챕터의 `Explore → Plan → Edit → Verify`가 디버깅에서는 **`증상 → 후보 → 검증 → 수정`** 으로 나타나는 셈입니다.

### 디버깅 프롬프트는 다섯 조각으로 만든다

강의가 제시하는 구체적인 템플릿입니다.

> "**문제, 환경, 증거, 제약, 요청**, 이렇게 5개로 프롬프트를 만들어서 Claude에게 제공을 해줘야 됩니다."

| 조각     | 담는 내용                                                        |
|----------|------------------------------------------------------------------|
| **문제** | 지금 무슨 일이 벌어지고 있는가                                   |
| **환경** | 로컬 / CI / Docker / 프로덕션 중 **어디서** 발생하는가           |
| **증거** | 로그, Stack Trace 등 수집한 자료                                 |
| **제약** | DB 스키마 변경 금지, API 응답 형태 변경 금지 등 **지켜야 할 선** |
| **요청** | 무엇을 해 달라는 것인가                                          |

그리고 **요청** 칸의 내용이 특히 중요합니다. "고쳐 줘"가 아닙니다.

```
[요청 칸에 써야 할 것]

  1. 가장 가능성 높은 원인 후보를 제시할 것
  2. 각 후보를 어떻게 확인할 수 있는지 알려줄 것
  3. 봐야 할 관련 파일 목록을 줄 것
  4. 회귀 테스트가 필요한지 판단할 것
```

요청을 이렇게 쓰면 모델의 첫 행동이 **수정이 아니라 분석**으로 바뀝니다. Context Harness 챕터에서 말한 **"올바른 첫 번째 행동"** 을 디버깅 상황에서 강제하는 장치입니다.

### 환경 변수: "로컬에서는 되는데요"의 정체

재현이 어려운 버그의 상당수는 코드 문제가 아닙니다.

> 로컬에서는 되는데 다른 환경에서는 실패하는 문제들은 **코드 문제보다 설정 스코프 (scope) 문제일 때가 많습니다.**

값이 틀린 게 아니라 **값이 그 자리까지 전달되지 않은 것**이죠. 그런데 여기서 딜레마가 생깁니다. 환경 변수를 확인하려면 값을 봐야 하고, 값에는 시크릿이 들어 있습니다. Permission Harness
챕터에서
`.env` 읽기를 **`Deny`** 로 분류했던 바로 그 지점입니다.

### 프라이버시를 지키면서 디버깅하기

강의의 해법이 우아합니다. **값을 보여주지 말고, 값에 대한 메타 정보를 보여주면 됩니다.**

| 주지 말아야 할 것 | 대신 줘야 할 것                       |
|-------------------|---------------------------------------|
| **값 자체**       | **키가 존재하는가** (존재 여부)       |
|                   | **어디서 왔는가** (출처)              |
|                   | **어디까지 적용되는가** (범위/스코프) |
|                   | **런타임에 값이 있는가** (유무)       |

이 정보만으로도 문제를 찾을 수 있습니다. 강의의 예시가 이 점을 잘 보여 줍니다.

```
  JWT_SECRET
    ├─ .env 파일에 존재함           ✅
    ├─ 호스트 셸에서 로드됨          ✅
    ├─ docker-compose에서 전달됨     ❌  ← 원인
    └─ 컨테이너 런타임에 값 있음      ❌
```

**`JWT_SECRET`의 값이 무엇인지는 끝까지 몰라도 됩니다.** "Docker Compose에서 컨테이너로 전달되지 않는다"는 사실만 알면 원인이 나옵니다.

이것이 **프라이버시 보존형 (privacy-preserving) 디버깅 하네스**입니다. Claude Code 설정 문서 역시 `settings.json`에서 환경 변수와 권한을 구성하고, **
`permissions.deny`로 민감한 파일 접근을 막을 수 있다**고 안내합니다. 즉 **막아 놓고도 디버깅은 가능**합니다.

| 흔한 오해                            | 실제                                |
|--------------------------------------|-------------------------------------|
| 디버깅하려면 시크릿을 열어 줘야 한다 | **메타 정보만으로 대부분 해결된다** |

### 확신할 때가 가장 위험하다

마지막으로 짚는 것은 **반례 검증**입니다.

> Claude가 원인을 **확신할 때** 반례를 물어야 합니다.

Verification Harness 챕터의 "가장 위험한 순간은 틀렸는데 그럴듯하게 완료됐다고 할 때"가 디버깅에서 반복됩니다. 자신 있게 원인을 지목하는 순간이 오히려 검증이 필요한 시점입니다.

```
[확신할 때 던져야 할 질문]

  · 이 가설이 틀릴 수 있는 조건은 무엇인가?
  · 이 수정이 실패할 수 있는 입력은 무엇인가?
  · 로그와 모순되는 다른 원인은 없는가?
```

이 질문들이 디버깅을 **직관에서 논리로** 옮깁니다.

### 디버깅은 결국 가설 검증 루프다

정리하면 디버깅은 세 동작의 반복입니다.

```
  가설 수립  →  증거로 원인 좁히기  →  반례 검증
      ↑                                    │
      └────────────────────────────────────┘
```

잘 설계된 Debugging Harness는 Claude가 이 루프의 각 단계를 **거들게** 만듭니다.

| 단계               | Claude가 돕는 일            |
|--------------------|-----------------------------|
| **가설 생성**      | 원인 후보를 나열            |
| **관찰 설계**      | 무엇을 어떻게 볼지 제안     |
| **재현 조건 정리** | 어떤 조건에서 터지는지 특정 |
| **검증 루프**      | 후보를 하나씩 확인          |

### 정리

1. **로그를 통째로 던지고 "왜 이래?"는 최악의 디버깅 프롬프트다.** 목적은 로그를 더 주는 게 아니라 **풀 수 있는 문제 형태로 바꾸는 것**이다.
2. **세 가지를 분리하라.** `Symptom`(무엇이 언제 실패했나) · `Evidence`(무엇을 관찰했나) · `Verification Path`(어떻게 확인하나). 특히 세 번째가 빠지면 가설은 추측으로
   끝난다.
3. **수정보다 원인 후보 좁히기가 먼저다.** 원인이 확정되지 않은 수정은 증상만 가린다.
4. **프롬프트는 다섯 조각으로.** `문제 · 환경 · 증거 · 제약 · 요청`, 그리고 요청 칸에는 "고쳐 줘"가 아니라 **원인 후보·확인 방법·관련 파일·회귀 테스트 필요 여부**를 적는다.
5. **"로컬에서는 되는데요"는 대개 설정 스코프 문제다.** 값 대신 **존재 여부·출처·범위·런타임 유무**를 주면, 시크릿을 노출하지 않고도 원인을 찾을 수 있다.
6. **확신할 때 반례를 물어라.** 자신 있게 지목한 원인일수록 검증이 필요하다.

## 6가지 하네스를 마치며

이것으로 섹션의 6가지 하네스를 모두 훑었습니다. 마지막으로 전체를 한 장으로 놓고 보겠습니다.

| # | 하네스                   | 설계하는 것                  | 핵심 문장                                         |
|---|--------------------------|------------------------------|---------------------------------------------------|
| 1 | **Context Harness**      | 무엇을 **보는가**            | 많이 주는 게 아니라 **올바른 첫 행동**을 하게     |
| 2 | **Permission Harness**   | 무엇을 **할 수 있는가**      | 신뢰가 아니라 **실패 비용** 기준                  |
| 3 | **Verification Harness** | 무엇으로 **완료를 판정**하나 | 실패하지 않는 게 아니라 **되돌릴 수 있는** 자동화 |
| 4 | **Tool Harness**         | 어느 **지점에 개입**하나     | 더 붙이는 게 아니라 **제자리에 두는 것**          |
| 5 | **Subagent & Worktree**  | 무엇을 **격리**하나          | 병렬 실행이 아니라 **병렬 격리**                  |
| 6 | **Debugging Harness**    | 문제를 **어떤 형태로** 주나  | 로그를 더 주는 게 아니라 **풀 수 있는 형태로**    |

여섯 챕터를 관통하는 문장은 결국 하나였습니다.

> **문제가 생겼을 때 "모델이 왜 이래?"가 아니라 "어느 하네스가 약한가?"를 먼저 묻는다.**

이 질문으로 바꾸는 순간, 할 수 있는 일이 "더 좋은 모델 기다리기"에서 **"오늘 고칠 파일 찾기"** 로 바뀝니다. 그게 하네스 엔지니어링의 전부입니다.
